第二部分 · 写入 Retain

05 · 实体解析与建边

上一章抽出了事实和一堆实体字符串。这一章回答两个问题:这些字符串如何被归一成规范实体(让 "Google" / "google inc" / "谷歌" 指向同一个)?事实之间如何建起时序 / 语义 / 因果三种边?以及,为"既不让慢操作长时间持锁、又保证检索数据原子可见"而设计的 Phase1 / 2 / 3 事务划分——这是 Retain 里最精巧的一处工程。

本章要点

  • 实体归一不用 LLM、不用 embedding,而是"字符串相似度 + 共现证据 + 时间接近"加权打分,阈值 0.6。便宜到可以在写入时同步跑。
  • 三种边各有来源:时序来自时间排序、语义来自向量 ANN、因果来自 LLM 抽取输出(只写 caused_by)。
  • "实体—实体"的可视化边不存储,由 /graph 从 unit_entities 按需派生。
  • Phase1(事务外)→ Phase2(短事务原子写)→ Phase3(提交后补边):慢读不持锁、检索依赖的数据原子可见、增强边失败不丢记忆。

2. 实体归一:一个朴素的加权打分

定位:engine/entity_resolver.py → _resolve_from_candidates(打分核心);候选生成 _resolve_entities_batch_impl。

先纠正一个直觉:这里的实体不是用 NER 模型在运行时识别的,而是直接来自上一章 LLM 抽取 schema 里的 entities 字符串列表。归一要解决的是:"这条事实提到的 'Google',是不是库里已有的那个 'Google Inc.'?"

第一步:生成候选

不会拿每个提及去和全表实体逐一比(太慢)。有三种候选生成策略:

策略做法说明
trigram(默认)用 pg_trgm 的 GIN 索引在库里做相似度连接(阈值降到 0.15)把"从 16.5 万行里找"压成"每个提及返回约 5–20 行"
full加载全 bank 实体,在 Python 里比(精确或双向子串包含)没装 pg_trgm 时的兜底
oracle_fuzzyOracle 的 JARO_WINKLER_SIMILARITY,阈值 70约等于 pg_trgm 0.15

第二步:打分(核心逻辑)

候选拿到后,对每个提及算一个 0–1 的分数,超过 0.6 就认为是同一实体,否则新建。打分由三项加权组成——没有 LLM,也没有 embedding:

engine/entity_resolver.py · _resolve_from_candidates(节选)python
for candidate_id, canonical_name, metadata, last_seen, mention_count in candidates:
    score = 0.0
    # 1. 名字相似度 (0–0.5)
    name_similarity = SequenceMatcher(None, entity_text.lower(), canonical_name.lower()).ratio()
    score += name_similarity * 0.5
    # 2. 共现实体 (0–0.3):和同一批其他实体一起出现过的证据
    if nearby_entity_set:
        overlap = len(nearby_entity_set & cooccurrence_map.get(candidate_id, set()))
        score += (overlap / len(nearby_entity_set)) * 0.3
    # 3. 时间接近 (0–0.2):7 天内出现过
    if last_seen and entity_event_date:
        days_diff = abs((event_date_utc - last_seen_utc).total_seconds() / 86400)
        if days_diff < 7:
            score += max(0, 1.0 - (days_diff / 7)) * 0.2

threshold = 0.6
if best_score > threshold and best_candidate is not None:
    resolved[idx] = best_candidate      # 归并到已有实体
else:
    entities_to_create.append(...)       # 新建实体

💡 为什么不用 LLM / embedding 来做归一?

因为归一发生在写入热路径上,每条事实的每个实体都要过一遍——调 LLM 或算 embedding 太贵太慢。而"字符串相似 + 共现 + 时间"这套启发式足够便宜(可以同步跑),效果也够好。这是一个典型的"在热路径上用廉价启发式、把昂贵操作留给离线"的取舍。共现信号来自 entity_cooccurrences 表(记录哪些实体曾在同一条事实里一起出现)。

规范化:先到先得,且大小写不敏感

  • entities 表的唯一索引建在 (bank_id, LOWER(canonical_name)) 上——所以 "Paris" 和 "paris" 在一个 bank 里是同一个实体。
  • 新建用 INSERT … ON CONFLICT DO NOTHING(不加行锁,并发安全)。规范名是"先到先得":第一个创建该实体的写法被存下,之后的变体只会解析到它,而不会改写它。
  • label 实体例外:配置出来的分类标签(形如 key:value)只做精确大小写不敏感匹配,绝不模糊归并——否则两个碰巧相似的标签值会被错误合并(issue GH-1558)。

⚠️ Python 的 lower() ≠ PostgreSQL 的 LOWER()

对土耳其语的 İ,Python str.lower() 和 PostgreSQL LOWER() 结果不同。所以身份匹配必须在数据库里两边都 lowercase,否则兜底的 SELECT 会漏配,进而触发 unit_entities.entity_id 的非空违约。

3. 三种边:temporal / semantic / causal

定位:engine/retain/link_utils.py(建边实现);link_creation.py(薄封装);表结构见第 02 章 memory_links。

所有边都存在 memory_links 表:from_unit_id / to_unit_id(指向事实,外键 DEFERRABLE INITIALLY DEFERRED)、link_type(CHECK 约束限定取值)、weight(0–1)。唯一性用 COALESCE(entity_id, '0000…0') 处理可空列。所有写入都是 ON CONFLICT DO NOTHING,所以重复探测永远安全。

时序边:时间上接近

只看 event_date 的排序。对每条有 event_date 的事实,找时间窗口内(默认 ±24h)的邻居,权重 = 时间接近度(下限 0.3):

engine/retain/link_utils.py · compute_temporal_links(节选)python
time_lower = unit_event_date_norm - timedelta(hours=time_window_hours)   # 默认 24h
time_upper = unit_event_date_norm + timedelta(hours=time_window_hours)
matching_neighbors = [
    (row["id"], row["event_date"]) for row in candidates
    if time_lower <= _normalize_datetime(row["event_date"]) <= time_upper
][:10]                                             # 最多取 10 个
for recent_id, recent_event_date in matching_neighbors:
    time_diff_hours = abs((unit_event_date_norm - _normalize_datetime(recent_event_date)).total_seconds() / 3600)
    weight = max(0.3, 1.0 - (time_diff_hours / time_window_hours))
    links.append((unit_id, str(recent_id), "temporal", weight, None))

✅ 一个 120× 的性能优化

批量版不会"扫描 24h 窗口里的所有事实"(那是 O(N),规模下是 16 万行),而是用 (bank_id, fact_type, event_date) 上的 B-tree 索引双向各取最近的 K 个。注释说在 16.4 万条时从 74ms 降到 0.6ms。每条事实的时序边上限 20 条——因为检索时用 LATERAL join 也只读 top 10–20,存更多只是浪费和写放大。

语义边:向量上相近

用向量 ANN 找余弦相似度 ≥ semantic_link_min_similarity 的邻居。关键是按 fact_type 分开探测,让规划器命中"每 bank、每 fact_type"的偏索引:

engine/retain/link_utils.py · compute_semantic_links_ann(节选)python
SELECT s.unit_id AS from_id, n.id::text AS to_id, n.similarity
FROM seeds s
CROSS JOIN LATERAL (
    SELECT mu.id, 1 - (mu.embedding <=> s.emb) AS similarity
    FROM memory_units mu
    WHERE mu.bank_id = $1
      AND mu.fact_type = $2              -- 命中 per-(bank,fact_type) 偏索引
      AND mu.embedding IS NOT NULL
    ORDER BY mu.embedding <=> s.emb      -- pgvector 余弦距离
    LIMIT $3
) n

⚠️ 故意不传"排除列表"

直觉上 ANN 探测时应排除自己/已处理的单元。但注释指出:传一个 8000+ UUID 的排除列表会逼 PostgreSQL 对每次 HNSW 探测退化成顺序扫描(8k seeds 耗时 67 秒)。于是干脆不排除——自环边无害,ON CONFLICT DO NOTHING 会处理重复。又一个"看似该做、实则有害"的反直觉优化。

因果边:来自 LLM 抽取,而非推导

和时序/语义不同,因果边是 LLM 抽取的直接输出(第 04 章 causal_relations 字段):模型被要求指出"这条事实是由批内哪条之前的事实引起的"。写入时只用规范的 caused_by 类型,权重恒为 1.0:

engine/retain/link_utils.py · _write_causal_links_batch(节选)python
for fact_idx, causal_relations in enumerate(causal_relations_per_fact):
    from_unit_id = unit_ids[fact_idx]
    for relation in causal_relations:
        target_idx = relation.target_fact_index
        if relation.relation_type not in allowed_relation_types: continue
        if target_idx < 0 or target_idx >= len(unit_ids): continue   # 校验序号
        to_unit_id = unit_ids[target_idx]
        if from_unit_id == to_unit_id: continue                      # 不自环
        links.append((from_unit_id, to_unit_id, relation_type, 1.0, None))

📖 因果边为何"不可再生"

时序边能从日期重算、语义边能从向量重算,但因果边是模型的主观判断,无法从数据重新推导。所以当一条事实被作废时,系统会把它的因果边快照进 invalidated_memory_units.causal_links,以便撤销时能重新物化(issue #2864)。这是"可再生 vs 不可再生"数据要区别对待的好例子。

实体—实体边:不存储,按需派生

⚠️ link_type 里有 'entity',但 Retain 从不写它

UI 上"实体连着实体"的图,不是在 Retain 时写满 memory_links 的,而是 /graph 端点从 unit_entities 按需派生的(migration e9b2c7d1f3a4 专门删掉了实体边存储)。原因很实在:实体边曾占全部边的 53%(约 190MB),而检索从来不读它们——只有可视化要。把"检索必需的边"和"可视化好看的边"分开,前者原子写入、后者失败也无妨,是第 5 节 Phase 划分的思想基础。

这是本章(乃至整个 Retain)最精巧的设计。核心矛盾:实体解析和 ANN 是慢读操作,而 facts + 边必须原子可见。怎么两全?

放在哪做什么为什么
Phase1(事务外)实体解析、ANN 候选计算这些是慢读;放进事务会长时间持行锁,并发下直接 TimeoutError
Phase2(短事务)facts + unit_entities + 三种边,一次提交保证检索永远看不到"半套数据"(有事实却没边)

# Phase 1: Run expensive read-heavy operations on a separate connection
# OUTSIDE the write transaction.
#   - Entity resolution: trigram GIN scan + co-occurrence fetch + scoring
#   - Semantic ANN: HNSW index probes to find similar existing units
# Running these outside the transaction avoids holding row locks during
# slow reads, eliminating TimeoutErrors under concurrent load.

# Phase 2 of the retain pipeline: insert facts and retrieval-critical links.
# Runs inside a single database transaction to ensure atomicity of the data
# that retrieval depends on (facts, unit_entities, temporal/semantic/causal links).
# Entity edges for UI graph visualization are derived on demand from
# unit_entities by the /graph endpoint, so no entity rows are written here.

占位 ID 与重映射

Phase1 时事实还没落库,没有真实 unit_id。于是用 str(fact_index)("0","1",…)当占位分组键。等 Phase2 的 insert_facts_batch 返回真实 UUID 后,_remap_phase1_results 把所有携带 unit id 的结构(实体映射、ANN 边的 from_id)统一替换。注意 ANN 边只重映射 from_id——to_id 是已存在的单元,本就有真 ID。

两个事务之间的"窗口陷阱"(issue #2662)

Phase1(解析)和 Phase2(写 unit_entities)是两个不同的事务。这中间有个时间窗:后台的图维护任务 prune_orphan_entities 会删除"没有任何 unit 引用的实体"。而 Phase1 刚建/解析出的实体此刻恰恰还没有 unit_entities 行——看起来就是个孤儿,会被误删!一旦删了,Phase2 的外键插入就失败,整批被当成不可重试错误丢弃 → 静默丢记忆。

💡 对策:reassert_entities_batch

在 Phase2 的连接上、真正建 unit_entities 之前,先调 reassert_entities_batch:对还活着的父实体加 FOR KEY SHARE 锁(让并发的 prune 删操作阻塞到本事务提交),对已经被删掉的原样重建。逻辑上,"被一个活单元引用的实体,按定义就不是孤儿",所以重建是正确的。这是一个"先制造不变量、再让并发操作遵守它"的经典并发修复。

5. 一组要记住的不变量

不变量为什么
所有边/实体写入都是 ON CONFLICT DO NOTHING幂等,重复探测安全
批量插边前按 (from_unit_id, to_unit_id) 排序强制全局一致的加锁顺序,消除循环等待死锁
实体解析 / ANN 绝不移进写事务慢读持锁 → 并发超时
mention_count 等统计在提交后、按 task 刷失败只丢统计,不丢记忆;并发 retain 不互相冲掉未提交 ID
ANN 的临时表 + 探测必须在同一事务pgBouncer transaction 池会在语句间换后端,跨语句临时表会"消失"
因果边作废时要快照它不可再生(见上)

小结

  • 实体归一 = 字符串相似(≤0.5)+ 共现(≤0.3)+ 时间接近(≤0.2),阈值 0.6,无 LLM、无 embedding。规范化先到先得、大小写不敏感。
  • 三种边:temporal(时间排序)、semantic(向量 ANN)、causal(LLM 输出,只写 caused_by)。实体—实体边不存储,由 /graph 派生。
  • Phase1(事务外慢读)→ Phase2(短事务原子写)→ Phase3(提交后补边),占位 ID 事后重映射;reassert_entities_batch 堵住 prune 窗口(#2662)。
