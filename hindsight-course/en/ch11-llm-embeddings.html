Part 5 · Cross-Cutting Infrastructure

11 · The LLM Abstraction & Embeddings

Every operation stands on the same foundation: calling an LLM (extract facts, consolidate, reflect) and generating embeddings (semantic retrieval). This chapter covers that cross-cutting abstraction — how a dozen providers collapse into one interface, how structured output is guaranteed, how embedding dimensions are managed, and a hierarchical-config truth that CLAUDE.md can mislead you on.

Chapter takeaways

  • Three layers: LLMProvider (facade) wraps an LLMInterface implementation the factory selects; the engine talks only to the facade (which adds concurrency permits, retry policy, tracing, multi-LLM routing). Embeddings are a separate, simpler hierarchy, one server-wide instance.
  • The interface has no streaming — Hindsight is a batch memory system, not a chat UI; every call awaits completion.
  • Provider selection is an if/elif factory; a large set (openai/groq/ollama/lmstudio/minimax…) all land on the same OpenAICompatibleLLM.
  • Structured output is a three-tier ladder: strict (grammar-enforced) → soft (prompt + json_object) → no grammar (some local backends).
  • Embedding dimension is owned by the model; the schema follows the model, a model switch recomputes the dimension (#2209).
  • provider/model/key are NOT per-bank configurable — they're server-level + per-operation; CLAUDE.md's “LLM settings are hierarchical” does not hold at the bank level.

2. The LLM interface: the contract

Locate: engine/llm_interface.py → LLMInterface (ABC). Four abstract methods: verify_connection, call, call_with_tools, cleanup.

               initial_backoff=1.0, max_backoff=60.0, skip_validation=False,
               strict_schema=False, return_usage=False, cached_prefix=None) -> Any:
    # response_format: a Pydantic model for structured output
    # scope: a scope id for tracing
    # strict_schema: grammar-enforce via json_schema strict (rather than soft json_object)
    # return_usage: if True, return (result, TokenUsage)
    # cached_prefix: an opaque handle for a cacheable system prefix (Gemini etc.)
  • No streaming: grepping stream in the LLM layer is empty. Every call waits to completion — fitting a “memory system”, not a “chat UI”.
  • Capability hooks default to no-ops: supports_batch_api(), supports_prompt_caching() + get_or_create_cached_prefix(), etc.; providers that don't support them “transparently run uncached”. The division of labor is explicit: “the engine decides WHAT is cacheable; the provider only chooses HOW to cache” (Gemini explicit CachedContent / OpenAI automatic / Anthropic inline markers).
  • Tool calls return LLMToolCallResult, using a typed LLMToolChoice (AUTO/NONE/REQUIRED/NAMED) — “serialized only at provider boundaries”, so a provider's native tool-choice dialect never leaks into engine code.

3. The LLMProvider facade: cross-cutting concerns

Locate: engine/llm_wrapper.py → LLMProvider.

💡 The constructor deliberately “reads no global config”

LLMProvider's constructor takes ~20 arguments and deliberately does not read the global HindsightConfig. Why? So “a provider's effective config is a pure function of its arguments” — and that is exactly the precondition for letting each member of a multi-LLM chain be configured independently. Default resolution is left to the caller.

LLMProvider.call does the cross-cutting work, then delegates:

  1. Retry-policy resolution: this call's arg → provider-configured default → method fallback (10/1.0/60.0).
  2. strict_schema resolved once: x if x is not None else get_config().llm_strict_schema. The comment warns you can't use or — that would make “explicitly passed False this call” indistinguishable from “unset”.
  3. Concurrency permits: enter all semaphores for that scope (per-operation + global), tagging a .queued stage first. The comment cites incident #3002: someone once spent an hour debugging llm.bedrock.* for tasks that had never reached Bedrock — they were stuck in the queue.
  4. Delegate to _provider_impl.call(...); on exception, attach the provider-reported usage to the error trace (the provider charged regardless of success).

Token accounting: two paths

  • Return path: return_usage=True returns (result, TokenUsage); TokenUsage has input/output/total/cached/thoughts_tokens and __add__ for aggregation.
  • Side-channel: providers stash usage into a contextvar before local parsing (stash_response_usage). Why? issue #2387 — the provider call may have succeeded and been billed, but the subsequent JSON parse/validation fails; then the real token count must be attached to the error trace (the money is spent either way).

The retry loop lives inside each provider, exponential backoff; classification is careful: 401/403 fast-fail, no retry (auth errors won't improve); OutputTooLongError not retried; MultiLLMProvider adds a tier — each member exhausts its own retries, then the router advances (failover or weighted round-robin), but over-length output never fails over (“a different provider won't fit it either”).

OpenAICompatibleLLM (~1700 lines) is the workhorse: it builds one call_params dict + per-vendor fixups (Groq seed/service_tier; MiniMax temperature clamped to [0.01,1]; reasoning models get reasoning_effort and a 16k-token floor) and absorbs a large set of OpenAI-compatible backends. Per-operation provider selection happens in MemoryEngine.__init__, as three independent fallback chains: retain/reflect/consolidation_llm_provider or config.* or memory_llm_provider.

⚠️ LLMConfig is not a config object

LLMConfig = LLMProvider (just an alias). Reading memory_engine._build_llm while assuming LLMConfig is a plain config is a quick way to get confused — it's actually the provider facade.

6. Embeddings: a simpler, separate hierarchy

Locate: engine/embeddings.py.

The Embeddings ABC has only four things: provider_name, dimension (int property), initialize(), encode(texts). Implementations include local (sentence-transformers), ONNX, TEI, OpenAI, Cohere, Gemini, etc. The engine holds one server-wide instance.

💡 The dimension is owned by the model; the schema follows

The dimension is probed at init (local reads the model's get_sentence_embedding_dimension(); TEI embeds a literal "test" and measures the length), and at startup the live dimension is passed into migrations so the pgvector column matches. A model switch re-dimensions memory_units, designed to be “structurally unable to trip a dimension mismatch” (#2209). The archive table simply has no embedding column, so an “archive vector” can't fall out of sync.

Two local-vs-TEI details: local doesn't use MPS by default (MPS leaks memory under variable-length workloads); the CPU encode deliberately skips gc/malloc_trim (it runs in retain's tight loop, where gc every call is too costly). TEI is an httpx client, batch_size=32, exponential backoff only on connect errors/timeouts/5xx. There is no embedding-level cache — only batching and GPU-memory reclamation.

7. Hierarchical config: an important clarification

Locate: config_resolver.py → ConfigResolver (get_bank_config for the API, resolve_full_config internally, keeping credentials).

Resolution order: ① global (env) → ② tenant overrides → ③ bank overrides. Resolved on every call (not cached), for consistency across multiple API servers. But here's the key:

⚠️ “LLM settings are hierarchical” is a misunderstanding at the bank level

Tenant and bank overrides are both filtered to the _CONFIGURABLE_FIELDS allow-list. And the LLM provider/model/key fields are not in that set (they live in _CREDENTIAL_FIELDS); the allow-list holds only behavioral fields (retain_chunk_size, retain_extraction_mode, mission, disposition, recall budgets, etc.). So although CLAUDE.md short-hands it as “LLM settings are hierarchical”, in reality provider/model selection is server-level and per-operation only (the three static retain/reflect/consolidation fallback chains), never per-bank. The resolver even re-pins the multi-LLM chain objects from global config, “never tenant/bank-overridable”.

Summary

  • LLM three layers: interface LLMInterface → facade LLMProvider (cross-cutting) → concrete provider (factory if/elif); no streaming; structured output a three-tier ladder.
  • A large provider set converges on OpenAICompatibleLLM; per-operation provider selection (three fallback chains); LLMConfig is just LLMProvider.
  • Embedding dimension model-owned, schema follows, model switch recomputes; no cache.
  • provider/model/key are not per-bank configurable (the allow-list holds only behavioral fields) — don't be misled by CLAUDE.md. none/mock each have a purpose.
