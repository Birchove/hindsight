Part 5 · Cross-Cutting Infrastructure

11 · The LLM Abstraction Layer & Embeddings

Every operation earlier stood on the same foundation: calling an LLM (fact extraction, consolidation, reflect) and generating embeddings (semantic retrieval). This chapter covers that cross-cutting abstraction — how a dozen providers collapse into one interface, how structured output is guaranteed, how embedding dimensions are managed, and a hierarchical-config truth that CLAUDE.md can mislead you about.

Chapter takeaways

  • Three layers: LLMProvider (facade) wraps an LLMInterface implementation chosen by a factory; the engine only talks to the facade (which adds concurrency permits, retry policy, tracing, multi-LLM routing). Embeddings are a separate, simpler hierarchy, one server-wide instance.
  • The interface has no streaming — Hindsight is a batch memory system, not a chat UI; every call is awaited to completion.
  • Provider selection is one if/elif factory; a large group (openai/groq/ollama/lmstudio/minimax…) all land on the same OpenAICompatibleLLM.
  • Structured output in three tiers: strict (grammar-enforced) → soft (prompt + json_object) → no grammar (some local backends).
  • The embedding dimension is owned by the model; the schema follows the model, and a model switch re-dimensions (#2209).
  • Provider/model/key are not per-bank overridable — they're server-level + per-operation; CLAUDE.md's “LLM settings are hierarchical” does not hold at the bank level.

2. The LLM interface: the contract

Locate: engine/llm_interface.py → LLMInterface (ABC). Four abstract methods: verify_connection, call, call_with_tools, cleanup.

               initial_backoff=1.0, max_backoff=60.0, skip_validation=False,
               strict_schema=False, return_usage=False, cached_prefix=None) -> Any:
    # response_format: a Pydantic model for structured output
    # scope: a scope identifier for tracking
    # strict_schema: grammar-enforce via json_schema strict (vs soft json_object)
    # return_usage: if True, return (result, TokenUsage)
    # cached_prefix: an opaque handle for a cacheable system prefix (Gemini etc.)
  • No streaming: grep stream in the LLM layer is empty. Every call is awaited to completion — fitting a “memory system” rather than a “chat UI”.
  • Capability hooks default to no-ops: supports_batch_api(), supports_prompt_caching() + get_or_create_cached_prefix(), etc.; a provider that doesn't support them just “transparently runs uncached”. The division of labor is written plainly: “the engine decides WHAT is cacheable; a provider only chooses HOW to cache that prefix” (explicit Gemini CachedContent / OpenAI automatic / Anthropic inline markers).
  • Tool calls return an LLMToolCallResult, using a typed LLMToolChoice (AUTO/NONE/REQUIRED/NAMED) — “serialized only at provider boundaries”, so a provider's native tool-choice dialect never leaks into engine code.

3. The LLMProvider facade: cross-cutting concerns

Locate: engine/llm_wrapper.py → LLMProvider.

💡 The constructor deliberately “reads no global config”

LLMProvider's constructor takes ~20 arguments and deliberately does not read the global HindsightConfig. Why? So that “a provider's effective settings are a pure function of its arguments” — which is exactly the prerequisite for each member of a multi-LLM chain to be configured independently. Resolving defaults is left to the caller.

LLMProvider.call does the cross-cutting work then delegates:

  1. Retry-policy resolution: per-call arg → provider-configured default → method fallback (10/1.0/60.0).
  2. strict_schema resolved once: x if x is not None else get_config().llm_strict_schema. The comment warns: you can't use or — that would make “explicitly passed False this call” indistinguishable from “unset”.
  3. Concurrency permits: enter every semaphore for that scope (per-operation + global), first tagging a .queued stage. The comment cites incident #3002: someone once spent an hour debugging llm.bedrock.* for tasks that had never even reached Bedrock — they were stuck in the queue.
  4. Delegate to _provider_impl.call(...); on exception, attach the provider's already-reported usage to the error trace (the provider charged whether or not it succeeded).

Token accounting: two paths

  • Return path: return_usage=True returns (result, TokenUsage); TokenUsage has input/output/total/cached/thoughts_tokens and an __add__ for aggregation.
  • Side channel: providers stash usage into a contextvar before local parsing (stash_response_usage). Why? issue #2387 — the provider call may have succeeded and been billed, but the subsequent JSON parse/validation fails; then the real token count must be attached to the error trace (the money's spent regardless).

The retry loop lives inside each provider, exponential backoff; classification is careful: 401/403 fast-fail, no retry (retrying an auth error is pointless); OutputTooLongError not retried; MultiLLMProvider adds another tier — each member exhausts its own retries, then the router advances (failover or weighted round-robin), but over-length output does not fail over (“a different provider won't fit it either”).

OpenAICompatibleLLM (~1700 lines) is the workhorse: one call_params dict + small per-vendor fixups (Groq's seed/service_tier; MiniMax temperature clamped to [0.01,1]; reasoning models get reasoning_effort and a 16k token floor) absorbs a large set of OpenAI-compatible backends. Per-operation provider selection happens in MemoryEngine.__init__, as three independent fallback chains: retain/reflect/consolidation_llm_provider or config.* or memory_llm_provider.

⚠️ LLMConfig is not a config object

LLMConfig = LLMProvider (just an alias). Reading memory_engine._build_llm while assuming LLMConfig is a pure config will confuse you — it's actually that provider facade.

6. Embeddings: another, simpler hierarchy

Locate: engine/embeddings.py.

The Embeddings ABC has just four members: provider_name, dimension (int property), initialize(), encode(texts). Implementations include local (sentence-transformers), ONNX, TEI, OpenAI, Cohere, Gemini, etc. The engine holds one server-wide instance.

💡 The dimension is owned by the model; the schema follows

The dimension is probed at init (local reads the model's get_sentence_embedding_dimension() directly; TEI embeds a literal "test" and measures the length), and at startup the live dimension is passed into migrations so the pgvector column matches. A model switch re-dimensions memory_units, designed to be “structurally unable to trip a vector-dimension mismatch” (#2209). The archive table has no embedding column at all, so the “archive vector” can't fall out of sync with the live model.

Two local-vs-TEI details: local by default doesn't use MPS (MPS leaks memory under variable-length workloads); the CPU encode deliberately skips gc/malloc_trim (it runs in tight retain loops, so a gc every call is too costly). TEI is an httpx client, batch_size=32, retrying only connect errors/timeouts/5xx with exponential backoff. There is no embedding-level cache — only batching and GPU memory reclamation.

7. Hierarchical config: an important clarification

Locate: config_resolver.py → ConfigResolver (get_bank_config for the public API, resolve_full_config internal keeping credentials).

Resolution order: ① global (env) → ② tenant overrides → ③ bank overrides. Resolved on every call (not cached), for consistency across multiple API servers. But the key point is here:

⚠️ “LLM settings are hierarchical” is a misunderstanding at the bank level

Both tenant and bank overrides are filtered to the _CONFIGURABLE_FIELDS allowlist. And the LLM provider/model/key fields are not in that set (they're in _CREDENTIAL_FIELDS); the allowlist holds only behavioral fields (retain_chunk_size, retain_extraction_mode, mission, disposition, recall budgets, etc.). So although CLAUDE.md shorthand says “LLM settings are hierarchical”, in reality provider/model selection is server-level and per-operation only (the three static retain/reflect/consolidation fallback chains), never per-bank. The resolver even re-pins multi-LLM chain objects from the global config as “never tenant/bank-overridable”.

Summary

  • LLM in three layers: interface LLMInterface → facade LLMProvider (cross-cutting) → concrete provider (factory if/elif); no streaming; structured output on a three-tier ladder.
  • A large group of providers collapses into OpenAICompatibleLLM; provider chosen per operation (three fallback chains); LLMConfig is just LLMProvider.
  • Embedding dimension owned by the model, schema follows, model switch re-dimensions; no cache.
  • Provider/model/key are not per-bank overridable (the allowlist holds only behavioral fields) — don't be misled by CLAUDE.md. none/mock each have a purpose.
