Part 2 · Writing (Retain)

05 · Entity Resolution & Link Building

Last chapter produced facts and a pile of entity strings. This chapter answers two questions: how are those strings normalized into canonical entities (so “Google” / “google inc” / “Alphabet” point to one)? And how are the three edge types — temporal / semantic / causal — built between facts? Plus the Phase1 / 2 / 3 transaction split, the mostrefined piece of engineering in Retain, designed so slow operations don't hold locks long while retrieval data stays atomically visible.

Chapter takeaways

  • Entity normalization uses no LLM and no embedding — a weighted score of “string similarity + co-occurrence evidence + temporal proximity”, threshold 0.6. Cheap enough to run synchronously on the write path.
  • The three edges come from different sources: temporal from time ordering, semantic from vector ANN, causal from LLM extraction output (only caused_by is written).
  • “Entity–entity” visualization edges are not stored; /graph derives them from unit_entities on demand.
  • Phase1 (outside txn) → Phase2 (short atomic txn) → Phase3 (backfill after commit): slow reads hold no locks, retrieval-critical data is atomically visible, enhancement edges may fail without losing memory.

2. Entity normalization: a plain weighted score

Locate: engine/entity_resolver.py → _resolve_from_candidates (the scoring core); candidate generation in _resolve_entities_batch_impl.

First, a correction to intuition: the entities here are not recognized at runtime by an NER model — they come straight from the LLM extraction schema's entities string list (ch04). Normalization answers: “is this fact's mention of 'Google' the same as the 'Google Inc.' already in the store?”

Step one: generate candidates

It does not compare each mention against every entity in the table (too slow). Three candidate-generation strategies exist:

StrategyHowNote
trigram (default)a pg_trgm GIN similarity join in the DB (threshold lowered to 0.15)shrinks “search 165k rows” to “~5–20 rows per mention”
fullload all the bank's entities and compare in Python (exact or two-way substring)fallback when pg_trgm isn't installed
oracle_fuzzyOracle's JARO_WINKLER_SIMILARITY, threshold 70roughly equal to pg_trgm 0.15

Step two: score (the core logic)

With candidates in hand, each mention gets a 0–1 score; above 0.6 it's deemed the same entity, otherwise a new one is created. The score is three weighted terms — no LLM, no embedding:

engine/entity_resolver.py · _resolve_from_candidates (excerpt)python
for candidate_id, canonical_name, metadata, last_seen, mention_count in candidates:
    score = 0.0
    # 1. Name similarity (0-0.5)
    name_similarity = SequenceMatcher(None, entity_text.lower(), canonical_name.lower()).ratio()
    score += name_similarity * 0.5
    # 2. Co-occurring entities (0-0.3): evidence of appearing with the same other entities
    if nearby_entity_set:
        overlap = len(nearby_entity_set & cooccurrence_map.get(candidate_id, set()))
        score += (overlap / len(nearby_entity_set)) * 0.3
    # 3. Temporal proximity (0-0.2): seen within 7 days
    if last_seen and entity_event_date:
        days_diff = abs((event_date_utc - last_seen_utc).total_seconds() / 86400)
        if days_diff < 7:
            score += max(0, 1.0 - (days_diff / 7)) * 0.2

threshold = 0.6
if best_score > threshold and best_candidate is not None:
    resolved[idx] = best_candidate      # merge into the existing entity
else:
    entities_to_create.append(...)       # create a new entity

💡 Why not use an LLM / embedding for normalization?

Because normalization happens on the write hot path — every entity of every fact goes through it — and calling an LLM or computing an embedding is too costly and slow. The “string similarity + co-occurrence + time” heuristic is cheap enough to run synchronously, and good enough. A classic “use a cheap heuristic on the hot path, save the expensive operation for offline” trade-off. The co-occurrence signal comes from the entity_cooccurrences table (which entities appeared together in the same fact).

Canonicalization: first-writer-wins, case-insensitive

  • The entities table's unique index is on (bank_id, LOWER(canonical_name)) — so “Paris” and “paris” are one entity within a bank.
  • Creation uses INSERT … ON CONFLICT DO NOTHING (no row lock, concurrency-safe). The canonical name is “first-writer-wins”: the first variant to create the row is stored; later variants only resolve to it, never rewrite it.
  • Label entities are the exception: configured classification labels (like key:value) match by exact case-insensitive only, never fuzzy-merged — otherwise two label values that happen to look alike would be wrongly collapsed (GH-1558).

⚠️ Python's lower() ≠ PostgreSQL's LOWER()

For the Turkish İ, Python str.lower() and PostgreSQL LOWER() disagree. So identity matching must lowercase both sides in the database, or the fallback SELECT misses and triggers a NOT NULL violation on unit_entities.entity_id.

3. The three edge types: temporal / semantic / causal

Locate: engine/retain/link_utils.py (the implementations); link_creation.py (thin wrapper); table structure in ch02's memory_links.

All edges live in memory_links: from_unit_id / to_unit_id (point at facts; FKs are DEFERRABLE INITIALLY DEFERRED), link_type (a CHECK constraint limits the values), weight (0–1). Uniqueness handles the nullable column with COALESCE(entity_id, '0000…0'). Every write is ON CONFLICT DO NOTHING, so re-probing is always safe.

Temporal edges: close in time

Computed from event_date ordering alone. For each fact that has an event_date, find neighbors within a time window (default ±24h); weight = temporal proximity (floored at 0.3):

engine/retain/link_utils.py · compute_temporal_links (excerpt)python
time_lower = unit_event_date_norm - timedelta(hours=time_window_hours)   # default 24h
time_upper = unit_event_date_norm + timedelta(hours=time_window_hours)
matching_neighbors = [
    (row["id"], row["event_date"]) for row in candidates
    if time_lower <= _normalize_datetime(row["event_date"]) <= time_upper
][:10]                                             # take at most 10
for recent_id, recent_event_date in matching_neighbors:
    time_diff_hours = abs((unit_event_date_norm - _normalize_datetime(recent_event_date)).total_seconds() / 3600)
    weight = max(0.3, 1.0 - (time_diff_hours / time_window_hours))
    links.append((unit_id, str(recent_id), "temporal", weight, None))

✅ A 120× speedup

The batched version does not “scan every fact in the 24h window” (that's O(N) — 160k rows at scale); instead it uses the B-tree index on (bank_id, fact_type, event_date) to take the nearest K in each direction. The comment reports 74ms → 0.6ms at 164k units. Each fact's temporal edges are capped at 20 — because retrieval's LATERAL join only reads the top 10–20 per unit anyway, so storing more is just waste and write amplification.

Semantic edges: close in vector space

Vector ANN finds neighbors with cosine similarity ≥ semantic_link_min_similarity. The key is to probe per fact_type, so the planner hits the per-(bank, fact_type) partial indexes:

engine/retain/link_utils.py · compute_semantic_links_ann (excerpt)sql
SELECT s.unit_id AS from_id, n.id::text AS to_id, n.similarity
FROM seeds s
CROSS JOIN LATERAL (
    SELECT mu.id, 1 - (mu.embedding <=> s.emb) AS similarity
    FROM memory_units mu
    WHERE mu.bank_id = $1
      AND mu.fact_type = $2              -- hits the per-(bank,fact_type) partial index
      AND mu.embedding IS NOT NULL
    ORDER BY mu.embedding <=> s.emb      -- pgvector cosine distance
    LIMIT $3
) n

⚠️ Deliberately no exclusion list

Intuition says an ANN probe should exclude self / already-processed units. But the comment notes: passing an 8000+ UUID exclusion list forces PostgreSQL to sequential-scan every HNSW probe (67s for 8k seeds). So it simply doesn't exclude — self-loop edges are harmless, and ON CONFLICT DO NOTHING handles duplicates. Another counter-intuitive “looks like you should, but it hurts” optimization.

Causal edges: from LLM extraction, not derived

Unlike temporal/semantic, causal edges are the LLM extraction's direct output (the causal_relations field from ch04): the model is asked to state “which earlier fact in the batch caused this one”. At write time only the canonical caused_by type is used, weight always 1.0:

engine/retain/link_utils.py · _write_causal_links_batch (excerpt)python
for fact_idx, causal_relations in enumerate(causal_relations_per_fact):
    from_unit_id = unit_ids[fact_idx]
    for relation in causal_relations:
        target_idx = relation.target_fact_index
        if relation.relation_type not in allowed_relation_types: continue
        if target_idx < 0 or target_idx >= len(unit_ids): continue   # validate the index
        to_unit_id = unit_ids[target_idx]
        if from_unit_id == to_unit_id: continue                      # no self-loop
        links.append((from_unit_id, to_unit_id, relation_type, 1.0, None))

📖 Why causal edges are “non-regenerable”

Temporal edges can be recomputed from dates and semantic edges from vectors, but a causal edge is the model's subjective judgment and cannot be re-derived from the data. So when a fact is invalidated, the system snapshots its causal edges into invalidated_memory_units.causal_links, so a revert can rematerialize them (issue #2864). A good example of treating regenerable vs non-regenerable data differently.

Entity–entity edges: not stored, derived on demand

⚠️ link_type lists 'entity', but Retain never writes it

The “entity connected to entity” graph you see in the UI is not written into memory_links at Retain time — the /graph endpoint derives it from unit_entities on demand (migration e9b2c7d1f3a4 dropped entity-edge storage). The reason is plain: entity edges were 53% of all edges (~190MB), and retrieval never reads them — only visualization wants them. Separating “edges retrieval needs” from “edges that look nice in a graph” — the former written atomically, the latter allowed to fail — is the idea behind the Phase split in §4.

4. Phase1 / 2 / 3: how the transaction boundaries are drawn

This is the mostrefined design in this chapter (and in all of Retain). The core tension: entity resolution and ANN are slow reads, yet facts + edges must be atomically visible. How to have both?

Placeholder IDs and remapping

In Phase1 the facts aren't persisted yet, so there are no real unit_ids. So str(fact_index) (“0”, “1”, …) is used as a grouping key. After Phase2's insert_facts_batch returns real UUIDs, _remap_phase1_results rewrites every structure that carries a unit id (entity mappings, the from_id of ANN edges). Note ANN edges only remap from_id — the to_ids are already-existing units with real IDs.

The “window trap” between the two transactions (issue #2662)

Phase1 (resolution) and Phase2 (writing unit_entities) are two different transactions. In the gap between them, the background graph-maintenance job prune_orphan_entities deletes entities that “no unit references”. But an entity Phase1 just created/resolved has no unit_entities row yet — it looks exactly like an orphan and gets wrongly deleted! Once deleted, Phase2's FK insert fails and the whole batch is dropped as a non-retryable error → silent memory loss.

💡 The fix: reassert_entities_batch

On the Phase2 connection, right before building unit_entities, call reassert_entities_batch: take a FOR KEY SHARE lock on the parents that still exist (so a concurrent prune DELETE blocks until this transaction commits), and re-insert any that were already pruned. Logically, “an entity referenced by a live unit is by definition not an orphan”, so resurrecting it is correct. A classic concurrency fix: establish the invariant first, then make the concurrent operation respect it.

5. Invariants to remember

InvariantWhy
every edge/entity write is ON CONFLICT DO NOTHINGidempotent; re-probing is safe
batch edge inserts are sorted by (from_unit_id, to_unit_id)force a global lock-acquisition order; eliminate circular-wait deadlocks
entity resolution / ANN are never moved into the write txnslow reads holding locks → concurrent timeouts

causal edges are snapshotted on invalidationthey are non-regenerable (see above)

Summary

  • Entity normalization = string similarity (≤0.5) + co-occurrence (≤0.3) + temporal proximity (≤0.2), threshold 0.6, no LLM, no embedding. Canonicalization is first-writer-wins, case-insensitive.
  • Three edges: temporal (time ordering), semantic (vector ANN), causal (LLM output, only caused_by). Entity–entity edges are not stored, derived by /graph.
  • Phase1 (slow reads outside txn) → Phase2 (short atomic txn) → Phase3 (backfill after commit), placeholder IDs remapped afterwards; reassert_entities_batch closes the prune window (#2662).
