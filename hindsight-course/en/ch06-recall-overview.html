Part 3 · Retrieval — Recall

06 · Recall Overview & Query Analysis

From this chapter on we enter the read path. Recall is where Hindsight's retrieval quality comes from: it finds memories four arms at once, then fuses and reranks. This chapter first builds the overall pipeline and clears up a common misconception — the thing called the “query analyzer” actually extracts just one thing: a temporal constraint. The four arms' internals and the fusion/reranking are in chapters 07 and 08.

Chapter takeaways

  • Recall = four-arm parallel retrieval (semantic / BM25 / graph / temporal) → fusion → cross-encoder rerank → token trim.
  • The query analyzer is not an LLM intent classifier: using dateparser (or a small local T5) it only pulls out a (start_date, end_date) window, used to decide whether to run the temporal arm at all.
  • The “four-way parallel” real shape is batched + selectively parallel: semantic+BM25 are fused in one SQL statement on one connection; temporal is a second query; only graph retrieval truly runs concurrently per fact_type (asyncio.gather).
  • Resources are controlled by budgeted_operation (connection budget, default 4) + a semaphore + thinking_budget (top-k); each arm has its own degradation on failure.

1. Why four arms?

Every single retrieval method has blind spots:

  • Semantic (vector) is good at “similar meaning” but insensitive to exact keywords (product names, IDs).
  • Keyword (BM25) is good at exact-term matching but misses synonymous rewordings.
  • Graph (link expansion) finds facts “that semantic/keyword both miss but that are related through an entity or a causal link”.
  • Temporal specifically answers “what happened in June”, “last week's stuff” — questions with a time window.

💡 Complementary, then let fusion adjudicate

Each arm recalls a batch of candidates from a different angle (and each arm's scores are in a different unit: cosine similarity, BM25 score, graph activation, temporal proximity). Fusion then merges their ranks (not their scores) — so you never have to force four incomparable scales onto one. That's the motivation for RRF in chapter 08.

3. Query analysis: only a temporal constraint

Locate: engine/query_analyzer.py, engine/search/temporal_extraction.py.

Many people hear “query analyzer” and assume “use an LLM to judge intent, extract entities, rewrite the query”. None of that. Its output has a single optional field:

engine/query_analyzer.py · QueryAnalysispython
class QueryAnalysis(BaseModel):
    """Result of analyzing a natural language query.
    Contains extracted structured information like temporal constraints."""
    temporal_constraint: TemporalConstraint | None = Field(
        default=None, description="Extracted temporal constraint, if any")
# TemporalConstraint is just start_date + end_date, two datetimes.
# No intent field, no entity list, no rewritten query.

It has two implementations, neither of which is the configured business LLM:

ImplementationHowCost
DateparserQueryAnalyzer (default)Pure library + rules: first try period extraction (“last week / last year”), then dateparser.search_dates, score every candidate and keep the strongest~10–50 ms, no model
TransformerQueryAnalyzer (optional)A small local model google/flan-t5-small (~80M): rules first, fall back to few-shot date-range generationsmall local model

💡 Why “score” the date matches? (issue #2768)

dateparser over-matches: short common words that happen to be weekday/month abbreviations in some language (“we”/“me”/“did” → a weekday, “do” → Sunday) come back as bogus dates. If such a false positive appears before the real date in the query, taking the first match silently produces a wrong temporal window — worse than none. So rather than a blacklist, each match is scored by the date signal it actually carries: a digit +100, a month/relative word +50, a weekday +30, a period word +20; a bare token scores 0 and is rejected.

The query analyzer runs before any database work; its output decides “whether to run the temporal arm at all”. Any dateparser exception is swallowed into “no constraint” — a parser bug must never bring down the whole retrieval.

4. The real shape of “four-way parallel”

The module bills itself as “4-way parallel search”, but the concrete orchestration is batched + selectively parallel, not four independent concurrent tasks:

flowchart TB A["1 temporal-constraint extraction (CPU, no DB)"] --> B B["2 semantic + BM25: fused in one SQL
(same connection, sequential)"] B --> C["3 temporal retrieval: a 2nd query on the same connection
(only if there is a constraint)"] B --> D["4 graph retrieval: one task per fact_type
asyncio.gather, true concurrency"] C --> D D --> E["aggregate per fact_type"]
Fig 6-2: the only true concurrency is the graph step. Semantic and BM25 are interleaved arms of one SQL statement, so they “run together”; temporal reuses the same connection.

💡 Why aren't semantic and BM25 on separate connections?

Two reasons: (1) asyncpg forbids concurrent queries on one connection; (2) making semantic and BM25 interleaved UNION ALL arms of one SQL statement gets both in a single round trip — a deliberate optimization (comment: “reduces connection usage from 2 to 1”). Temporal reuses the same connection for the same reason. Only graph retrieval (one independent connection per fact_type) uses asyncio.gather for true concurrency, and it depends on the seeds the semantic phase produced (see chapter 07), so it can only run after semantic.

What happens when one arm fails

  • Graph: asyncio.wait_for timeout → fall back to semantic+causal only (drop the most expensive entity self-join). No seeds → that fact type returns empty (graph just contributes nothing).
  • BM25 (Oracle): full-text index not synced (DRG-10599, etc.) → the whole query is rebuilt as semantic-only.
  • Temporal: no constraint → the whole arm is skipped; Oracle lacks unnest → “spreading” is skipped but entry points still return.
  • Connection-level: connection errors retry 3× with exponential backoff; but a client-disconnect cancellation error is never retried — re-raised directly.

⚠️ asyncio.gather has no return_exceptions

The graph retrieval's asyncio.gather is called without return_exceptions=True. So an unexpected exception in one graph task propagates and fails the whole recall (caught upstream by the retry/500 logic), rather than being swallowed. In other words: at the gather layer a failing arm is not “quietly dropped” — usually a good thing (no silence), but it also means one arm's surprise crash drags down the whole retrieval.

5. Key data structures

The unified carrier the four arms return is RetrievalResult (search/types.py): it carries the memory payload (id/text/fact_type/time/tags/proof_count, etc.) plus several score slots where only one is set per source:

FieldSet by
similaritythe semantic arm
bm25_scorethe keyword arm
activationthe graph arm (the additive multi-signal score)
temporal_score / temporal_proximitythe temporal arm

Above that are aggregate structures: SemanticBm25Result (per-fact-type semantic/bm25/graph seeds), ParallelRetrievalResult (the four lists + per-arm timings + the temporal constraint), MultiFactTypeRetrievalResult (the per-fact-type dict + aggregate timings). The post-fusion MergedCandidate and post-rerank ScoredResult are in chapter 08.

✅ Cancellation is cooperative

After the client disconnects, the engine checks request_context.raise_if_cancelled() at each stage boundary. So a recall can still be “mid-query” when the client leaves — cancellation isn't a hard kill, it takes effect at the next checkpoint. The most expensive cross-encoder stage checks explicitly right before it runs (chapter 08).

Summary

  • Recall = four arms (semantic/BM25/graph/temporal) complementary recall → fusion → rerank → trim.
  • The query analyzer only extracts a temporal constraint (dateparser + a false-positive-scoring guard, or a small local T5) — not an LLM intent classifier.
  • Real parallelism: semantic+BM25 in one SQL, temporal in one SQL, graph gather-concurrent per fact_type; connection budget 4.
  • Each arm has degradation on failure; gather doesn't swallow exceptions.
