Part 3 · Retrieval (Recall)

06 · Recall Overview & Query Analysis

From here on we enter the read path. Recall is the source of Hindsight's retrieval quality: it finds memories four ways at once, then fuses and reranks. This chapter builds the overall pipeline and clears up a common misunderstanding — the thing called “query analyzer” actually extracts only one thing: a temporal constraint. The internals of the four paths and the fusion/rerank stage are chapters 07 and 08.

Chapter takeaways

  • Recall = four parallel retrievals (semantic / BM25 / graph / temporal) → fusion → cross-encoder rerank → token trim.
  • Query analysis is not an LLM intent classifier: it only uses dateparser (or a small local T5) to extract a (start_date, end_date) window, which decides whether to run the temporal path at all.
  • “Four-way parallel” is really batched + selectively parallel: semantic + BM25 are fused into one SQL on one connection; temporal is a second query; only graph retrieval is truly concurrent per fact_type (asyncio.gather).
  • Resources are governed by budgeted_operation (connection budget, default 4) + a semaphore + thinking_budget (top-k); each path has its own degradation on failure.

1. Why four paths?

Any single retrieval method has blind spots:

  • Semantic (vector) is good at “similar meaning” but insensitive to exact keywords (product names, codes).
  • Keyword (BM25) is good at exact word matches but misses synonymous rephrasings.
  • Graph (link expansion) finds facts that “semantic/keyword both miss but that are connected through an entity or a cause”.
  • Temporal specifically answers windowed questions like “what happened in June” or “last week's stuff”.

💡 Complementary, then let fusion adjudicate

Each path recalls a batch of candidates from a different angle — and each path's scores are on a different scale (cosine similarity, BM25 score, graph activation, temporal proximity). Fusion then merges their ranks (not their scores), so you never have to force four incommensurable scales onto one axis. That is the motivation for RRF in ch08.

3. Query analysis: only a temporal constraint

Locate: engine/query_analyzer.py, engine/search/temporal_extraction.py.

Many people hear “query analyzer” and assume “an LLM that judges intent, extracts entities, rewrites the query”. None of that. Its output has a single optional field:

engine/query_analyzer.py · QueryAnalysispython
class QueryAnalysis(BaseModel):
    """Result of analyzing a natural language query.
    Contains extracted structured information like temporal constraints."""
    temporal_constraint: TemporalConstraint | None = Field(
        default=None, description="Extracted temporal constraint, if any")
# TemporalConstraint is just start_date + end_date, two datetimes.
# No intent field, no entity list, no rewritten query.

Two implementations exist, neither being the configured business LLM:

ImplementationHowCost
DateparserQueryAnalyzer (default)pure library + rules: try period extraction (“last week/year”) first, then dateparser.search_dates, score every match and keep the strongest~10–50ms, no model
TransformerQueryAnalyzer (opt-in)a small local model google/flan-t5-small (~80M); rules first, few-shot generation only for unusual patternssmall local model

💡 Why “score” the date matches? (issue #2768)

dateparser over-matches: short common words that happen to be weekday/month abbreviations in some language (“we”/“me”/“did” → a weekday, “do” → Sunday) come back as bogus dates. If such a false positive appears before the real date in the query, taking the first match silently produces a wrong temporal window — worse than none. So instead of a blacklist, each match is scored by the date signal it actually carries: a digit +100, a month/relative word +50, a weekday +30, a period word +20; a bare token scores 0 and is rejected.

Query analysis runs before any database work; its output decides “whether to run the temporal path at all”. Any dateparser exception is swallowed into “no constraint” — a parser bug must never bring down the whole retrieval.

4. The real shape of “four-way parallel”

The module bills itself as “4-way parallel search”, but the concrete orchestration is batched + selectively parallel, not four independent concurrent tasks:

flowchart TB A["1 temporal extraction (CPU, no DB)"] --> B B["2 semantic + BM25: fused into one SQL
(same connection, sequential)"] B --> C["3 temporal retrieval: a second query on the same connection
(only if a constraint exists)"] B --> D["4 graph retrieval: one task per fact_type
asyncio.gather, truly concurrent"] C --> D D --> E["aggregate per fact_type"]
Fig 6-2: the only true concurrency is the graph step. Semantic and BM25 are interleaved arms of one SQL statement, so they execute “together”; temporal reuses the same connection.

💡 Why don't semantic and BM25 each get a connection?

Two reasons: (1) asyncpg forbids concurrent queries on one connection; (2) making semantic and BM25 interleaved UNION ALL arms of one SQL gets both in a single round trip — a deliberate optimization (comment: “reduces connection usage from 2 to 1”). Temporal reuses the same connection for the same reason. Only graph retrieval (one independent connection per fact_type) uses asyncio.gather for real concurrency, and it depends on the seeds the semantic phase produced (ch07), so it can only run after semantic.

What happens when one path fails

  • Graph: asyncio.wait_for timeout → degrade to “semantic + causal only” (drop the expensive entity self-join). No seeds → that fact_type returns empty (graph just contributes nothing).
  • BM25 (Oracle): full-text index not synced (DRG-10599 etc.) → the whole query is rebuilt as semantic-only.
  • Temporal: no constraint → the whole path is skipped; no pool rows → {ft: []}; Oracle lacks unnest → spreading is skipped but entry points still return.
  • Connection-level: connection errors retry 3× with exponential backoff; but a client-disconnect cancellation is never retried — it's re-raised.

⚠️ asyncio.gather has no return_exceptions

The graph retrieval's asyncio.gather is called without return_exceptions=True. So an unexpected exception in one graph task propagates and fails the whole recall (caught upstream by the retry/500 logic), rather than being silently swallowed. In other words: at the gather layer, a failing path is not “quietly dropped” — usually good (no silence), but it also means one path's surprise crash drags down the entire retrieval.

5. Key data structures

The four paths' unified carrier is RetrievalResult (search/types.py): it carries the memory payload (id/text/fact_type/time/tags/proof_count/…) plus several per-source score slots of which only one is set per source:

FieldSet by
similaritysemantic path
bm25_scorekeyword path
activationgraph path (the summed multi-signal score)
temporal_score / temporal_proximitytemporal path

Above that sit aggregates: SemanticBm25Result (per-fact_type semantic/bm25/graph seeds), ParallelRetrievalResult (the four lists + per-path timings + temporal constraint), MultiFactTypeRetrievalResult (the per-fact_type dict + aggregate timings). The post-fusion MergedCandidate and post-rerank ScoredResult are in ch08.

✅ Cancellation is cooperative

After a client disconnects, the engine checks request_context.raise_if_cancelled() at stage boundaries. So a retrieval can still be “mid-query” when the client leaves — cancellation isn't a hard kill; it takes effect at the next checkpoint. The most expensive cross-encoder stage checks once specifically before it runs (ch08).

Summary

  • Recall = four complementary paths (semantic/BM25/graph/temporal) → fusion → rerank → trim.
  • Query analysis only extracts a temporal constraint (dateparser + scoring against false positives, or a small local T5) — not an LLM intent classifier.
  • Real parallelism: semantic+BM25 one SQL, temporal one SQL, graph per fact_type via gather; connection budget 4.
  • Each path has a degradation on failure; gather does not swallow exceptions.
