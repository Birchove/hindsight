Part 1 · Understanding the System

01 · The Big Picture & Core Concepts

Before reading a single line of code, build three things: what problem the system solves, its core mental model, and its code layering and repo layout. All three are referenced again and again in every later chapter.

Chapter takeaways

  • Hindsight is not “stuff the conversation history into a vector store” — it processes text into an atomic fact network (facts + entities + three edge types), then retrieves and reasons over it.
  • Memory has three tiers: world facts / experience facts / mental models (observations); the first two are written by Retain, the third is produced by background consolidation.
  • There are only three operations: Retain (write), Recall (read), Reflect (reason).
  • The code is in three layers: API adapter → Engine facade → pipeline packages; never look for things across layers, and never read the two enormous files top to bottom.
  • Almost all the complexity in the course traces back to three engineering trade-offs — learn them now.

1. Starting from “an agent needs memory”

Large language models are stateless: each call only sees the context window you pass in. To make an agent “remember” a user or “learn” from experience across sessions, the two most naive approaches are:

  • Plain RAG: chunk the raw text → vectorize → at query time do similarity search and stuff the most similar chunks back into the prompt.
  • Knowledge graph (KG): extract information into an entity–relation graph and traverse it at query time.

Both have clear gaps. Plain RAG retrieves “which chunk looks like this sentence”, but what an agent really wants is “what did I learn, who is this about, when did it happen, how did my belief change later” — those signals are scattered and implicit in raw chunks, and similarity search misses “time”, “causality”, and “different phrasings of the same entity”. A KG has good structure but is expensive to build and hard to maintain, and used alone it loses the fine semantics in the text.

📖 Hindsight's trade-off

Combine the strengths of both and add a layer of “learning”: at write time, use an LLM to extract text into atomic facts and build structure (like a KG); at retrieval time, run multiple arms in parallel — vector + keyword + graph + temporal (stronger than RAG); and afterwards consolidate scattered facts into higher-level observations (a “learning” ability RAG/KG don't have). The project calls this “biomimetic” memory: like a person, it has knowledge of the world, personal experience, and the ability to reflect and summarize.

One sentence to remember the whole design intent:

💡 The narrative thread of the course

Hindsight does not “store the raw text and embed it” — it turns text into an atomic fact network that is retrievable, linkable, and consolidable. Retain (write) builds the network; Recall (read) finds the relevant nodes efficiently; Reflect reasons on top of the nodes; Consolidation distills nodes into higher-level “observations”. Every piece of complexity that follows is in service of making this network “correct to write, findable, and able to learn”.

2. The core mental model: what memory looks like

Hindsight organizes memory into three tiers — the higher you go, the more abstract and the closer to “knowledge”:

Fig 1-1: the three tiers of memory. The bottom layer is atomic facts, the middle is structure (entities and edges), the top is the consolidated observations. Consolidation is the bottom-up “learning”.
  • ① Atomic facts: a single self-standing assertion, of two kinds — world fact (objective knowledge about the world, e.g. “Alice is an engineer at Google”) and experience fact (the agent's own experience, e.g. “last time I deployed I forgot to run migrations and it broke”). In the database both are one row of the memory_units table, distinguished by fact_type. The fact is the system's unified semantic primitive — a point that keeps recurring.
  • ② Entities and edges: the entities each fact mentions (people, places, organizations, even abstract concepts like “friendship” or “career growth”) are extracted and normalized — “Google”, “google inc”, “Alphabet” point at one canonical entity. Facts also get three edge types between them: temporal (close in time), semantic (close in vector space), causal (this fact was caused by that one). These edges are the material the graph retriever works on.
  • ③ Observations / mental models: higher-level judgments reflected and synthesized out of scattered facts, e.g. “the user prefers functional programming”. An observation is itself stored as a special kind of fact (fact_type='observation'), carrying “how many facts support it” (proof_count) and “which facts it was synthesized from” (source_memory_ids).

⚠️ Get two easily-confused terms straight first

In the code, observation and mental model are two different things — the source comments stress this explicitly:
· An observation is synthesized bottom-up, automatically from raw facts by the consolidation engine, and lives in the memory_units table (fact_type='observation').
· A mental model is a user-defined “topic I want tracked long-term”, stored in the separate mental_models table — essentially “a pinned reflect result”, refreshed on demand.
In casual talk they get mixed up, but reading the code you must keep them apart. Chapters 09 and 10 expand on this.

3. The three operations

The system exposes only three verbs. Line them up against the memory tiers above:

OperationWhat it doesR/WMemory tiers it touches
RetainHands the input to an LLM, extracts facts/time/entities/relations, normalizes, storeswriteProduces ① ②; plants hooks for ③ (observation_scopes)
RecallRuns semantic / keyword / graph / temporal retrieval in parallel, fuses + reranks + trims by tokenreadConsumes ① ② ③ (an observation can be retrieved like any fact)
ReflectRuns a tool-using agent loop, retrieves on demand, produces a grounded “disposition-aware” answerread (no write)Consumes ③ (mental model / observation) + ① (raw-fact fallback)

There is also a background process not among the three verbs but running throughout: Consolidation. It runs asynchronously after Retain and synthesizes/updates new facts into observations. The reason it isn't folded into Retain is that Retain commits in streamed chunks, so mid-flight there is no “complete set of facts” to synthesize over — that “why” is chapter 09.

✅ An analogy to build intuition

Picture Hindsight as a diligent assistant's notebook: Retain is “listen to you, then write the key points down one by one, noting who, when, and because of what” (not a voice-recorder that stores the raw audio); Recall is “when you ask a question, he flips through his notes four ways at once — keyword index, similar topics, who-knows-whom, timeline — and hands you the most relevant lines”; Reflect is “when you ask ‘what do you know about me’, he reviews the impressions he's summarized and, combined with the raw notes, answers carefully”; Consolidation is “every night he tidies the day's scattered notes into a few long-term impressions”.

6. bank & disposition: isolation and “personality”

Two business concepts that run through the whole course:

  • bank (memory bank): a fully isolated memory store — “one brain for a given user/agent”. Each request targets a single bank; banks never leak data into each other (the database enforces this with schema / bank_id double isolation). Cross-bank queries are the client's responsibility — the system doesn't provide them.
  • disposition: each bank can set three integer traits 1–5 — skepticism, literalism, empathy. It only affects the tone and judgment of Reflect and does not affect Recall at all. Implementation-wise it is just serialized into one line of the system prompt, skepticism=3, literalism=3, empathy=3, and how exactly it shapes the answer is left to the model to interpret (chapter 10 shows this is a very “soft” mechanism, in sharp contrast to the hard-constraint directives).

7. The three engineering trade-offs that run through the course

Finally, and most importantly for this chapter. The places where the system looks “over-engineered” almost all trace back to three trade-offs. Learn them by heart — later, whenever you hit a baffling design, you'll likely be able to match it to one of these:

Trade-offPlainly putEngineering response (later chapters)
LLM is slow & expensive ↔ writes must be fast & recoverable Extracting facts calls an LLM — slow and costly; but the user can't wait, and a failure mustn't throw the whole document away. streaming mini-batch commits, delta retains (re-extract only the changed parts), async enqueue + idempotency (ch 03, 04)
Retrieval needs precomputed structure ↔ computing that structure can fail Graph/temporal retrieval depends on edges built at write time; but building edges (ANN, entity resolution) is a slow operation that can fail. Phase1 read-outside / Phase2 short atomic transaction / Phase3 post-commit edge top-up (ch 05)
Concurrent multi-tenancy ↔ per-document consistency Many requests write the same bank, even the same document, at once; but they mustn't produce duplicates or overwrite each other. content_hash dedup, SELECT … FOR UPDATE row locks, sequential slicing per document (ch 03)

✅ How to use these three trade-offs

Later, whenever you see an issue number like #1875, #2662, #1888 in a source comment, it's basically one of these trade-offs having surfaced in a real incident. Reading those comments explains “why it's written this way” faster than reading the function body. This course cites these issue numbers where relevant.

Summary

  • Hindsight's core proposition: process text into an atomic fact network (facts + normalized entities + temporal/semantic/causal edges), rather than storing raw chunks.
  • Three memory tiers: world/experience facts → entities and edges → consolidated observations; plus user-defined mental models (don't confuse the two).
  • Three operations Retain / Recall / Reflect, plus a background Consolidation.
  • Three code layers API → Engine facade → pipeline packages; read per layer, jump by function, stay away from reading the two long files top to bottom.
  • The three trade-offs (slow/costly ↔ fast/recoverable, precompute ↔ can-fail, concurrency ↔ consistency) are the key to understanding all the complexity.
