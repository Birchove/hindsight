Part 1 · Understanding the System

01 · Big Picture & Core Concepts

Before reading a single line of code, build three things: the problem this system solves, its core mental model, and its code layering and repo layout. All three are referenced again and again in every later chapter.

Chapter takeaways

  • Hindsight is not “stuff the conversation history into a vector store” — it processes text into an atomic fact network (facts + entities + three edge types), then retrieves and reasons over it.
  • Memory has three kinds: world facts / experience facts / mental models (observations); the first two are written by Retain, the third is produced by background consolidation.
  • There are only three operations: Retain (write), Recall (read), Reflect (reason).
  • The code has three layers: API adapter → Engine facade → pipeline packages. When reading, never look across layers for a thing, and never read the two huge files top to bottom.
  • Nearly all the complexity traces to three engineering trade-offs — learn them first.

1. Start from “agents need memory”

A large language model is stateless: on each call it sees only the context window you pass in. To make an agent “remember” a user or “learn” from experience across sessions, the two naive approaches are:

  • Naive RAG: chunk the raw text → vectorize → at query time do similarity search and stuff the closest chunks back into the prompt.
  • Knowledge graph (KG): extract information into an entity–relationship graph and traverse it at query time.

Both have real weaknesses. Naive RAG retrieves “which chunk resembles this sentence”, but what an agent actually wants is “what did I learn, who is this about, when did it happen, how did my belief change later” — and in a raw chunk those signals are scattered and implicit; similarity search misses “time”, “causality”, and “different phrasings of the same entity”. A knowledge graph has good structure but is expensive to build and hard to maintain, and used alone it loses the subtle semantics that live in the text.

📖 Hindsight's trade-off

Combine the strengths of both and add a layer of “learning”: on write, use an LLM to extract atomic facts and build structure (like a KG); on read, retrieve on several paths at once — vector + keyword + graph + time (stronger than RAG); and afterwards consolidate scattered facts into higher-level observations (a “learning” capability neither RAG nor a KG has). The project calls this biomimetic memory: like a person, it has knowledge about the world, personal experience, and the ability to reflect and summarize.

Hold the whole system's design intent in one sentence:

💡 The narrative through-line

Hindsight does not “store the text then embed it” — it turns text into an atomic fact network that is retrievable, linkable, and consolidatable. Retain builds that network, Recall finds the relevant nodes efficiently, Reflect reasons on top of them, and Consolidation distills nodes into higher-level observations. Every bit of complexity that follows serves that network's three needs: written correctly, found, and able to learn.

2. Core mental model: what a memory looks like

Hindsight organizes memory in three layers, each more abstract — closer to “knowledge” — than the last:

Fig 1-1: the three layers of memory. The bottom is atomic facts, the middle is structure (entities and edges), the top is consolidated observations. Consolidation is the bottom-up “learning”.
  • ① Atomic facts: a single free-standing assertion, in two flavors — world fact (objective knowledge about the world, e.g. “Alice is an engineer at Google”) and experience fact (the agent's own experience, e.g. “last time I deployed I forgot to run migrations and it broke”). In the database both are rows of the memory_units table, distinguished by fact_type. The fact is the system's uniform semantic primitive — this matters a lot and keeps coming up.
  • ② Entities and edges: the entities each fact mentions (people, places, orgs, even abstract concepts like “friendship” or “career growth”) are extracted and normalized — “Google”, “google inc”, “Alphabet” point to one canonical entity. Facts are also joined by three edge types: temporal (close in time), semantic (close in vector space), causal (this fact was caused by that one). These edges are the raw material for graph retrieval.
  • ③ Observations / mental models: higher-level judgments reflected and synthesized out of scattered facts, e.g. “the user prefers functional programming”. An observation is itself stored as a special kind of fact (fact_type='observation'), carrying “how many facts support it” (proof_count) and “which facts it was synthesized from” (source_memory_ids).

⚠️ Clear up the two most-confused terms first

In the code, observation and mental model are two different things — the source comments say so explicitly:
· observation = synthesized bottom-up, automatically from raw facts by the consolidation engine; lives in memory_units as fact_type='observation'.
· mental model = a user-defined “topic I want tracked long-term”; lives in a separate mental_models table; essentially a “pinned reflect result”, refreshed on demand.
In casual speech the two get mixed; when reading code you must keep them apart. Chapters 09 and 10 unpack this.

3. The three operations

The system exposes only three verbs to its users. Map them onto the layers above:

OperationWhat it doesR/WMemory layers it touches
RetainHands the input text to an LLM, extracts facts/time/entities/relations, normalizes, and persistswriteproduces layers ①②; plants the hooks for ③ (observation_scopes)
RecallRuns semantic / keyword / graph / temporal retrieval in parallel, then fuses + reranks + trims by token budgetreadconsumes ①② (an observation can also be retrieved like any fact)
ReflectRuns a tool-using agent loop that retrieves on demand and produces a grounded, disposition-aware answerread (no write)consumes ③ (mental model / observation) + ① (raw-fact fallback)

There is also one process that is not among the three verbs but runs throughout: Consolidation. It runs asynchronously after Retain and synthesizes/updates new facts into observations. The reason it isn't folded into Retain is that Retain commits in streamed chunks, so mid-way through there is no “complete set of facts for the document” to synthesize from — that “why” is chapter 09.

6. bank and disposition: isolation and personality

Two business concepts that run through the whole course:

  • bank (memory bank): a fully isolated memory store — “one brain for a given user/agent”. Each request targets a single bank; banks never leak data into each other (isolated at the database level by schema / bank_id). Cross-bank queries are the client's responsibility — the system does not provide them.
  • disposition: each bank can set three integer 1–5 traits — skepticism, literalism, empathy. It affects only the tone and judgment of Reflect, never Recall. In implementation it is just serialized into the system prompt as one line, skepticism=3, literalism=3, empathy=3; how it shapes the answer is left to the model to interpret (chapter 10 shows this is a deliberately “soft” mechanism, in sharp contrast to the hard constraint that directives provide).

7. The three engineering trade-offs that run through the course

Finally — the most important section of this chapter. The places where this system looks “overly complex” almost all trace to three trade-offs. Learn them, and later, every puzzling design will probably click into place:

Trade-offPlainlyEngineering response (later chapters)
LLM is slow & expensive ↔ writes must be fast & recoverable Extracting facts calls an LLM — slow and costly; but the user can't wait, and a failure must not throw the whole document away. streaming mini-batches, delta retains (re-extract only what changed), async enqueue + idempotency (ch03, 04)
Retrieval needs precomputed structure ↔ computing that structure can fail Graph/temporal retrieval depend on edges built at write time; but building edges (ANN, entity resolution) is slow and can fail. Phase1 read outside / Phase2 short atomic transaction / Phase3 backfill after commit (ch05)
Concurrent multi-tenancy ↔ per-document consistency Many requests write the same bank — even the same document — at once; but you can't produce duplicates or clobber each other. content_hash dedup, SELECT … FOR UPDATE row locks, sequential slicing within a document (ch03)

✅ How to use these three trade-offs

Later, whenever you see an issue number like #1875, #2662, #1888 in a source comment, it is almost always one of these trade-offs having surfaced in a real incident. Reading those comments explains “why it's written this way” faster than reading the function body. This course cites those issue numbers where relevant.

Summary

  • Hindsight's core proposition: process text into an atomic fact network (facts + normalized entities + temporal/semantic/causal edges), not stored raw chunks.
  • Three memory layers: world/experience facts → entities and edges → consolidated observations; plus user-defined mental models (don't conflate them).
  • Three operations Retain / Recall / Reflect, plus a background Consolidation.
  • Three code layers API → Engine facade → pipeline packages; read by layer, jump by function, avoid reading the two huge files in full.
  • The three trade-offs (slow/costly ↔ fast/recoverable, precompute ↔ can-fail, concurrency ↔ consistency) are the key to all the complexity.
