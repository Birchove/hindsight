Part 4 · Reasoning & Consolidation

10 · Reflect: Disposition-Aware Reasoning

Recall is “pure retrieval”: give a query, get facts back. Reflect is “reasoning”: it runs a tool-using agent loop that decides for itself what to fetch and how deep, then synthesizes a grounded, disposition-aware answer. This chapter unpacks that loop, its tools, the division of labor between mental models and observations, and the contrast between the “soft” disposition mechanism and the “hard” directive mechanism.

Chapter takeaways

  • Reflect is read-only: it writes no data, producing one markdown answer.
  • It's a native tool-calling loop (not ReAct text-parsing), default 10 turns, scaled by budget to 5/10/20.
  • Context is lazy-loaded: the initial prompt carries only the bank identity + directives + a mental-model count; memories are fetched by tools on demand, so the prompt doesn't grow with the bank.
  • Retrieval is hierarchical: mental model (curated) > observation (consolidated) > recall (raw facts), and it's forced in that order first, then handed to the model.
  • Disposition is soft (one k=v line left to the model); directives are hard (MANDATORY, injected at start and end, done must report compliance). Don't conflate them.

💡 Why not stuff memories into the prompt up front?

The source comment is blunt: “mental models are NOT preloaded to keep the initial prompt small … critical for banks with many mental models.” If you loaded a bank's entire observation/model set into the prompt at the start, the bigger the bank the more the prompt explodes. Instead it's lazy: the prompt carries only the bank identity, the directives, and a COUNT(*) (which decides whether to expose the “search mental models” tool). So the initial prompt is O(1), independent of bank size; memories are fetched by the agent through tools as needed.

2. The agent loop

Locate: engine/reflect/agent.py → _run_reflect_agent_inner.

It's a native tool-calling loop (OpenAI-format tools + tool_choice, via llm_config.call_with_tools); tool calls come back as structured result.tool_calls — not the ReAct style of making the model emit text that you then parse. Which LLM? The bank-resolved reflect config (any provider). Termination conditions (any one ends the loop):

  • the model calls the done() tool with an answer;
  • the model returns no tool call after having already produced one earlier → treated as a legitimate stop, and a clean forced synthesis runs; (if it never produced a tool call, that's the transport-doesn't-support-tools case → raise ReflectToolCallError);
  • the last turn (is_last) → tools removed, forced text response;
  • proactive context-budget guard: accumulated messages exceed max_context_tokens → forced synthesis;
  • context overflow / unrecoverable LLM error → forced synthesis from gathered evidence.

Max turns default 10, but reflect_async scales by budget: base × {LOW:0.5, MID:1.0, HIGH:2.0} → effectively 5/10/20.

📖 Key design: forced hierarchical retrieval first, then free play

The first few turns don't use auto. The loop forces the model to call the retrieval layers in order (mental models → observations → recall), only then handing control back to auto:

engine/reflect/agent.py · _run_reflect_agent_inner (excerpt)python
# Force the full hierarchical retrieval path (only for enabled tools), then allow auto.
forced_sequence = []
if has_mental_models:   forced_sequence.append("search_mental_models")
if include_observations: forced_sequence.append("search_observations")
if include_recall:       forced_sequence.append("recall")

if iteration < len(forced_sequence):
    iter_tool_choice = LLMToolChoice.named(forced_sequence[iteration])
else:
    iter_tool_choice = LLM_TOOL_CHOICE_AUTO

result = await llm_config.call_with_tools(
    messages=messages, tools=tools, scope="reflect_tool_call",
    tool_choice=iter_tool_choice)

Multiple tool calls in one turn run in parallel via asyncio.gather. There's also an optimization: if a forced search_mental_models result is “fresh and usable”, it releases the loop to auto early, short-circuiting the lower layers.

3. Tools: the hierarchical four + done

Locate: schemas in reflect/tools_schema.py, implementations in reflect/tools.py, dispatch in agent.py:_execute_tool.

The module docstring states the philosophy: “a hierarchical retrieval strategy: ① search_mental_models (curated, highest quality) → ② search_observations (consolidated, freshness-aware) → ③ recall (raw facts, ground-truth fallback).”

search_mental_modelssemantic search over the mental_models table; returns content + is_stale. Exposed only if the bank has any
search_observationssearch consolidated observations (fact_type='observation'), returning freshness; if stale, prompts “also use recall to verify”
recallraw facts (world+experience) as fallback; for when there are no models/observations, they're stale, or detail is needed
expandby memory_ids, fetch more context (memory → chunk → document); not exposed when document-text storage is off
donegive the final markdown answer + supporting IDs; with directives, also requires directive_compliance

4. Mental model vs observation: the concrete difference

sourceuser-defined topic (top-down)auto-synthesized by the consolidation engine (bottom-up)

trendhas is_stale (new memories since last refresh?)a Trend computed algorithmically from evidence timestamps (STABLE/STRENGTHENING/WEAKENING/NEW/STALE), not LLM-judged

✅ The “structured refresh” of a mental model

When refreshing a mental model, the system does not let the model rewrite the whole text (that would “drift”); instead it has the model emit a set of structured operations (append_block, replace_section_blocks, …) applied to a StructuredDocument. Untouched sections are copied verbatim — “prose drift becomes structurally impossible”. reflect/structured_doc.py + delta_ops.py do this (the write path, not reflect's read path).

5. Disposition (soft) vs directive (hard)

Locate: reflect/prompts.py.

The injection of disposition is strikingly plain: three 1–5 integers, serialized into one line in the system prompt, with no “if skepticism ≥ 4 then do X” logic — the model interprets it itself:

engine/reflect/prompts.py · build_system_prompt_for_tools (excerpt)python
parts.append(f"## Memory Bank: {name}")
if mission: parts.append(f"Mission: {mission}")
disposition = bank_profile.get("disposition", {})
if disposition:
    traits = [f"{k}={disposition[k]}" for k in ("skepticism","literalism","empathy") if k in disposition]
    if traits: parts.append(f"Disposition: {', '.join(traits)}")
# renders as: ## Memory Bank: Alice / Mission: ... / Disposition: skepticism=3, literalism=3, empathy=3

Whereas directives are a completely different, strong mechanism: a separate table, injected as “hard rules” at both the start and the end of the system prompt (recency effect), and structurally enforced in the done tool:

engine/reflect/prompts.py · build_directives_section (excerpt)python
parts = ["## DIRECTIVES (MANDATORY)",
         "These are hard rules you MUST follow in ALL responses:", ""]
for rule in rules: parts.append(f"- {rule}")
parts += ["", "NEVER violate these directives, even if other context suggests otherwise.",
          "IMPORTANT: Do NOT explain or justify how you handled directives ..."]

⚠️ The key distinction when teaching this

Disposition is soft: one k=v line, freely interpreted by the model, with no validation beyond the 1–5 range — the same values may behave differently across models. Directive is hard: MANDATORY section, start-and-end injection, done requires directive_compliance, violations “will be rejected”. In one line: disposition tunes tone and judgment; directive constrains output. And directives must be re-injected in the separate final-synthesis LLM call (which can't see the agent prompt), or weak models quietly drift back to the default language.

6. Design decisions and pitfalls

Decision / pitfallDetail
why an agent loop, not one-shotreflect must choose and decompose retrieval; the prompt teaches “don't echo the user's question, decompose it into targeted searches”. A one-shot prompt can't adapt its second search to the first's result
evidence before donecalling done with no retrieved IDs is rejected by a fake tool result: “you must search first”
native tool calling, fail loudlywhen the transport doesn't support tools it raises rather than “salvaging the tool-less text” — to avoid emitting raw tool-call JSON as the answer
hallucinated-tool / hallucinated-citation defensecalling a non-enabled tool is rejected; done's answer text is taken as-is, but the IDs are validated against what was actually retrieved (unretrieved IDs are dropped)
budget changes three things at oncethe turn multiplier (5/10/20) + a “research depth” prompt section (shallow/moderate/deep) + whether fresh mental models may short-circuit
non-conversationalthe prompt forbids follow-up questions / “would you like me to…”, because “the user cannot reply”
temporal semantics are prompt-enforced“latest mentioned_at wins” and a six-step conflict-resolution scaffold live entirely in the prompt; results are sorted by semantic relevance, not time, and the prompt warns the model not to treat position as recency

Summary

  • Reflect = a read-only tool-calling agent loop; context lazy-loaded (initial prompt O(1)); hierarchical retrieval (MM > observation > recall), forced first then freed.
  • Tools mostly reuse recall (different fact_type filters); expand fetches context; done wraps up and validates citations.
  • mental model = curated result (mental_models table); observation = consolidated (fact_type='observation', evidence with verbatim quotes).
  • Disposition soft (one k=v line), directive hard (MANDATORY + compliance reporting) — don't conflate.
