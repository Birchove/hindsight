Part 6 · Ecosystem Overview

12 · The Ecosystem at a Glance

The first 11 chapters all stayed in hindsight-api-slim/. This chapter steps out to take in the whole monorepo: how the system is packaged, deployed, and integrated into various frameworks, what the console and CLI look like, and how benchmarks run. This chapter doesn't read code line by line — it builds the map of “what this project looks like as a product”, and gives an account of the “cover the rest by comparison” you asked for.

Chapter takeaways

  • One engine, three delivery shapes: standalone server (Docker), Python embedded (hindsight-all, bundles pg0), npm embedded (hindsight-all-npm).
  • Clients in 4 languages (Python/TS/Rust/Go), all generated from OpenAPI; the CLI is Rust; plus a “two lines of code” LLM Wrapper.
  • 49 framework integrations are mostly variants of one pattern: wrap retain/recall/reflect into the framework's “memory/tool” interface.
  • The control plane is a Next.js admin UI that proxies the dataplane; adding an API parameter means changing both sides.
  • Storage defaults to embedded pg0, also supports external PostgreSQL and Oracle 23ai (feature parity); migrations dispatch by dialect.

1. Three “run it” shapes

The engine is one, but the delivery shapes are three, for different scenarios:

📖 pg0: the embedded Postgres that makes “zero-dependency” possible

Hindsight can't live without PostgreSQL + pgvector. To avoid making users install a database first, it embeds PostgreSQL as pg0 (data in ~/.pg0). So a single docker run, or pip install hindsight-all, brings the database up automatically. That's why files like pg0.py and daemon.py exist. The “one schema per tenant” multi-tenancy from chapter 02 still holds on top of this.

The README's “simplest integration” is actually the LLM Wrapper: swap your existing LLM client for Hindsight's wrapper, and afterwards every LLM call automatically stores and retrieves memory — reportedly two lines of code. For finer control over how and when the agent stores and recalls, use the SDK/HTTP to call the three operations directly.

2. Clients, SDKs, and the CLI

  • SDKs: hindsight-clients/ holds Python, TypeScript, Rust, Go. They are generated — after changing the API, run ./scripts/generate-openapi.sh to regenerate the OpenAPI spec, then ./scripts/generate-clients.sh to regenerate all SDKs. So don't hand-edit the generated clients.
  • CLI: hindsight-cli/ is written in Rust (self-described as “A beautiful CLI for Hindsight”), using progenitor to generate the API client from OpenAPI.
  • Embedded CLI: hindsight-embed/ offers “local memory operations without a server”.

✅ A discipline that runs through the whole repo: change the API first, then regenerate

The API is the single source of truth. After changing a dataplane endpoint: ① regenerate the OpenAPI spec (CI verifies it) → ② regenerate the SDKs → ③ update the control plane's proxy routes and types in sync. This chain explains why so much in the repo is “generated” — to keep four languages + the CLI + the UI forever aligned with the API.

3. The integration ecosystem: 49 of them, one pattern

hindsight-integrations/ holds 49 framework integrations: LangGraph, CrewAI, Pydantic AI, AutoGen/AG2, Claude Code, Cursor, Cline, LlamaIndex, Haystack, n8n, Dify… The number is intimidating, but the vast majority are variants of one pattern:

(pre/post hook, Tool, Memory class)"] end subgraph adapter["Hindsight integration (a thin adapter layer)"] A["translate the framework's messages/context
into retain input"] B["translate the framework's 'need memory' moment
into recall/reflect calls"] end subgraph hs["Hindsight server"] API["retain / recall / reflect"] end HOOK --> A --> API HOOK --> B --> API
Fig 12-1: the generic integration shape. Frameworks differ, but the adapter layer does something highly isomorphic: call retain at the right moment, call recall/reflect when context is needed.

📖 How to read the 49 (without reading all 49)

Pick one integration for a framework you know and read it through (if you've used LangGraph read langgraph/, if Claude Code read claude-code/), and understand “at which hook, what, translated into which operation”. The rest you can skim the README — the differences are mostly “what the framework's mount point is called and what its message structure looks like”, not anything on the Hindsight side.

The repo has a hard checklist for “adding a new integration” (from CLAUDE.md, which exactly spells out what a “complete integration” contains):

  1. Tests are required — must simulate/exercise the external system (mock the framework's interfaces, verify the integration actually calls Hindsight correctly); pure helper unit tests don't count.
  2. CI job — add a test job in .github/workflows/test.yml following the existing pattern (build, install deps, uv run pytest tests -v), and wire it into detect-changes so it only runs when its files change.
  3. Release — add the integration name to the VALID_INTEGRATIONS array in scripts/release-integration.sh.
  4. Follow code standards — Python style, type safety, no raw dicts for structured data, no multi-item tuple returns.

4. The control plane

hindsight-control-plane/ is a Next.js admin UI (pages include dashboard / banks / login, etc.), by default on port 9999. It stores no data itself — it proxies calls to the dataplane API. Its API routes map almost one-to-one to the dataplane:

Control-plane route (src/app/api/)Maps to
recall / reflect / memories (retain)The three operations
banks / profile / statsBank management and statistics
documents / chunks / entities / graphMemory content browsing and visualization
operations / extract / files / health / versionOps and tooling

⚠️ Adding an API parameter? Sync both sides

CLAUDE.md stresses: when adding/changing a parameter on the dataplane, change three places on the control plane too — ① the route handler (destructure the parameter from the body, pass it to the SDK call), ② the client types (the recall()/reflect()/retain() types in src/lib/api.ts), ③ the UI components that need it. Miss one and the new parameter is unusable from the UI.

5. Storage & deployment

  • Embedded pg0 by default, zero dependency; for production swap to external PostgreSQL (docker/docker-compose).
  • Oracle 23ai is also supported, with “feature parity”. This explains the heavy dialect dispatch in the code: each migration picks _pg_upgrade or _oracle_upgrade through run_for_dialect(pg=..., oracle=...) (the “Oracle has no unnest, observations use a junction table” differences from chapter 02 come from this). A pytest lint (test_migration_shape.py) fails CI if a migration omits the dispatcher.
  • Pluggable vector backends (pgvector/diskann/vchord/scann, ch 02) and pluggable full-text backends (native tsvector / pg_search / pgroonga / vchord, ch 07).
  • Orchestration: helm/ (K8s), monitoring/; the config template is .env.example (the setup script copies it to .env).

7. The config system, recapped

Bringing all the config knowledge together (see chapter 11 for detail): config is hierarchical — global (env) → tenant (via extension) → bank (database). Fields come in two flavors:

  • Configurable (hierarchical): overridable by tenant/bank — LLM behavioral settings, retain mode, chunk size, mission, disposition, recall budgets, etc.
  • Static (server-level): database URL, port, global concurrency limits, and (note) the LLM provider/model/key.

The standard process for adding a new config field (from CLAUDE.md): in config.py add the ENV_*/DEFAULT_*/dataclass field; if overridable, add it to _CONFIGURABLE_FIELDS; in the engine resolve per bank with ConfigResolver.get_bank_config; sync the docs and .env.example; after editing .env.example also copy it into hindsight-embed/ (a sync test watches this).

Summary

  • One engine, three deliveries: Docker server / Python embedded / npm embedded; pg0 makes zero-dependency possible.
  • 4 SDKs + the Rust CLI are all generated from OpenAPI; changing the API means the “regenerate + sync control plane” chain.
  • 49 integrations = 49 variants of one pattern; read one through, skim the rest; adding an integration has a hard checklist.
  • The control plane is a proxy-type Next.js UI; storage defaults to pg0, swappable to PG/Oracle (dialect dispatch).
  • Benchmarks split into accuracy (LongMemEval/LoCoMo) and performance; config is hierarchical with configurable vs static fields.
