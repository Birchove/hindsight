12 · The Ecosystem

The first 11 chapters lived inside hindsight-api-slim/. This chapter steps out and surveys the whole monorepo: how the system is packaged, deployed, and integrated into many frameworks, what the console and CLI look like, and how the benchmarks run. This chapter doesn't read code line by line — it builds the map of “what the project looks like as a product”, and gives the “cover the rest by comparison” treatment you asked for.

Chapter takeaways

  • One engine, three delivery forms: standalone server (Docker), Python-embedded (hindsight-all, ships pg0), npm-embedded (hindsight-all-npm).
  • Clients in 4 languages (Python/TS/Rust/Go), all generated from OpenAPI; the CLI is Rust; plus the “two-line” LLM Wrapper.
  • 49 framework integrations are mostly variants of one pattern: wrap retain/recall/reflect into the framework's “memory/tool” hook.
  • The control plane is a Next.js admin UI that proxies the dataplane; adding an API parameter means changing both sides.
  • Storage defaults to embedded pg0, also supports external PostgreSQL and Oracle 23ai (feature parity); migrations dispatch by dialect.

📖 pg0: the embedded Postgres that makes “zero dependencies” possible

Hindsight can't live without PostgreSQL + pgvector. To avoid making users install a database first, it embeds PostgreSQL as pg0 (data in ~/.pg0). So a single docker run, or pip install hindsight-all, brings the database up automatically. That's why files like pg0.py and daemon.py exist. The per-tenant-schema multi-tenancy from ch02 still holds on top of it.

The README's “simplest integration” is actually the LLM Wrapper: swap your existing LLM client for Hindsight's wrapper, and afterwards every LLM call automatically stores and retrieves memory — advertised as two lines of code. Reach for the SDK/HTTP three operations directly only when you need finer control.

2. Clients, SDKs, and the CLI

  • SDKs: hindsight-clients/ has Python, TypeScript, Rust, and Go. They are generated — after changing the API, run ./scripts/generate-openapi.sh to regenerate the OpenAPI spec, then ./scripts/generate-clients.sh to regenerate all SDKs. So don't hand-edit the generated clients.
  • CLI: hindsight-cli/ is written in Rust (described as “A beautiful CLI for Hindsight”), using progenitor to generate its API client from OpenAPI.
  • Embedded CLI: hindsight-embed/ provides “local memory operations without a server”.

✅ A discipline that runs through the whole repo: change the API, then regenerate

The API is the single source of truth. After changing a dataplane endpoint: ① regenerate the OpenAPI spec (CI checks it) → ② regenerate the SDKs → ③ update the control plane's proxy routes and types. This chain explains why so much in the repo is “generated” — it keeps the four languages + CLI + UI aligned with the API forever.

3. The integration ecosystem: 49 of them, one pattern

hindsight-integrations/ holds 49 framework integrations: LangGraph, CrewAI, Pydantic AI, AutoGen/AG2, Claude Code, Cursor, Cline, LlamaIndex, Haystack, n8n, Dify… a staggering number — but the vast majority are variants of one pattern:

Fig 12-1: the generic shape of an integration. Frameworks differ, but the adapter does a highly isomorphic job: call retain at the right moment, call recall/reflect when context is needed.

📖 How to read the 49 (you don't read them all)

Pick one integration for a framework you know and read it through (used LangGraph? read langgraph/; used Claude Code? read claude-code/), understanding “at which hook does it translate what into which operation”. Then skim the rest's READMEs — the differences are mainly “what the framework's hook is called and what its message structure looks like”, not anything on the Hindsight side.

The repo has a hard checklist for “adding an integration” (from CLAUDE.md — and it neatly defines what a “complete integration” includes):

  1. Tests are required — they must simulate/exercise the external system (mock the framework's interfaces and verify the integration actually calls Hindsight correctly); pure helper unit tests don't count.
  2. A CI job — add a test job in .github/workflows/test.yml following the existing pattern (build, install deps, uv run pytest tests -v), and wire it into detect-changes so it only runs when its files change.
  3. Release — add the integration name to VALID_INTEGRATIONS in scripts/release-integration.sh.
  4. Follow the code standards — Python style, type safety, no raw dicts for structured data, no multi-item tuple returns.

4. The control plane

hindsight-control-plane/ is a Next.js admin UI (pages: dashboard / banks / login / …), by default on port 9999. It stores no data itself; it proxies calls to the dataplane API. Its API routes map almost one-to-one onto the dataplane:

control plane route (src/app/api/)Maps to
recall / reflect / memories (retain)the three operations
banks / profile / statsbank management and stats
documents / chunks / entities / graphbrowsing memory contents and visualization
operations / extract / files / health / versionops and tools

⚠️ Adding an API parameter? Sync both sides

CLAUDE.md stresses: when you add/change a dataplane parameter, the control plane needs three matching changes — ① the route handler (destructure the parameter from the body and pass it to the SDK call), ② the client types (the recall()/reflect()/retain() types in src/lib/api.ts), ③ any UI component that uses it. Miss one and the new parameter is unusable from the UI.

5. Storage and deployment

  • Embedded pg0 by default, zero dependencies; production can switch to external PostgreSQL (docker/docker-compose).
  • Oracle 23ai is also supported, with “feature parity”. This explains the heavy dialect dispatch in the code: every migration selects _pg_upgrade or _oracle_upgrade via run_for_dialect(pg=..., oracle=...) (the “Oracle has no unnest, observations use a junction table” differences from ch02 come from exactly this). A pytest lint (test_migration_shape.py) fails CI if a migration omits the dispatcher.
  • Vector backend pluggable (pgvector/diskann/vchord/scann, ch02), full-text backend pluggable (native tsvector / pg_search / pgroonga / vchord, ch07).
  • Orchestration: helm/ (K8s), monitoring/; the config template is .env.example (the setup script copies it to .env).

7. The config system, recapped

Bringing the config knowledge together (details in ch11): configuration is hierarchical — global (env) → tenant (via extension) → bank (database). Fields fall in two classes:

  • Configurable (hierarchical): overridable by tenant/bank — LLM behavioral settings, retain mode, chunk size, mission, disposition, recall budgets, etc.
  • Static (server-level): database URL, port, global concurrency limits, and (note) LLM provider/model/key.

The standard process for adding a config field (from CLAUDE.md): add ENV_*/DEFAULT_*/a dataclass field in config.py; if overridable, add it to _CONFIGURABLE_FIELDS; in the engine resolve per bank with ConfigResolver.get_bank_config; keep the docs and .env.example in sync; after editing .env.example, copy it into hindsight-embed/ too (a sync test watches this).

Summary

  • One engine, three deliveries: Docker server / Python-embedded / npm-embedded; pg0 makes zero-dependency possible.
  • 4 SDKs + a Rust CLI, all generated from OpenAPI; changing the API means the “regenerate + sync the control plane” chain.
  • 49 integrations = one pattern in 49 variants; read one thoroughly, skim the rest; a new integration has a hard checklist.
  • The control plane is a proxying Next.js UI; storage defaults to pg0, swappable to PG/Oracle (dialect dispatch).
  • Benchmarks split into accuracy (LongMemEval/LoCoMo) and performance; configuration is hierarchical, fields configurable vs static.
