Part 3 · Retrieval — Recall

08 · Fusion & Reranking

Each of the four arms hands back one ranked list. This chapter covers the “merge → rerank → trim” trio: use Reciprocal Rank Fusion (RRF) to combine the four incomparable rankings into one; use a cross-encoder to rerank the survivor set; then trim by token budget into the final answer. Two classic exam points live here: why RRF, and why “fuse first, then rerank”.

Chapter takeaways

  • RRF looks at rank only, not score: score(d) = Σ 1/(k+rank), k=60. No need to align the four score scales, and no weights to tune.
  • The cross-encoder is expensive, so RRF pre-filters to 300 first and only reranks that — the cost gate of the whole pipeline.
  • The rerank score is the primary signal, then multiplied by recency / temporal / proof boosts (each centered at 0.5 as a ×1.0 neutral), giving the final order.
  • Trimming is two passes: first cap the count by thinking_budget×2, then by max_tokens (tiktoken) stopping before the overflowing fact — never splitting a fact.

The pure algorithms are in search/fusion.py, search/reranking.py, search/recall_boost.py; but the orchestration (who goes before whom, prefiltering, trimming) is in memory_engine._search_with_retries. The pipeline at a glance:

2. RRF: Reciprocal Rank Fusion

Locate: search/fusion.py → reciprocal_rank_fusion(result_lists, k=60).

Formula: score(d) = Σ_lists 1/(k + rank(d)), k=60 (the classic Cormack/Clarke/Buettcher constant), ranks 1-based.

engine/search/fusion.py · reciprocal_rank_fusion (excerpt)python
rrf_scores[doc_id] += 1.0 / (k + rank)
source_ranks[doc_id][f"{source_name}_rank"] = rank

# The merged result keeps only the FIRST-seen arm's RetrievalResult,
# so each arm's raw score is recorded separately into ArmScores for downstream
# reporting / filtering.
if source_name == "semantic" and retrieval.similarity is not None:
    arm_scores[doc_id].semantic = retrieval.similarity
elif source_name == "bm25" and retrieval.bm25_score is not None:
    arm_scores[doc_id].keyword = retrieval.bm25_score

# Final order by RRF score descending; rrf_rank numbered from 1 in that order.
for rrf_rank, (doc_id, rrf_score) in enumerate(
    sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True), start=1):
    merged_results.append(MergedCandidate(
        retrieval=all_retrievals[doc_id], rrf_score=rrf_score,
        rrf_rank=rrf_rank, source_ranks=..., arm_scores=...))

💡 Why RRF rather than a weighted sum?

The four arms' raw scores are in completely incomparable units: cosine similarity in [0,1], BM25 with no upper bound, graph activation in [0,3], temporal proximity yet another scale. A weighted sum would first have to normalize them onto one scale and then tune weights. RRF uses rank only — “where did you place in your own arm” — so: no weights to tune and no scales to align, naturally robust to one score type being inflated. That's the so-called “parameter-free fusion”.

  • Dedup key is the document id; a fact appearing in several arms accumulates RRF score, but the merged result keeps only the first-seen arm's payload (raw scores kept separately via ArmScores).
  • cap_per_source: before fusion you can cap each arm to its top-cap, so one over-expanding arm can't crowd out the others (default 0 = off).

📖 There's also an interleave mode, fixing one of RRF's flaws

RRF scores a doc by the sum of its reciprocal ranks, so a result that is #1 in one arm but absent/low in the others gets averaged down. This bit during consolidation dedup: a “twin” result almost identical to an existing observation ranked #1 semantically but got buried past the budget by RRF/reranking, so the model never saw it and created a duplicate. interleave_fusion uses round-robin to guarantee each arm's top hits a slot (and skips the later combined-scoring re-sort). Consolidation uses interleave for exactly this reason (chapter 09).

3. Cross-encoder reranking

Locate: CrossEncoderReranker in search/reranking.py; the model abstraction CrossEncoderModel in cross_encoder.py.

📖 First understand bi-encoder vs cross-encoder

A bi-encoder (what the semantic arm uses) encodes query and doc separately into vectors then computes similarity — cheap, doc vectors can be precomputed, so it can recall quickly out of millions. But it never lets query and doc “meet”, so precision is limited. A cross-encoder feeds [query, document] concatenated through one transformer and outputs a single relevance score — much more accurate, but doc vectors can't be precomputed; it must score each candidate fresh, O(n) forward passes, expensive. This “cost asymmetry” determines the whole pipeline's shape: the cheap bi-encoder recalls a wide net, the expensive cross-encoder reranks only a small set.

When building the [query, doc] pairs, the doc text is context + ": " + text, and a formatted date is prepended for temporal awareness: f"[Date: {date_readable} ({date_iso})] {doc_text}". All pairs go into cross_encoder.predict(pairs) at once.

Normalization is conditional

engine/search/reranking.py · rerank (excerpt)python
scores = await self.cross_encoder.predict(pairs)

# External API rerankers (Cohere/Jina/etc.) return a calibrated relevance_score
# already in [0,1] — pass through as-is, preserving "absolute confidence"
# (a 0.007 candidate should stay low, not be inflated to 1.0 by rank normalization).
# Local models return logits (any real number) — sigmoid maps them to (0,1).
if scores and min(scores) >= 0.0 and max(scores) <= 1.0:
    normalized_scores = list(scores)          # calibrated — pass through
else:
    normalized_scores = [1 / (1 + np.exp(-s)) for s in scores]   # sigmoid

4. Pipeline order: fuse first, then rerank, on the pre-filtered set

# Pre-filter candidates by RRF before the (optional) cross-encoder.
# RRF already provides good ranking; this caps cross-encoder cost.
if len(merged_candidates) > reranker_max_candidates:      # default 300
    merged_candidates.sort(key=lambda mc: boosted_rrf_score(mc, strategy_boosts), reverse=True)
    merged_candidates = merged_candidates[:reranker_max_candidates]

if reranking == "cross_encoder":
    # Cancellation checkpoint: the cross-encoder rerank is the single most
    # CPU-expensive stage and runs in a worker thread that can't be interrupted
    # once dispatched. If the client already disconnected, skip it — don't burn
    # ~2 CPUs producing a result nobody will read.
    if request_context is not None:
        request_context.raise_if_cancelled()
    scored_results = await reranker_instance.rerank(query, merged_candidates)

Final order: CE primary, three multiplicative boosts

apply_combined_scoring treats the cross-encoder score as the primary signal, then multiplies by three boosts, each centered at 0.5 (missing signal = ×1.0):

engine/search/reranking.py · apply_combined_scoring (excerpt)python
recency_boost     = 1.0 + recency_alpha     * (sr.recency - 0.5)    # alpha=0.2
temporal_boost    = 1.0 + temporal_alpha    * (sr.temporal - 0.5)   # alpha=0.2
proof_count_boost = 1.0 + proof_count_alpha * (proof_norm - 0.5)    # alpha=0.1
sr.combined_score = (sr.cross_encoder_score_normalized
                     * recency_boost * temporal_boost * proof_count_boost)
sr.weight = sr.combined_score

💡 Why multiplicative rather than additive?

Multiplication guarantees these secondary signals' influence is always proportional to the base relevance — a candidate with a very low CE score won't be lifted by being “new” no matter what; and it's insensitive to how the cross-encoder calibrates its scores (different models score on different scales). At the default alphas the boosts swing at most about +21%/−19%: enough to nudge, not enough to overpower.

📖 recall_boost: weighting one arm, in two places and on two scales

A deployment can prioritize one arm (e.g. HINDSIGHT_API_RECALL_STRATEGY_BOOSTS=graph:high). It takes effect in two structurally different places: ① before the reranker cap, with a “weighted RRF” (rank-aware) so the boosted arm's candidates aren't cut by the 300-name gate; ② after the reranker, adding a flat boost to the final weight, nudging them up the delivered order.

5. Token-budget trimming

Two ordered cuts:

  1. By count: top_scored = scored_results[: thinking_budget * 2]. thinking_budget is resolved from the budget enum (default 100/300/1000, or adaptive to max_tokens).
  2. By token: _filter_by_token_budget uses tiktoken cl100k_base, counts only the text field, accumulates in rank order, and breaks the moment the next result would overflow — dropping the rest rather than splitting a fact:
engine/memory_engine.py · _filter_by_token_budget (excerpt)python
for result in results:
    text_tokens = len(encoding.encode(result.get("text", "")))
    if total_tokens + text_tokens <= max_tokens:     # default 4096
        filtered_results.append(result)
        total_tokens += text_tokens
    else:
        break          # stop before the overflowing fact

⚠️ Chunks are a separate budget, and they get truncated

If include_chunks, chunks use their own max_chunk_tokens budget (default 8192), taken before the fact filter; and unlike facts, the last chunk is truncated to fit (rather than dropped). Consequence: max_tokens=0 returns 0 facts but can still return chunks.

Summary

  • RRF: parameter-free fusion using rank only, Σ1/(60+rank), dedup by id.
  • Cross-encoder: feed query+doc together to rerank, expensive; so RRF pre-filters to 300 then reranks; normalization treats “calibrated vs logits” differently.
  • Combined scoring: CE primary × recency × temporal × proof (multiplicative, 0.5 neutral).
  • Trim: first thinking_budget×2 by count, then by token stopping before overflow; chunks on a separate budget.
