Part 3 · Retrieval (Recall)

08 · Fusion & Reranking

The four paths each hand back a ranked list. This chapter covers the “merge → rerank → trim” trio: Reciprocal Rank Fusion (RRF) combines the four incommensurable rankings into one; a cross-encoder reranks the survivors; then a token budget trims it to the final answer. Two classic exam questions live here: why RRF, and why “fuse first, rerank after”.

Chapter takeaways

  • RRF looks only at ranks, not scores: score(d) = Σ 1/(k+rank), k=60. No scales to align, no weights to tune.
  • The cross-encoder is expensive, so RRF pre-filters to 300 before reranking — this is the pipeline's cost gate.
  • The rerank score is the primary signal, then multiplied by recency / temporal / proof boosts (each centered at a neutral 0.5 → ×1.0) to get the final order.
  • Trimming happens twice: first cut the count to thinking_budget×2, then by max_tokens (tiktoken), stopping before the overflowing fact — never splitting a fact.

2. RRF: reciprocal rank fusion

Locate: search/fusion.py → reciprocal_rank_fusion(result_lists, k=60).

Formula: score(d) = Σ_lists 1/(k + rank(d)), k=60 (the classic Cormack/Clarke/Buettcher constant), ranks 1-based.

engine/search/fusion.py · reciprocal_rank_fusion (excerpt)python
rrf_scores[doc_id] += 1.0 / (k + rank)
source_ranks[doc_id][f"{source_name}_rank"] = rank

# The merged result keeps only the FIRST arm's RetrievalResult,
# so record each arm's raw score separately into ArmScores for downstream reporting/filtering.
if source_name == "semantic" and retrieval.similarity is not None:
    arm_scores[doc_id].semantic = retrieval.similarity
elif source_name == "bm25" and retrieval.bm25_score is not None:
    arm_scores[doc_id].keyword = retrieval.bm25_score

# Finally sort by RRF score descending; rrf_rank is assigned 1-based in that order.
for rrf_rank, (doc_id, rrf_score) in enumerate(
    sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True), start=1):
    merged_results.append(MergedCandidate(
        retrieval=all_retrievals[doc_id], rrf_score=rrf_score,
        rrf_rank=rrf_rank, source_ranks=..., arm_scores=...))

💡 Why RRF rather than a weighted sum?

The four paths' raw scores are on completely incommensurable scales: cosine similarity in [0,1], BM25 with no upper bound, graph activation in [0,3], temporal proximity yet another. A weighted sum would first need careful normalization onto one scale, plus tuned weights. RRF uses only ranks — “where you placed in your own path” — so there are no weights to tune and no scales to align, and it's naturally robust to one score type blowing up. Hence “parameter-free fusion”.

  • The dedup key is the document id; a fact appearing in several paths accumulates RRF score, but the merged result keeps only the first arm's payload (raw scores kept separately via ArmScores).
  • cap_per_source: before fusion you can cap each path to its top-cap, so one over-expanding path can't crowd out the others (default 0 = off).

📖 There's also an interleave mode, built to fix an RRF weakness

RRF scores by the sum of reciprocal ranks across arms, so a result that is #1 in one arm but absent/low in the others gets averaged down. This bit consolidation dedup: a “twin” result almost identical to an existing observation, ranked #1 by semantic, was buried by RRF/rerank outside the budget, so the model never saw it and created a duplicate. interleave_fusion uses round-robin to guarantee each arm's top gets a slot (and skips the later combined-scoring re-sort). Consolidation uses interleave specifically for this reason (ch09).

3. Cross-encoder reranking

Locate: search/reranking.py's CrossEncoderReranker; the model abstraction is cross_encoder.py's CrossEncoderModel.

📖 First, bi-encoder vs cross-encoder

A bi-encoder (what the semantic path uses) encodes query and doc independently into vectors, then compares — cheap, doc vectors can be precomputed, so it can recall from millions fast. But it never lets query and doc “meet”, so precision is limited. A cross-encoder feeds [query, document] concatenated through one transformer and outputs a single relevance score — far more accurate, but doc vectors can't be precomputed, so it's O(n) forward passes per candidate, expensive. This cost asymmetry determines the whole pipeline shape: the cheap bi-encoder recalls broadly, the expensive cross-encoder reranks only the small set.

When building the [query, doc] pairs, the doc text is context + ": " + text, and a formatted date is prepended for temporal awareness: f"[Date: {date_readable} ({date_iso})] {doc_text}". All pairs go into one cross_encoder.predict(pairs) call.

Normalization is conditional

engine/search/reranking.py · rerank (excerpt)python
scores = await self.cross_encoder.predict(pairs)

# External API rerankers (Cohere, Jina, ...) return calibrated relevance_score already in [0,1]
# -- pass through unchanged, preserving absolute confidence (a 0.007 candidate should stay low,
# not be inflated to 1.0 by rank normalization). Local models return logits (any real number)
# -- sigmoid maps them to (0,1).
if scores and min(scores) >= 0.0 and max(scores) <= 1.0:
    normalized_scores = list(scores)          # already calibrated, pass through
else:
    normalized_scores = [1 / (1 + np.exp(-s)) for s in scores]   # sigmoid

4. Pipeline order: fuse first, then rerank, on the pre-filtered set

# Pre-filter candidates by RRF before the (optional) cross-encoder.
# RRF already provides good ranking; this caps cross-encoder cost.
if len(merged_candidates) > reranker_max_candidates:      # default 300
    merged_candidates.sort(key=lambda mc: boosted_rrf_score(mc, strategy_boosts), reverse=True)
    merged_candidates = merged_candidates[:reranker_max_candidates]

if reranking == "cross_encoder":
    # Cancellation checkpoint: the cross-encoder rerank is the single most CPU-expensive
    # stage and runs in a worker thread that can't be interrupted once dispatched. If the
    # client already disconnected, skip it rather than burning ~2 CPUs for nothing.
    if request_context is not None:
        request_context.raise_if_cancelled()
    scored_results = await reranker_instance.rerank(query, merged_candidates)

Final order: CE primary, three multiplicative boosts

apply_combined_scoring treats the cross-encoder score as the primary signal, then multiplies by three boosts, each centered at a neutral 0.5 (missing signal = ×1.0):

engine/search/reranking.py · apply_combined_scoring (excerpt)python
recency_boost     = 1.0 + recency_alpha     * (sr.recency - 0.5)    # alpha=0.2
temporal_boost    = 1.0 + temporal_alpha    * (sr.temporal - 0.5)   # alpha=0.2
proof_count_boost = 1.0 + proof_count_alpha * (proof_norm - 0.5)    # alpha=0.1
sr.combined_score = (sr.cross_encoder_score_normalized
                     * recency_boost * temporal_boost * proof_count_boost)
sr.weight = sr.combined_score

💡 Why multiplicative rather than additive?

Multiplication guarantees these secondary signals' influence is always proportional to the base relevance — a candidate with a low CE score won't be lifted by being “new” no matter what; and it's robust to different cross-encoder calibrations (different models score on different scales). At the default alphas the boosts swing at most about +21%/−19%: enough to nudge, not enough to overpower.

📖 recall_boost: weighting a path in two places, on two scales

A deployment can prioritize one path (e.g. HINDSIGHT_API_RECALL_STRATEGY_BOOSTS=graph:high). It takes effect in two structurally different places: ① before the rerank cap, a “weighted RRF” (rank-aware) keeps the boosted path's candidates from being cut at the 300-mark; ② after the rerank, a flat additive is added to the final weight, nudging the boosted path's candidates up the delivered order.

5. Token-budget trimming

Two ordered cuts:

  1. By count: top_scored = scored_results[: thinking_budget * 2]. thinking_budget is resolved from the budget enum (default 100/300/1000, or adaptive from max_tokens).
  2. By token: _filter_by_token_budget uses tiktoken cl100k_base, counts only the text field, accumulates in ranked order, and breaks the moment the next result would overflow — dropping the rest, not splitting a fact:
engine/memory_engine.py · _filter_by_token_budget (excerpt)python
for result in results:
    text_tokens = len(encoding.encode(result.get("text", "")))
    if total_tokens + text_tokens <= max_tokens:     # default 4096
        filtered_results.append(result)
        total_tokens += text_tokens
    else:
        break          # stop before the overflowing fact

⚠️ Chunks are a separate budget, and they get truncated

If include_chunks, chunks use an independent max_chunk_tokens budget (default 8192), fetched before the fact token filter; and unlike facts, the last chunk is truncated to fit (rather than dropped). Consequence: max_tokens=0 yields 0 facts but can still return chunks.

Summary

  • RRF: parameter-free fusion on ranks only, Σ1/(60+rank), dedup by id.
  • cross-encoder: feeds query+doc together to rerank, expensive; so RRF pre-filters to 300 first; normalization treats “calibrated vs logits” differently.
  • combined scoring: CE primary × recency × temporal × proof (multiplicative, neutral at 0.5).
  • trim: first thinking_budget×2 by count, then by token stopping before overflow; chunks on a separate budget.
