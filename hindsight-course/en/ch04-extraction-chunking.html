Part 2 · Writing — Retain

04 · Fact Extraction & Chunking

Last chapter we walked the Retain backbone. This chapter dives into the most important step inside the streaming loop: how text is cut into chunks and how an LLM extracts atomic facts from them. Two designs that look ordinary but have repeatedly caused real trouble hide here — chunking idempotency, and decoupling the extraction prompt from the bank.

Chapter takeaways

  • Chunking chunk_text branches by content type: plain text sentence-aware, JSON conversation at turn boundaries, JSONL at line boundaries.
  • Chunking must be idempotent (re-chunking a result yields itself), else streaming's “pre-chunk once, re-chunk at extraction” makes sub-chunks collide on chunk_id (issue #2301).
  • A “fact” is multi-dimensional: what/when/where/who/why + fact_type + entities + causal_relations, finally joined into one fact_text.
  • The extraction prompt's system part is deliberately bank-agnostic (the mission goes into the user message), purely to share the LLM cache across banks.
  • chunks mode is the “call no LLM” fallback: the whole chunk becomes one fact.

1. Two sub-problems: how to cut, how to extract

Retain's “extract + embed” happens in engine/retain/fact_extraction.py (~2800 lines, one of the largest files in the package — also read by jumping to functions). It solves two sub-problems:

  • Chunking: cut possibly-large input text into small pieces suitable for the LLM. Entry point chunk_text.
  • Extraction: hand each piece to the LLM and pull out structured facts one by one. Entry point extract_facts_from_contents (processes multiple contents in parallel).

2. Chunking: chunk_text

Locate: engine/retain/fact_extraction.py → chunk_text; the branch helpers _chunk_conversation, _chunk_jsonl, _split_oversized_unit.

It first decides what kind of input it is, then picks a different cutting strategy:

engine/retain/fact_extraction.py · chunk_text (excerpt)python
def chunk_text(text: str, max_chars: int, structured_chunk_size: int | None = None) -> list[str]:
    # small enough — return the whole thing
    if len(text) <= max_chars:
        return [text]

    structured_limit = structured_chunk_size if structured_chunk_size is not None else max_chars

    # try to parse as a JSON conversation array ([{user...}, {assistant...}, ...])
    try:
        parsed = json.loads(text)
    except (json.JSONDecodeError, ValueError):
        parsed = None

    if isinstance(parsed, list) and all(isinstance(turn, dict) for turn in parsed):
        # a conversation — chunk at turn boundaries, never cut one utterance in half
        return _chunk_conversation(parsed, max_chars, structured_limit)

    if isinstance(parsed, dict):
        # a single JSON object (maybe one JSONL line already pre-chunked upstream) — keep whole
        if len(text) <= structured_limit:
            return [text]
        return _split_oversized_unit(text, max_chars)

    # try JSONL (one JSON object per line, e.g. session logs)
    jsonl_chunks = _chunk_jsonl(text, max_chars, structured_limit)
    if jsonl_chunks is not None:
        return jsonl_chunks

    # fallback: sentence-aware plain-text splitting
    return _split_oversized_unit(text, max_chars)

Behavior notes:

  • Plain text: sentence-aware splitting (prefer cutting at sentence boundaries, not mid-sentence).
  • JSON conversation array: cut at turn boundaries so no utterance is split in two.
  • JSONL: cut at line boundaries, one object per line not split.
  • If a single utterance/line exceeds max_chars, keep it whole up to structured_chunk_size, then cut as text.

⚠️ Idempotency: the single most important invariant here (issue #2301)

The chunk_text docstring states plainly: “the result is idempotent: re-chunking any chunk this returns yields that chunk unchanged.” Why must it be? Because the streaming pipeline pre-chunks the whole document once, then re-chunks each piece again at extraction. If the second pass cut a piece further, those sub-chunks would inherit the same chunk_index, and chunk_id = {bank}_{doc}_{chunk_index} is a deterministic primary key — hence a collision and corrupted data. The isinstance(parsed, dict) branch above exists specifically to plug the hole where “one object the upstream deliberately kept whole falls through to plain-text splitting and gets re-cut”.

✅ A general engineering lesson

When the same function will be called repeatedly at different pipeline stages, make it idempotent. Otherwise the side effect of the second call (here, cutting one more time) quietly breaks an invariant the first call established. These bugs are extremely hard to reproduce and usually surface only on inputs of a specific length.

After chunking, the orchestrator clears the big RetainContent.content string, keeping only the all_pre_chunks working set — purely for memory (a large document can be several MB × N copies).

3. What one “fact” looks like

Locate: fact_extraction.py → ExtractedFact (the default-mode Pydantic schema).

The LLM is asked to output several dimensions per fact, not just one sentence:

engine/retain/fact_extraction.py · ExtractedFact (excerpt)python
class ExtractedFact(BaseModel):
    what: str = Field(description="Core fact - concise but complete (1-2 sentences)")
    when: str = Field(description="When it happened. 'N/A' if unknown.")
    where: str = Field(description="Location if relevant. 'N/A' if none.")
    who: str = Field(description="People involved with relationships. 'N/A' if general.")
    why: str = Field(description="Context/significance if important. 'N/A' if obvious.")

    fact_kind: str = Field(default="conversation", description="'event' or 'conversation'")
    occurred_start: str | None = Field(default=None, description="ISO timestamp for events")
    occurred_end: str | None = Field(default=None, description="ISO timestamp for event end")
    fact_type: Literal["world", "assistant"] = Field(
        description="'world' = objective/external facts, including user preferences, rules...; "
                    "'assistant' = actions/experiences the assistant/agent actually performed.")
    entities: list[str] = Field(default_factory=list,
        description='People, places, concepts - plain strings, e.g. ["Alice", "Kubernetes"]')
    causal_relations: list[FactCausalRelation] | None = Field(
        default=None, description="Links to previous facts (target_index < this fact's index)")

    def build_fact_text(self) -> str:
        parts = [self.what]
        if self.who and self.who.upper() != "N/A":
            parts.append(f"Involving: {self.who}")
        if self.why and self.why.upper() != "N/A":
            parts.append(self.why)
        return " | ".join(parts) if len(parts) > 1 else parts[0]

📖 The fact_type “dialect”: world/assistant → world/experience

Note that at extraction time the LLM outputs fact_type as "world" or "assistant"; whereas chapter 01 said the database stores world / experience. These are two names for the same concept: the prompt uses “assistant” because it fits the model's understanding of “the first person is me (the agent)”, and it's mapped to the more general experience at storage. Don't think they're two different things when you see both words in the code.

  • entities is a plain list of strings (e.g. ["Alice", "Kubernetes"]), even abstract concepts like “friendship” or “career growth”. These strings get normalized into canonical entities in the next chapter — the extraction layer only records “what was mentioned”, not “is it the same as an existing entity”.
  • causal_relations can only point at earlier facts (target_index < this fact's index, at most 2 each). This is the source of causal edges; chapter 05 shows how it becomes a caused_by edge. It references by “index within the batch” rather than ID, because at this point the facts aren't stored yet and have no real IDs.
  • build_fact_text() joins the dimensions into one string (what | Involving: who | why) — this is what actually goes into memory_units.text, gets embedded, and gets retrieved.

4. Prompt design: why the system part is bank-agnostic

Locate: fact_extraction.py → _build_extraction_prompt_and_schema (assembles the system prompt + picks the schema); _build_user_message (assembles the per-request user message).

Extraction modes

Key design: the system prompt is deliberately “bank-agnostic”

This is the design decision most worth remembering in this chapter. Intuitively, a bank's retain_mission (“what this memory bank focuses on”) seems like it belongs in the system prompt. But the source deliberately does not:

engine/retain/fact_extraction.py · _build_extraction_prompt_and_schema (comment)python
# The per-bank retain mission is NOT baked into this system prompt: it would
# make the prompt bank-specific and force a separate Gemini context cache per
# mission (one per bank). Instead the prompt is bank-agnostic so a single
# CachedContent serves every bank, and the mission rides in the per-request
# user message via _retain_mission_preamble().

💡 Why? To share the cache across banks and save money

Gemini (and Anthropic, OpenAI) support prompt-prefix caching: an identical prefix is paid for in full once, and later hits are much cheaper. If the mission were in the system prompt, then every bank's system prompt would differ, requiring a separate cache per bank — thousands of banks means thousands of caches and a collapsing hit rate. Put the part that's identical for all banks (extraction rules, input format, output format) into the cacheable system, and the per-bank mission into each request's user message, and one cache serves every bank. A classic example of “adjusting prompt structure for cost”.

First-person attribution: Narrator vs Context precedence

Extraction also has to resolve who “I” is. _build_user_message injects a Narrator note, and makes Context take precedence:

engine/retain/fact_extraction.py · _build_user_message (excerpt)python
if agent_name:
    narrator_section = (
        f"\nNarrator: {agent_name} (the AI agent whose memory this is). By default, "
        f'first-person statements like "I did X" are {agent_name}\'s own actions → classify as '
        f'"assistant".'
    )
    if context:
        narrator_section += (
            " BUT the Context above takes precedence: if it identifies a different "
            "first-person speaker (e.g. a user or customer in a transcript), attribute those "
            'statements to that speaker and classify them as "world", not "assistant".'
        )

Meaning: by default “I did X” is the agent's own action → classified as assistant (i.e. experience); but if the Context shows the speaker is a user/customer, then “I” refers to the user → classified as world. This decides whether the memory is “my experience” or “a fact about the world (the user)”.

✅ Also note: output language and search language are different things

The prompt also appends a “force the facts to be emitted in the configured language” directive (llm_output_language). The source comment stresses: this and the BM25 indexing language (text_search_extension_native_language) are two independent configs — “what language the LLM outputs in” and “what language full-text search tokenizes by” are separate concerns; don't mix them.

5. chunks mode: the “call no LLM” fallback

Locate: fact_extraction.py → _extract_facts_chunks.

When you don't need (or can't) call an LLM, the system uses chunks mode: each chunk directly becomes one world fact, the raw text is the fact_text, no entities extracted.

engine/retain/fact_extraction.py · _extract_facts_chunks (excerpt)python
# chunks mode: no LLM call, no entity extraction.
# Each chunk becomes one memory unit with the raw text as fact_text.
for chunk in chunks:
    extracted_facts.append(ExtractedFactType(
        fact_text=chunk,
        fact_type="world",
        entities=[],          # this mode extracts no entities
        content_index=content_index,
        chunk_index=global_chunk_idx,
        ...
    ))

📖 When is it forced into chunks?

When HINDSIGHT_API_LLM_PROVIDER is set to none, config validation forces retain_extraction_mode="chunks" and disables observations — the logic being: with no model, don't pretend you can extract facts; honestly do “vector-retrieval-only” naive memory. This also makes “no LLM” a runnable, demonstrable degraded mode.

6. Failure handling: be loud, but also fault-tolerant

  • Fail when you should: exhausted retries, protocol errors, etc. must raise (issue #1833) — never return an empty list and mark success, which would silently lose memory (stressed in chapter 03).
  • Output-too-long auto-splits and retries: if the model says “output too long” (OutputTooLongError), _extract_facts_with_auto_split splits that chunk in two and extracts each separately, rather than giving up.
  • Transient errors are retryable: occasional JSON parse failures, connection errors, etc. go through retries; but deterministic errors like “embedding dimension mismatch” are not retried (retrying just burns worker slots for nothing).

⚠️ Two same-named functions — don't mix

embedding_processing.py and embedding_utils.py each have a generate_embeddings_batch — the former is the wrapper, the latter the implementation. Watch the import path.

Summary

  • chunk_text branches by type (text/conversation/JSONL); the core invariant is idempotency (issue #2301).
  • A fact is multi-dimensional (what/when/where/who/why + fact_type + entities + causal_relations), finally joined into a single fact_text.
  • fact_type at extraction is world/assistant; at storage it's world/experience.
  • The extraction system prompt is decoupled from the bank, with the mission in the user message, to share the LLM cache across banks.
  • chunks mode is the no-LLM fallback; failure handling follows “be loud when you should, be tolerant when you can”.
