Part 2 · Writing (Retain)

04 · Fact Extraction & Chunking

Last chapter we walked the Retain skeleton. This one zooms into the most critical step inside the streaming loop: how text is cut into chunks and how an LLM turns each chunk into atomic facts. Two designs here look ordinary but have repeatedly caused real bugs — chunking idempotency, and decoupling the extraction prompt from the bank.

Chapter takeaways

  • chunk_text splits by content type: plain text sentence-aware, JSON conversations at turn boundaries, JSONL at line boundaries.
  • Chunking must be idempotent (re-chunking a result yields itself), else streaming's “pre-chunk once, re-chunk during extraction” collides on chunk_id (issue #2301).
  • A “fact” is multi-dimensional: what/when/where/who/why + fact_type + entities + causal_relations, finally joined into one fact_text.
  • The extraction prompt's system part is deliberately bank-agnostic (the mission rides in the user message) — purely to share the LLM cache across banks.
  • chunks mode is the “no LLM” fallback: each whole chunk becomes one fact.

1. Two sub-problems: how to cut, how to extract

Retain's “extract + embed” lives in engine/retain/fact_extraction.py (~2800 lines, one of the package's largest files — jump by function here too). It solves two sub-problems:

  • Chunking: cut possibly large input text into pieces small enough to feed the LLM. Entry point chunk_text.
  • Extraction: hand each piece to the LLM and extract structured facts. Entry point extract_facts_from_contents (processes several contents in parallel).

2. Chunking: chunk_text

Locate: engine/retain/fact_extraction.py → chunk_text; branch helpers _chunk_conversation, _chunk_jsonl, _split_oversized_unit.

It first decides what kind of input it has, then picks a cutting strategy:

engine/retain/fact_extraction.py · chunk_text (excerpt)python
def chunk_text(text: str, max_chars: int, structured_chunk_size: int | None = None) -> list[str]:
    # Small enough: return as one chunk
    if len(text) <= max_chars:
        return [text]

    structured_limit = structured_chunk_size if structured_chunk_size is not None else max_chars

    # Try to parse as a JSON conversation array ([{user...}, {assistant...}, ...])
    try:
        parsed = json.loads(text)
    except (json.JSONDecodeError, ValueError):
        parsed = None

    if isinstance(parsed, list) and all(isinstance(turn, dict) for turn in parsed):
        # It's a conversation - cut at turn boundaries, never split one utterance
        return _chunk_conversation(parsed, max_chars, structured_limit)

    if isinstance(parsed, dict):
        # A single JSON object (maybe one JSONL line the producer already kept whole)
        if len(text) <= structured_limit:
            return [text]
        return _split_oversized_unit(text, max_chars)

    # Try JSONL (one JSON object per line, e.g. session logs)
    jsonl_chunks = _chunk_jsonl(text, max_chars, structured_limit)
    if jsonl_chunks is not None:
        return jsonl_chunks

    # Fallback: sentence-aware plain-text splitting
    return _split_oversized_unit(text, max_chars)

Behavior in brief:

  • Plain text: sentence-aware (cut at sentence boundaries where possible, not mid-sentence).
  • JSON conversation array: at turn boundaries, never splitting one utterance.
  • JSONL: at line boundaries, one object per line not split.
  • A single utterance/line larger than max_chars is kept whole up to structured_chunk_size, then cut as text.

⚠️ Idempotency: the most important invariant here (issue #2301)

The chunk_text docstring says so explicitly: “the result is idempotent: re-chunking any chunk this returns yields that chunk unchanged.” Why must it be? Because the streaming pipeline pre-chunks the whole document once, then re-chunks each piece again during extraction. If the second pass split a piece further, those sub-chunks would inherit the same chunk_index, and since chunk_id = {bank}_{doc}_{chunk_index} is a deterministic primary key — collision and corruption. The isinstance(parsed, dict) branch above exists specifically to plug the hole where “an object the producer kept whole falls into plain-text splitting and gets re-cut”, breaking idempotency.

✅ A general engineering lesson

When the same function is called repeatedly at different pipeline stages, make it idempotent. Otherwise the second call's side effect (here, one more cut) quietly breaks the invariant the first call established. These bugs are very hard to reproduce — they usually surface only at particular input lengths.

After chunking, the orchestrator clears the big RetainContent.content string, keeping only the all_pre_chunks working set — purely for memory (a large document can be several MB × N copies).

3. What one “fact” looks like

Locate: fact_extraction.py → ExtractedFact (the default-mode Pydantic schema).

The LLM is asked to output several dimensions per fact, not a single sentence:

engine/retain/fact_extraction.py · ExtractedFact (excerpt)python
class ExtractedFact(BaseModel):
    what: str = Field(description="Core fact - concise but complete (1-2 sentences)")
    when: str = Field(description="When it happened. 'N/A' if unknown.")
    where: str = Field(description="Location if relevant. 'N/A' if none.")
    who: str = Field(description="People involved with relationships. 'N/A' if general.")
    why: str = Field(description="Context/significance if important. 'N/A' if obvious.")

    fact_kind: str = Field(default="conversation", description="'event' or 'conversation'")
    occurred_start: str | None = Field(default=None, description="ISO timestamp for events")
    occurred_end: str | None = Field(default=None, description="ISO timestamp for event end")
    fact_type: Literal["world", "assistant"] = Field(
        description="'world' = objective/external facts, including user preferences, rules...; "
                    "'assistant' = actions/experiences the assistant/agent actually performed.")
    entities: list[str] = Field(default_factory=list,
        description='People, places, concepts - plain strings, e.g. ["Alice", "Kubernetes"]')
    causal_relations: list[FactCausalRelation] | None = Field(
        default=None, description="Links to previous facts (target_index < this fact's index)")

    def build_fact_text(self) -> str:
        parts = [self.what]
        if self.who and self.who.upper() != "N/A":
            parts.append(f"Involving: {self.who}")
        if self.why and self.why.upper() != "N/A":
            parts.append(self.why)
        return " | ".join(parts) if len(parts) > 1 else parts[0]

📖 The fact_type “dialect”: world/assistant → world/experience

Note that at extraction the LLM outputs fact_type as "world" or "assistant", while ch01 said the database stores world / experience. These are two names for the same concept: the prompt uses “assistant” because it fits the model's understanding of “first person = me (the agent)”, and it is mapped to the more general experience on persistence. Don't read the two words as different things.

  • entities is a list of plain strings (e.g. ["Alice", "Kubernetes"]), including abstract concepts like “friendship” or “career growth”. These strings are normalized into canonical entities in the next chapter — the extraction layer only records “what was mentioned”, not “is this the same entity as an existing one”.
  • causal_relations may only point to earlier facts (target_index < this fact's index, max 2 per fact). This is the source of causal edges; ch05 shows how it becomes a caused_by edge. It references by in-batch index rather than ID because at this point the facts aren't persisted yet and have no real ID.
  • build_fact_text() joins the dimensions into one string (what | Involving: who | why) — and that is what actually lands in memory_units.text, gets embedded, and gets retrieved.

4. Prompt design: why the system part is bank-agnostic

Locate: fact_extraction.py → _build_extraction_prompt_and_schema (assembles the system prompt + picks the schema); _build_user_message (assembles the per-request user message).

Extraction modes

The config field retain_extraction_mode chooses which prompt and schema to use:

Key design: the system prompt is deliberately bank-agnostic

This is the design decision most worth remembering in this chapter. Intuitively the bank's retain_mission (“what this bank cares about”) seems like it belongs in the system prompt. But the source deliberately does not do that:

engine/retain/fact_extraction.py · _build_extraction_prompt_and_schema (comment)python
# The per-bank retain mission is NOT baked into this system prompt: it would
# make the prompt bank-specific and force a separate Gemini context cache per
# mission (one per bank). Instead the prompt is bank-agnostic so a single
# CachedContent serves every bank, and the mission rides in the per-request
# user message via _retain_mission_preamble().

💡 Why? To share the cache across banks and save money

Gemini (and Anthropic, OpenAI) support prompt-prefix caching: an identical prefix is paid for in full once, and later hits are much cheaper. If the mission were in the system prompt, then every bank's system prompt would differ, requiring a separate cache per bank — thousands of banks means thousands of caches, and the hit rate collapses. Putting the bank-invariant part (extraction rules, input format, output format) in the cacheable system prompt, and the per-bank mission in the per-request user message, lets one cache serve all banks. A textbook case of “reshaping the prompt for cost”.

First-person attribution: Narrator vs Context precedence

Extraction also has to resolve who “I” is. _build_user_message injects a Narrator note, and makes Context take precedence:

engine/retain/fact_extraction.py · _build_user_message (excerpt)python
if agent_name:
    narrator_section = (
        f"\nNarrator: {agent_name} (the AI agent whose memory this is). By default, "
        f'first-person statements like "I did X" are {agent_name}\'s own actions → classify as '
        f'"assistant".'
    )
    if context:
        narrator_section += (
            " BUT the Context above takes precedence: if it identifies a different "
            "first-person speaker (e.g. a user or customer in a transcript), attribute those "
            'statements to that speaker and classify them as "world", not "assistant".'
        )

Meaning: by default “I did X” is the agent's own action → assistant (i.e. experience); but if the Context shows the speaker is a user/customer, then “I” refers to the user → world. This decides whether the memory is “my experience” or “a fact about the world (the user)”.

5. chunks mode: the no-LLM fallback

Locate: fact_extraction.py → _extract_facts_chunks.

When you don't need (or can't use) an LLM, the system takes chunks mode: each chunk directly becomes one world fact, the raw text is the fact_text, and no entities are extracted.

engine/retain/fact_extraction.py · _extract_facts_chunks (excerpt)python
# chunks mode: no LLM call, no entity extraction.
# Each chunk becomes one memory unit with the raw text as fact_text.
for chunk in chunks:
    extracted_facts.append(ExtractedFactType(
        fact_text=chunk,
        fact_type="world",
        entities=[],          # no entity extraction in this mode
        content_index=content_index,
        chunk_index=global_chunk_idx,
        ...
    ))

📖 When is chunks mode forced?

When HINDSIGHT_API_LLM_PROVIDER is none, config validation forces retain_extraction_mode="chunks" and disables observations — the logic being: with no model, don't pretend you can extract facts; honestly do “vector-search-only” memory. This also makes “no LLM” a runnable, demoable degraded mode.

6. Failure handling: be loud, but tolerate what's tolerable

  • Fail when you should fail: exhausted retries, protocol errors, etc. must raise (issue #1833) — never return an empty list while marking success, which would silently lose memory (stressed in ch03).
  • Auto-split on output-too-long: if the model says “output too long” (OutputTooLongError), _extract_facts_with_auto_split splits that chunk in two and extracts each, instead of giving up.
  • Transient errors are retryable: occasional JSON-parse failures and connection errors retry; but a deterministic error like “embedding dimension mismatch” is not retried (retrying just burns worker slots for nothing).

Summary

  • chunk_text splits by type (text/conversation/JSONL); its core invariant is idempotency (issue #2301).
  • A fact is multi-dimensional (what/when/where/who/why + fact_type + entities + causal_relations), finally joined into one fact_text.
  • fact_type at extraction is world/assistant; persisted as world/experience.
  • The extraction system prompt is decoupled from the bank; the mission rides in the user message — to share the LLM cache across banks.
  • chunks mode is the no-LLM fallback; failure handling follows “be loud when you should, tolerate when you can”.
