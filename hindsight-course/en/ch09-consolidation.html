Part 4 · Reasoning & Consolidation

09 · Consolidation: Facts to Observations

Hindsight claims it “learns, not just remembers”. That “learning” happens in consolidation: a background job that runs after Retain and synthesizes / updates scattered world/experience facts into observations. This chapter covers how it works, why it can't happen inline in Retain, and why it's almost paranoid about tags.

Chapter takeaways

  • Consolidation is bottom-up “learning”: facts → observation (a memory_units row with fact_type='observation'). It is not the mental_models table (that's user-defined, refreshed on demand).
  • It's decoupled from Retain: Retain commits in streamed chunks so there's no “full fact set” mid-flight; consolidation is also expensive; decoupling also makes it crash-resumable.
  • The work queue is just a SQL predicate: consolidated_at IS NULL AND fact_type IN ('experience','world').
  • Core policy: prefer UPDATE over CREATE (one observation with many evidence facts > a pile of twins each with one); tags are a security boundary — facts with different tags never share one LLM call.
  • When a source changes, delete the observation + reset consolidated_at so the facts re-consolidate next round.

1. What consolidation does, and why it's separate from Retain

Retain is a recording pipeline: extract facts, store them, and stamp each fact with an observation_scopes directive — but synthesize nothing. Consolidation is the separate learning pipeline: read a batch of unconsolidated facts and produce/update observation rows (carrying proof_count support count, source_memory_ids evidence set, history change log).

💡 Why not consolidate inline in Retain?

(1) No complete set: Retain commits in streamed chunks, so halfway through there's no “all the facts for this document”, yet observations need to aggregate across chunks and documents. (2) Cost: consolidation is LLM-heavy (recall + synthesis + optional dedup adjudication); folding it into Retain would couple write latency to synthesis; separated, it can run on the worker pool with its own concurrency budget and exploit a bank-agnostic cacheable prompt prefix to save money. (3) Re-runnable: progress is marked per fact (consolidated_at), failures quarantined (consolidation_failed_at), so a crash or a half-run simply resumes where it left off.

2. observation_scopes: at what granularity to consolidate

Locate: consolidator.py → _resolve_obs_tags_list.

At Retain time each content item can carry an observation_scopes that decides “group these facts into observations by what tag scope”:

ValueMeaning
combined (default/None)Use the fact's full tag set as one scope, one consolidation pass
per_tagOne pass per individual tag: tags [a, b] contribute to scope {a} and scope {b} separately
all_combinationsOne pass per non-empty subset of the tags: {a}, {b}, {a,b}
sharedOne pass over the empty scope: the produced observation carries no tags and is matched with tags_match="any" — every fact consolidates into one global observation (used to dedup across volatile provenance tags)
explicit list[list[str]]One pass per inner tag list — full caller control
engine/consolidation/consolidator.py · _resolve_obs_tags_list (excerpt)python
parsed = _parse_observation_scopes(memory)
tags = list(memory.get("tags") or [])
if parsed == "per_tag":
    return [[t] for t in tags] if tags else None
if parsed == "all_combinations":
    return [list(c) for r in range(1, len(tags)+1) for c in combinations(tags, r)] if tags else None
if parsed == "shared":
    return [[]]                      # one empty scope
if parsed == "combined" or parsed is None:
    return None                      # default: use the fact's own tags
return parsed                        # explicit list[list[str]]

There's also _resolve_write_scopes, which returns the same scopes as frozensets so the parallel dispatcher can take one async lock per scope: two tag groups whose write-scope sets overlap serialize on the shared scope (instead of racing on the same observation row); disjoint groups run concurrently. Lock acquisition order is a total order, specifically to be deadlock-free.

engine/consolidation/consolidator.py · fetch & group (excerpt)python
memories = await conn.fetch(f"""
    SELECT id, text, fact_type, ..., observation_scopes
    FROM memory_units
    WHERE bank_id = $1
      AND consolidated_at IS NULL
      AND consolidation_failed_at IS NULL
      AND fact_type IN ('experience', 'world')
    ORDER BY created_at ASC
    LIMIT ${limit_idx}""", *fetch_params)
if not memories:
    break

# Group by exact tag set — security requirement: facts with different tags
# must never share one LLM call.
tag_groups: dict[tuple[str, ...], list[dict]] = {}
for m in memories:
    tag_key = tuple(sorted(m.get("tags") or []))
    tag_groups.setdefault(tag_key, []).append(dict(m))

Inside each LLM batch: ① per-fact parallel recall of related observations (reusing recall, but limited to fact_type=["observation"], tags_match="all_strict", reranking="interleave"); ② union across the batch, dedup; ③ one LLM call handling N facts + those observations; ④ sequential write actions (writes stay serial for consistency). Execution order is deletes first (free observation slots) then updates then creates. Failure handling uses adaptive bisection: a failed batch is split in half and retried down to a single memory; only a single-memory failure gets stamped consolidation_failed_at.

A few processing rules are especially worth remembering (all places the model tends to err):

RuleThe gist, in the model's words
Prefer UPDATE over CREATEIf new facts describe the same canonical event/statement already covered by an existing observation, UPDATE it and attach the new facts as evidence — don't create a near-duplicate sibling. “One canonical observation with many source facts is always better than many siblings with one source fact each.”
One observation per facetA count, an entity, a relationship — never merged.
State changes update“sold X”, “X died”, “moved to Y” → update the matching observation to reflect current state.
Preserve historyObservations recording significant events are important history — never delete them; deletes must be very conservative.
No computation“You don't have the full picture — never calculate, derive, or adjust numeric values. If the user says ‘I have 2 dogs’ then ‘I have a dog named Rex’, don't change the count to 3 — you don't know if Rex is one of the 2 or a new one.”

Output is {"creates":[...], "updates":[...], "deletes":[...]}; every action must carry a reason (“for a CREATE, state which existing observations you considered and why none matched — this is audited to catch duplicate creates”). And at most one UPDATE per observation_id (multiple would silently overwrite each other).

💡 The model isn't trusted, so layers of defense

After the LLM there are several deterministic guardrails: _dedupe_updates collapses multiple updates to the same observation_id; an exact-text guard drops CREATEs that verbatim reproduce an observation already in the context (because “the model intermittently does this”); and optional semantic dedup (when the threshold < 1.0) probes each CREATE/UPDATE against its top-5 in-scope neighbors, then a focused second LLM call adjudicates merge-vs-keep on the word-level differences.

📖 Why consolidation recall uses interleave reranking

Consolidation's observation recall uses reranking="interleave" (covered in chapter 08). The reason is measured and written in the comment: the cross-encoder demotes that “near-identical twin observation” from semantic #1 to reranked #37, and RRF also pushes it out of the 512-token budget — so the model never sees it and creates a duplicate. Interleave guarantees each arm's top hits a slot, the twin is always shown, and the model UPDATEs instead of CREATEs.

5. Update vs recreate, and invalidation

An UPDATE rewrites in place the observation's text and embedding, extends provenance, merges inherited fields — never re-created from scratch. Two notes: tags are unioned, not replaced (every contributor keeps visibility); temporal fields aggregate (earliest start, latest end, latest mentioned). Each update first snapshots the prior state into the observation_history table, capped in row count — because an earlier design stored history in a single JSONB column, and an often-reinforced observation grew it past PostgreSQL's 256 MB jsonb limit and got stuck.

⚠️ Invalidation = delete the observation + reset consolidated_at

When underlying facts are removed/replaced (document re-ingest, memory delete, tag change, clear observations), delete_stale_observations_for_memories will: ① delete the observations referencing those facts (even one missing source makes its text stale); ② reset the surviving source facts' consolidated_at to NULL so they re-consolidate next round. That's the system's “re-consolidation” mechanism: delete + reset = put the facts back in the work queue. The reverse race (consolidation building an observation from facts deleted mid-run) is closed by _filter_live_source_memories, which re-checks source ids FOR SHARE before every insert/update.

6. Triggering & scheduling

  • Automatic after Retain: after each fact insert, _submit_post_insert_maintenance is called, gated by bank config enable_observations + enable_auto_consolidation. Failure is only logged, never raised — consolidation can't fail a retain.
  • Bank-level dedupe: on submit, if an “unscoped pending” operation already exists for the bank, the original operation_id is reused instead of queuing a duplicate (dedupe checks only pending, not processing — a processing task uses a watermark from when it started, so facts added after that still need a fresh run).
  • Worker claims it: a separate worker process polls async_operations every 500ms, with reserved slots for consolidation (default {"consolidation": 2}) so consolidation gets guaranteed capacity without starving retains.
  • Manual / maintenance: POST /banks/{id}/consolidate, clearing a memory's observations, a maintenance reconcile that sweeps backlog.
  • Self re-queue: hitting the per-round budget re-submits the job — and that failure must propagate, else “the bank has backlog but no queued work — silently stuck”.
  • Downstream: on a completed final round, consolidation submits refresh_mental_model tasks for stale user-defined mental models with matching tags.

7. Design decisions & gotchas

PointNotes
Tags are a security boundary, not a hintFacts with different tags never share an LLM call; recall uses all_strict; writes re-check the per-fact recall set — preventing cross-tenant/cross-user leakage
Visibility is algorithmic, the model doesn't decideTags are inherited/merged by algorithm; the prompt explicitly says “don't output tags”
Only world/experience consolidateObservations don't consolidate each other; a singleton failure is stamped and excluded from future automatic runs (manual recover exists)
total_count is a point-in-time estimateFacts retained mid-run get picked up; processed may exceed it
Semantic dedup is PG-onlyUses unnest/array_agg/UPDATE...FROM; Oracle skips it and uses the observation_sources junction table
shared scope is untagged & globally visibleMisuse is a cross-tag leak; docs frame it as the dedicated dedup-across-provenance-tags mode

Summary

  • Consolidation = bottom-up learning: facts → observation (a special fact); decoupled from retain (no full set, expensive, resumable).
  • The work queue is a SQL predicate; group by exact tag set (security); each batch “parallel recall → one LLM → sequential writes”; delete before create.
  • Policy core: prefer UPDATE; no computation; layers of defense against the model erring; tags are a security boundary.
  • Invalidation = delete observation + reset consolidated_at = re-consolidation.
