Part 4 · Reasoning & Consolidation

09 · Consolidation: Facts to Observations

Hindsight claims it “learns, not just remembers”. That learning happens in consolidation: a background job that runs after Retain and synthesizes and updates scattered world/experience facts into observations. This chapter covers how it works, why it can't be folded into Retain, and why it is almost obsessive about tags.

Chapter takeaways

  • Consolidation is the bottom-up “learning”: facts → observation (a memory_units row with fact_type='observation'). It is not the mental_models table (that's user-defined, refreshed on demand).
  • Decoupled from Retain: Retain commits in streamed chunks, so mid-way there's no “full fact set”; consolidation is also expensive; decoupled, it can also resume after a crash.
  • The work queue is just a SQL predicate: consolidated_at IS NULL AND fact_type IN ('experience','world').
  • Core policy: prefer UPDATE over CREATE (one observation with many evidence facts > a pile of twins with one each); tags are a security boundary — facts with different tags never share one LLM call.
  • When a source changes: delete the observation + reset consolidated_at, so the surviving facts re-consolidate next round.

1. What consolidation does, and why it's separate from Retain

Retain is the recording pipeline: extract facts, persist them, and stamp each fact with an observation_scopes directive — but synthesize nothing. Consolidation is the separate learning pipeline: read a batch of unconsolidated facts and produce/update observation rows (carrying proof_count, the evidence set source_memory_ids, and a history of changes).

💡 Why not consolidate inside Retain?

(1) No full set exists: Retain commits in streamed chunks; half-way through there is no “all facts for this document”, yet observations need to aggregate across chunks and documents. (2) Cost: consolidation is LLM-heavy (recall + synthesis + optional dedup adjudication); shoving it into Retain couples write latency to synthesis; separate, it runs in the worker pool on its own concurrency budget and can use a bank-agnostic cacheable prompt prefix to save money. (3) Re-runnable: progress is marked per fact (consolidated_at), failures quarantined (consolidation_failed_at), so a crash or a half-run simply resumes where it left off.

2. observation_scopes: at what granularity to consolidate

Locate: consolidator.py → _resolve_obs_tags_list.

At Retain time each content item can carry an observation_scopes, deciding “group these facts into observations by what tag scope”:

ValueMeaning
combined (default / None)one consolidation pass using the fact's full tag set as a single scope
per_tagone pass per individual tag: tags [a, b] feed scope {a} and scope {b} separately
all_combinationsone pass per non-empty subset of the tags: {a}, {b}, {a,b}
sharedone pass over the empty scope: the produced observation carries no tags and matches with tags_match="any" — every fact consolidates into one global observation (for dedup across volatile provenance tags)
explicit list[list[str]]one pass per inner tag list — full caller control
engine/consolidation/consolidator.py · _resolve_obs_tags_list (excerpt)python
parsed = _parse_observation_scopes(memory)
tags = list(memory.get("tags") or [])
if parsed == "per_tag":
    return [[t] for t in tags] if tags else None
if parsed == "all_combinations":
    return [list(c) for r in range(1, len(tags)+1) for c in combinations(tags, r)] if tags else None
if parsed == "shared":
    return [[]]                      # one empty scope
if parsed == "combined" or parsed is None:
    return None                      # default: use the fact's own tags
return parsed                        # explicit list[list[str]]

There's also _resolve_write_scopes, which returns the same scopes as frozensets so the parallel dispatcher can take one async lock per scope: two tag-groups whose write-scopes overlap serialize on the shared scope (preventing a race on the same observation row); disjoint groups run concurrently. Lock acquisition follows a total order, specifically to be deadlock-free.

engine/consolidation/consolidator.py · fetch and group (excerpt)python
memories = await conn.fetch(f"""
    SELECT id, text, fact_type, ..., observation_scopes
    FROM memory_units
    WHERE bank_id = $1
      AND consolidated_at IS NULL
      AND consolidation_failed_at IS NULL
      AND fact_type IN ('experience', 'world')
    ORDER BY created_at ASC
    LIMIT ${limit_idx}""", *fetch_params)
if not memories:
    break

# Group by exact tag set -- security requirement: facts with different tags
# must never share one LLM call.
tag_groups: dict[tuple[str, ...], list[dict]] = {}
for m in memories:
    tag_key = tuple(sorted(m.get("tags") or []))
    tag_groups.setdefault(tag_key, []).append(dict(m))

Inside each LLM batch: ① recall related observations per fact in parallel (it reuses recall, but limited to fact_type=["observation"], tags_match="all_strict", reranking="interleave"); ② union + dedup across the batch; ③ one LLM call over N facts + those observations; ④ execute the write actions sequentially (writes must be serial for consistency). Execution order is delete first (free observation slots) then update then create. Failure handling uses adaptive bisection: a failed batch is halved and retried down to a single fact; only a single-fact failure gets stamped consolidation_failed_at.

A few processing rules are especially worth remembering (they target exactly where models misbehave):

RuleGist
prefer UPDATE over CREATEif the new facts describe the same canonical event/claim an existing observation already covers, update it and attach the new facts as evidence; don't create a near-duplicate sibling. “One canonical observation with many source facts is always better than many siblings with one source fact each.”
one observation per faceta count, an entity, a relation — never merged.
state changes update“sold X”, “X died”, “moved to Y” → update the matching observation to the current state.
preserve historyobservations recording significant events are important history — never delete them; be very conservative with deletes.
no computation“you don't have the full picture — never calculate, derive, or adjust numeric values. If the user says ‘I have 2 dogs’ then ‘I have a dog named Rex’, don't change the count to 3 — you don't know if Rex is one of the 2.”

The output is {"creates":[...], "updates":[...], "deletes":[...]}; every action must carry a reason (“for a CREATE, state which existing observations you considered and why none matched — this is audited to catch duplicate creates”). And at most one UPDATE per observation_id (several would silently overwrite each other).

💡 The model isn't trusted, so there are deterministic guard rails

After the LLM there are several deterministic defenses: _dedupe_updates collapses multiple updates to the same observation_id; an exact-text guard drops CREATEs whose text verbatim reproduces an observation already shown (because “the model intermittently does exactly this”); and optional semantic dedup (when threshold < 1.0) probes each CREATE/UPDATE against its top-5 in-scope neighbors and uses a focused second LLM call to adjudicate merge-vs-keep.

📖 Why consolidation uses interleave reranking

Consolidation's observation recall uses reranking="interleave" (ch08). The reason is measured and written in the comment: the cross-encoder demotes the near-identical “twin” observation from semantic #1 to reranked #37, and RRF pushes it outside the 512-token budget — so the model never sees it and creates a duplicate. Interleave guarantees each arm's top gets a slot, so the twin is always shown and the model UPDATEs instead of CREATEs.

5. Update vs recreate, and invalidation

UPDATE mutates in place — rewrites the observation's text and embedding, extends provenance, merges fields — never recreated from scratch. Two notes: tags are unioned, not replaced (so every contributor keeps visibility); temporal fields aggregate (earliest start, latest end, latest mentioned). Each update first snapshots the prior state into the observation_history table, capped in row count — because a single JSONB column once grew past PostgreSQL's 256MB jsonb limit on a frequently-reinforced observation and got stuck.

⚠️ Invalidation = delete observation + reset consolidated_at

When underlying facts are deleted/replaced (document re-ingest, memory delete, tag change, clear observations), delete_stale_observations_for_memories will: ① delete observations referencing those facts (even one missing source makes its text stale); ② reset the surviving source facts' consolidated_at to NULL so they re-consolidate next round. That's the system's re-consolidation mechanism: delete + reset = put the facts back on the work queue. The reverse race (consolidation building from facts deleted mid-run) is closed by _filter_live_source_memories, which re-checks source ids FOR SHARE before every write.

6. Triggering and scheduling

  • Automatic after Retain: each fact insert calls _submit_post_insert_maintenance, gated by bank config enable_observations + enable_auto_consolidation. Failure is only logged, never raised — consolidation must not fail a retain.
  • Bank-level dedupe: on submit, if an unscoped pending op already exists for the bank, the existing operation_id is reused instead of queueing a duplicate (dedupe checks only pending, not processing — a processing task uses a watermark from when it started, so facts added after that still need a fresh run).
  • Worker claims it: a separate worker process polls async_operations every 500ms, with reserved slots for consolidation (default {"consolidation": 2}), guaranteeing it capacity without starving retains.
  • Manual / maintenance: POST /banks/{id}/consolidate, clearing a memory's observations, a maintenance reconcile that sweeps backlog.
  • Self re-queue: hitting the per-round memory budget re-submits the job — and this failure must propagate, else “the bank has backlog and no queued work — silently stuck”.
  • Downstream: on a completed final round, submit refresh tasks for tag-matching user mental models with refresh_after_consolidation.

Summary

  • Consolidation = bottom-up learning: facts → observation (a special fact); decoupled from retain (no full set, expensive, re-runnable).
  • The work queue is a SQL predicate; group by exact tag set (security); per batch “parallel recall → one LLM → sequential writes”; delete before create.
  • Policy core: prefer UPDATE; no computation; layered defenses against the model; tags are a security boundary.
  • Invalidation = delete observation + reset consolidated_at = re-consolidation.
