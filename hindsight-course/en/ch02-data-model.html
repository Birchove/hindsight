Part 1 · Understanding the System

02 · The Data Model: What a Memory Looks Like

Every later chapter reads and writes the same handful of tables. This chapter lays the foundation: which tables exist, how they relate, what “one fact” actually looks like on disk, how vectors are stored, and how multi-tenancy is isolated. Read this and none of the later SQL will be foreign.

Chapter takeaways

  • The heart of memory is the memory_units table — one row = one atomic fact; it also carries the embedding, the BM25 search vector, the temporal fields, and the consolidation bookkeeping.
  • The graph is entities + unit_entities (fact↔entity) and memory_links (the three fact↔fact edge types).
  • Observations are not a separate table — they are memory_units rows with fact_type='observation'. Don't confuse them with the mental_models table (renamed several times).
  • Vectors use pgvector (384-dim, HNSW cosine); at HEAD there is one partial index per (bank, fact_type).
  • Multi-tenancy = one schema per tenant + search_path; at runtime a contextvar + fq_table() fully-qualifies every table; banks are isolated by WHERE bank_id = ….

⚠️ Heads-up first: models.py is not the whole truth

The SQLAlchemy ORM (models.py) defines only 7 tables and a subset of columns; the running engine executes hand-written asyncpg SQL (engine/db/ops_postgresql.py, ~59KB) against a real schema of ~20 tables and many more columns (search vectors, tags, consolidation bookkeeping). The authoritative sources are the Alembic migrations (~89 of them) plus that hand-written SQL. The ORM lags the real schema (e.g. Bank still shows the since-renamed background column). When reading the schema, trust the migrations and ops_postgresql.py.

Fig 2-1: core relations. Note an observation's link to its source facts is a UUID[] array (a soft reference), not a foreign key; and on PG, banks are mostly not FK-referenced by their data tables — isolation is logical via the bank_id column.
  • bank → documents / memory_units / entities: 1∶N (every row carries bank_id).
  • document → chunks: 1∶N via composite FK (document_id, bank_id), ON DELETE CASCADE.
  • chunk → memory_units: 1∶N but ON DELETE SET NULL — deleting a chunk orphans facts rather than destroying them.
  • memory_unit ↔ entity: M∶N through unit_entities, composite PK, both sides CASCADE.
  • memory_unit ↔ memory_unit: M∶N directed through memory_links, 4-column PK (from_unit_id, to_unit_id, link_type, entity_id) — the same pair can carry one edge of each type.
  • observation → source facts: not a FK — a source_memory_ids UUID[] array column, queried with array operators.

3. memory_units: the anatomy of a fact

This is the most important table in the system. Grouping its fields by purpose:

    sa.Column("document_id", sa.Text(), nullable=True),

    sa.Column("occurred_start", ...), sa.Column("occurred_end", ...),
    sa.Column("mentioned_at", ...),
    sa.Column("fact_type", sa.Text(), server_default="world", nullable=False),

)

#   fact_type IN ('world', 'experience', 'observation')

📖 Why four timestamp fields?

Because the temporal semantics of a memory are genuinely multi-dimensional: when an event happened (occurred_start/end), when it was mentioned (mentioned_at), plus a fallback event_date. Temporal retrieval (ch07) matches a window against both occurred_* and mentioned_at — “what happened in June” and “what did we talk about in June” are different questions.

⚠️ chunk_id is deterministic, not a UUID

chunk_id = f"{bank_id}_{document_id}_{chunk_index}" (chunk_storage.py). Inserts are idempotent upserts — re-submitting the same document_id yields the same chunk_ids, and overwriting is the correct behavior. This is also why chunking must be idempotent (ch04): a chunk_index collision would hit the PK directly.

4. entities / unit_entities / memory_links

initial_schema.py · entities unique index + memory_links constraints (excerpt)python
# entities: unique per (bank, lowercased canonical name) -- "Paris" and "paris" are one entity
op.execute("CREATE UNIQUE INDEX idx_entities_bank_lower_name "
           "ON entities (bank_id, LOWER(canonical_name))")

# memory_links: type and weight constraints
CheckConstraint(
  "link_type IN ('temporal','semantic','entity','causes','caused_by','enables','prevents')")
CheckConstraint("weight >= 0.0 AND weight <= 1.0")

# uniqueness: the nullable entity_id is replaced by a nil-UUID so it fits a unique index
op.execute("CREATE UNIQUE INDEX idx_memory_links_unique ON memory_links "
  "(from_unit_id, to_unit_id, link_type, "
  " COALESCE(entity_id, '00000000-0000-0000-0000-000000000000'::uuid))")

⚠️ The memory_links FKs are DEFERRABLE

The from_unit_id/to_unit_id foreign keys are DEFERRABLE INITIALLY DEFERRED, to break an insert-vs-cascade-delete deadlock. The cost is that the link inserter can't rely on a WHERE EXISTS guard and instead locks the parent units FOR KEY SHARE inside the same statement (seen in ch05). Also, although the CHECK still lists 'entity', that's only for historical rows — Retain no longer writes entity edges.

5. Observations are not a separate table (terminology trap)

There is no observations table on PostgreSQL. A consolidated observation is a memory_units row with fact_type='observation', using the observation-only fields (proof_count, source_memory_ids, history, observation_scopes).

⚠️ The term “mental model” has meant three things — read the migrations, not the names

This word has historically referred to three different things:
(a) a fact_type in memory_units, later renamed to 'observation' by t5o6p7q8r9s0;
(b) a standalone mental_models v4 table, later dropped entirely by p1k2l3m4n5o6;
(c) the current mental_models table, which is actually reflections ← pinned_reflections renamed, storing reflect results (subtypes directive/pinned).
So CLAUDE.md's “mental models = consolidated knowledge” maps, at HEAD, to the fact_type='observation' rows — not the mental_models table. This is exactly why ch01 insists “observation ≠ mental model”.

6. pgvector: how vectors are stored and indexed

  • Column: memory_units.embedding, type vector(384). The dimension 384 is a module constant (DEFAULT_EMBEDDING_DIMENSION), not configurable per bank — when a model change alters the dimension, the system recomputes rather than storing mixed dimensions (the archive table invalidated_memory_units deliberately has no embedding column, so an “archive vector” can't fall out of sync with the live model, #2209).
  • Index: HNSW + cosine (vector_cosine_ops). The vector backend is pluggable (pgvector / pgvectorscale diskann / vchord / scann), mapped by _vector_index.py's _INDEX_USING_CLAUSES:
_vector_index.py · _INDEX_USING_CLAUSESpython
_INDEX_USING_CLAUSES = {
    "pgvector":      "USING hnsw (embedding vector_cosine_ops)",
    "pgvectorscale": "USING diskann (embedding vector_cosine_ops) WITH (num_neighbors = 50)",
    "pg_diskann":    "USING diskann (embedding vector_cosine_ops) WITH (max_neighbors = 50)",
    "vchord":        "USING vchordrq (embedding vector_cosine_ops)",
    "scann":         "USING scann (embedding cosine) WITH (mode = 'AUTO')",
}

💡 At HEAD: the global index is gone — replaced by per-(bank, fact_type) partial indexes

Early on there was a single global HNSW index. Migration d5e6f7a8b9c0 dropped it in favor of three partial indexes per bank: idx_mu_emb_{worl|expr|obsv}_{first 16 hex of internal_id}. Why? Because retrieval SQL always carries WHERE bank_id = … AND fact_type = … before ORDER BY embedding <=> …; the partial index lets the planner go straight to the small index instead of being out-competed by the global one. The index name uses internal_id rather than bank_id so names stay stable and within PostgreSQL's 63-character identifier limit. Recall's per-fact_type UNION ALL arms (ch07) exist precisely to hit these partial indexes.

7. Full-text search (BM25) storage

Parallel to vectors, memory_units also has a search_vector column. The default backend is native tsvector:

initial_schema.py · the generated full-text columnsql
ALTER TABLE memory_units
ADD COLUMN search_vector tsvector
GENERATED ALWAYS AS (
  to_tsvector('english', COALESCE(text, '') || ' ' || COALESCE(context, ''))
) STORED;

But the type of search_vector varies by backend: native → a generated tsvector; pg_textsearch/pg_search → a dummy TEXT column with indexes on the base columns; vchord → bm25_catalog.bm25vector. So runtime inserts branch by backend (and BM25 retrieval in ch07 uses this column too).

Fig 2-2: three layers of isolation. The schema gives physical isolation, fq_table gives runtime qualification, and bank_id gives logical isolation within a schema.
engine/schema.py · fq_tablepython
def fq_table(table_name: str) -> str:
    if _is_oracle():
        return table_name              # Oracle uses ALTER SESSION SET CURRENT_SCHEMA
    from .memory_engine import get_current_schema
    return f"{get_current_schema()}.{table_name}"   # PG: schema.table

Key points: the migration tree runs once per tenant schema (hindsight-admin run-db-migration --schema tenant_xyz); the current schema lives in a contextvar, set after tenant authentication; all raw SQL fully-qualifies via fq_table(). Banks, by contrast, are isolated not by FK or row-level security but by a WHERE bank_id = $n on every query — on PG the data tables have no foreign key to banks at all (the Oracle baseline is stricter and adds ON DELETE CASCADE bank FKs).

Summary

  • The central table is memory_units (one row per fact), holding the embedding, search_vector, four timestamps, and consolidation bookkeeping.
  • The graph = entities + unit_entities + memory_links (three edge types; nullable column via nil-UUID; deferrable FKs).
  • An observation is a fact_type='observation' row, not a separate table; don't conflate with the mental_models table.
  • Vectors: pgvector 384-dim HNSW; at HEAD, one partial index per (bank, fact_type); full-text search runs in parallel.
  • Multi-tenancy in three layers: schema/search_path + contextvar/fq_table + bank_id WHERE.
