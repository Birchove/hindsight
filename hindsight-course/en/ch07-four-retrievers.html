Part 3 · Retrieval (Recall)

07 · The Four Retrievers

Last chapter saw the pipeline skeleton. This one opens each path up: how semantic walks the vectors, how BM25 does full-text, how graph expands from seeds, how temporal does “entry + spreading”. Each path has a detail worth remembering — HNSW over-fetch, the graph's additive scoring, and the counter-intuitive choice to rank temporal entry points by similarity rather than by time.

Chapter takeaways

  • All four paths read memory_units, all filter by bank_id + fact_type + tags, all return list[RetrievalResult].
  • Semantic: one UNION ALL arm per fact_type to hit the partial indexes; HNSW is approximate, so it over-fetches 5× then trims in Python.
  • BM25: default native tsvector + ts_rank_cd; if the query has no tokens, the whole path is skipped.
  • Graph: not multi-hop BFS — “one SQL round trip from semantic seeds, expanded through three link signals”, scored by summing across signals to reward convergent evidence.
  • Temporal: first pick “entry points” (by similarity, covering the whole window), then spreading activation along temporal/causal edges (this step is the BFS-like one).

1. Semantic path: vector similarity

Locate: SQL built by engine/sql/postgresql.py's build_semantic_arm; executed in search/retrieval.py's retrieve_semantic_bm25_combined.

Similarity uses pgvector's cosine-distance operator <=>, expressed as 1 - distance:

engine/sql/postgresql.py · build_semantic_arm (excerpt)sql
(SELECT {cols},
        1 - (embedding <=> $q::vector) AS similarity,
        NULL::float AS bm25_score,
        'semantic' AS source
 FROM memory_units
 WHERE bank_id = $b
   AND fact_type = 'world'              -- one arm per fact_type
   AND embedding IS NOT NULL
   AND (1 - (embedding <=> $q::vector)) >= {min_similarity}   -- default 0.3
 ORDER BY embedding <=> $q::vector
 LIMIT {fetch_limit})

💡 Two key design choices

(1) One UNION ALL arm per fact_type rather than one big query with a window function ROW_NUMBER() PARTITION BY fact_type. Why? Because with the fact_type = '...' filter the planner walks the per-fact_type partial HNSW index (the idx_mu_emb_* from ch02); the window-function form used to force a full sequential scan.
(2) HNSW over-fetch: HNSW is approximate nearest neighbor, so a plain LIMIT k can miss the truly good results. So each arm fetches hnsw_fetch = max(limit*5, 100), over-fetching 5× and trimming back to limit in Python. At connection init ef_search=200 is also set to improve recall.

✅ Bonus: semantic results are reused by the graph path

If the semantic threshold ≤ graph_seed_min_similarity, the ordered semantic rows double as the graph retrieval's entry seeds (capped at 20), saving the graph path from doing another ANN query. This is the concrete form of ch06's “graph depends on semantic”.

2. Keyword path: BM25 / full-text

Locate: build_bm25_arm (same file).

The default backend is native tsvector, ranking with ts_rank_cd and gating matches with @@:

engine/sql/postgresql.py · build_bm25_arm native branch (excerpt)sql
(SELECT {cols},
        NULL::float AS similarity,
        ts_rank_cd(search_vector, to_tsquery('english', $text)) AS bm25_score,
        'bm25' AS source
 FROM memory_units
 WHERE bank_id = $b AND fact_type = 'world'
   AND search_vector @@ to_tsquery('english', $text)   -- the match gate
 ORDER BY bm25_score DESC
 LIMIT {limit})

Query terms are joined with | (OR) by prepare_bm25_text. Key points:

  • No tokens → the whole path is skipped: tokenize_query strips punctuation and splits on whitespace; a purely symbolic query yields no tokens, so no BM25 arms are generated at all (which also changes the bind-parameter layout).
  • The backend is swappable: besides native tsvector it supports pg_search (ParadeDB), pgroonga, vchord, pg_textsearch. _pg_search.py is only a ParadeDB index-DDL helper, not on the query path.
  • Oracle fallback: if CONTAINS errors because the index isn't synced, the whole query is rebuilt as semantic-only.

3. Graph path: link expansion

Locate: search/link_expansion_retrieval.py's LinkExpansionRetriever (the default graph retriever).

📖 It is not multi-hop BFS

The name has “expansion” in it, so it's tempting to picture “a graph traversal expanding layer by layer”. In reality it is a bounded, single-SQL-round-trip expansion: starting from the semantic seeds, it finds neighbors through the three link signals that were built at Retain time. Those three signals were bounded in size at write time, so no deep traversal is needed at query time.

Three link signals, each a CTE, finally UNION ALL-ed into one query on one connection:

SignalSourceScore
entityquery-time self-join on unit_entities (shared entities)COUNT(DISTINCT entity_id), with a LATERAL per-entity cap of 200
semanticthe precomputed kNN graph (memory_links with link_type='semantic'), checked both directions (the graph isn't symmetric)MAX(weight)
causalcauses/caused_by/enables/preventsweight (boosted as the highest-quality signal)
engine/db/ops_postgresql.py · entity expansion CTE (excerpt)sql
entity_expanded AS (
  SELECT mu.id, ...,
         COUNT(DISTINCT se.entity_id)::float AS score,   -- number of shared entities
         'entity'::text AS source
  FROM seed_entities se
  CROSS JOIN LATERAL (
      SELECT ue_target.unit_id
      FROM unit_entities ue_target
      WHERE ue_target.entity_id = se.entity_id
        AND ue_target.unit_id != ALL($1::uuid[])          -- exclude the seeds themselves
        AND EXISTS (SELECT 1 FROM memory_units mu_target
                    WHERE mu_target.id = ue_target.unit_id
                      AND mu_target.fact_type = $2)        -- filter before capping
      ORDER BY ue_target.unit_id DESC
      LIMIT 200                                            -- per-entity cap
  ) t
  JOIN memory_units mu ON mu.id = t.unit_id
  GROUP BY mu.id
  ORDER BY score DESC
  LIMIT $3
)

Additive scoring: reward convergent evidence

A fact may be hit by several signals at once. On merge the scores are summed across signals (total lands in [0,3]):

  • entity → tanh(shared_count × 0.5) (1 shared → 0.46, 2 → 0.76, saturating);
  • semantic → max link weight;
  • causal → max link weight.

💡 Why sum rather than take the max?

If a fact both shares entities with the query and has a semantic edge and a causal edge, its evidence is “convergent” and it should rank above something that only hit one path. Summation lets that multi-evidence accumulate. The final summed score is stored in RetrievalResult.activation — and note it must be the summed score, not a single-signal score, or cross-fact_type ordering would disagree with within-graph ordering.

⚠️ Timeout degradation and the observation special path

The whole graph query is wrapped in asyncio.wait_for(timeout=10s); on timeout it degrades to semantic + causal only (drops the expensive entity self-join). Also, observations have no direct entity links, so they take a separate _expand_observations: via source_memory_ids → world facts → entities → other world facts → their observations.

4. Temporal path: entry points + spreading activation

Locate: search/retrieval.py's retrieve_temporal_combined. Runs only when query analysis found a temporal constraint.

Two phases:

Phase one: pick entry points (by similarity, not by time!)

One “similarity-ranked + window-filtered” arm per fact_type, first pulling a pool (_TEMPORAL_POOL_SIZE = 60), then narrowing to _TEMPORAL_ENTRY_POINTS = 10 per fact_type — and those 10 must cover the whole window (round-robin across 8 time buckets, so they don't all cluster at one end):

search/retrieval.py · one temporal entry-point arm (excerpt)sql
(SELECT {pool_cols}, 1 - (embedding <=> $1::vector) AS similarity
 FROM memory_units
 WHERE bank_id = $2 AND fact_type = 'world' AND embedding IS NOT NULL
   AND (   -- window match: occurred range or mentioned_at within [start,end]
        (occurred_start IS NOT NULL AND occurred_end IS NOT NULL
         AND occurred_start <= $4 AND occurred_end >= $3)
     OR (mentioned_at IS NOT NULL AND mentioned_at BETWEEN $3 AND $4)
     OR (occurred_start IS NOT NULL AND occurred_start BETWEEN $3 AND $4)
     OR (occurred_end   IS NOT NULL AND occurred_end   BETWEEN $3 AND $4))
   AND (1 - (embedding <=> $1::vector)) >= $5      -- default 0.1
 ORDER BY embedding <=> $1::vector
 LIMIT 60)

💡 Why “rank by similarity” rather than “rank by recency”?

An earlier version ranked entry points by date, which biased results toward the end of the window; and on banks with dense/uniform dates it degenerated into “a near-random sample + a full scan + a disk-spilling sort” — 30+ seconds on a 660k-row bank. Switching to ranking by similarity (via the ANN index) + using buckets to guarantee time coverage is both fast and balanced.

Phase two: spreading activation (this step is the BFS-like one)

From the entry points, a bounded multi-hop expansion along temporal/causal edges (frontier + visited set + budget, max_iterations=5):

search/retrieval.py · one spreading hop (excerpt)sql
SELECT src.from_unit_id, mu.id, ..., l.weight, l.link_type,
       1 - (mu.embedding <=> $1::vector) AS similarity
FROM unnest($2::uuid[]) AS src(from_unit_id)
CROSS JOIN LATERAL (
    SELECT ml.to_unit_id, ml.weight, ml.link_type
    FROM memory_links ml
    WHERE ml.from_unit_id = src.from_unit_id
      AND ml.link_type IN ('temporal','causes','caused_by','enables','prevents')
      AND ml.weight >= 0.1
    ORDER BY ml.weight DESC
    LIMIT $5
) l
JOIN memory_units mu ON mu.id = l.to_unit_id
WHERE mu.bank_id = $6 AND mu.fact_type = $3 AND mu.embedding IS NOT NULL
  AND (1 - (mu.embedding <=> $1::vector)) >= $4

Each neighbor gets a temporal_proximity (1.0 at the window midpoint → 0.0 at the edges) and a propagated score = parent score × edge weight × causal boost × 0.7 (causal boost: causes/caused_by = 2.0, enables/prevents = 1.5). Take max(proximity, propagated); neighbors above 0.2 re-enter the frontier.

⚠️ Spreading is skipped on Oracle

Spreading uses unnest / LATERAL, which Oracle has no equivalent for, so on Oracle spreading is skipped (but entry points still return). When temporal results are empty they're normalized to None (meaning “no temporal path”), distinct from [].

Summary

  • Semantic: per-fact_type arms hit the partial indexes; HNSW over-fetches 5× then trims; gate 0.3; results reusable as graph seeds.
  • BM25: native tsvector + ts_rank_cd; no tokens → skipped; swappable backend; Oracle fallback to semantic-only.
  • Graph: bounded single-SQL expansion, three link signals (entity/semantic/causal) with additive scoring; timeout degrades; observations take a detour.
  • Temporal: entry points chosen by similarity (buckets cover the window) + spreading activation along temporal/causal edges; Oracle skips spreading.

Each path hands back a ranked list. Next we see how they're fused (RRF), reranked (cross-encoder), and finally trimmed to a token budget for the answer.
