Part 2 · Writing — Retain

03 · Retain End-to-End

Retain is the write path. In this chapter we follow one of the most common requests (text JSON, synchronous, no delta hit) from HTTP all the way to storage, wiring the three code layers together, and explain the seemingly over-engineered streaming mini-batch + staged transactions backbone. The two finer pieces — fact extraction/chunking and entities/edges — are left to chapters 04 and 05.

Chapter takeaways

  • Retain is not “store the raw text and embed it” — it turns text into atomic facts + entities + three edge types, pre-building the structure that Recall's four arms depend on.
  • A request passes three layers: api_retain (translate & route) → retain_batch_async (guardrails & batching) → orchestrator.retain_batch (the real orchestration).
  • The main execution path is streaming mini-batch: pre-chunk the whole document, then per batch “extract → build edges → commit → free”; even small docs go this way (just one batch).
  • Correctness rests on document-level content_hash + chunk-level hash + FOR UPDATE; delta retain is “optimistic read + in-transaction recheck”.
  • Sync/async are two paths; async uses operation_id for idempotency, and an oversized single item is not split into concurrent siblings but sliced sequentially inside the process.

💡 Almost all the complexity comes from three trade-offs

Recall the three trade-offs from chapter 01 — Retain is where they concentrate most: LLM slow & costly ↔ writes fast & recoverable (→ streaming, delta, async); retrieval needs precomputed structure ↔ computing that structure can fail (→ Phase1/2/3); concurrent multi-tenancy ↔ per-document consistency (→ content_hash, FOR UPDATE, sequential slicing per document). Reading this chapter with those in mind makes it flow.

2. Layer one: HTTP only “translates & routes”

Locate: api/http.py → api_retain (the request-body models are RetainRequest / MemoryItem in the same file).

This layer calls no LLM and writes no business tables. It does just three things:

  1. Collapses each MemoryItem into the engine's internal content_dict (timestamp → event_date, the string "unset" → None, etc.).
  2. Groups by item.strategy — one request may carry several strategies, but each must enter the engine separately.
  3. async=false → calls retain_batch_async (synchronous); async=true → calls submit_async_retain (enqueues async).

💡 Why group by strategy at the HTTP layer?

Because the engine's internal apply_strategy applies one resolved config to the whole batch. If you mixed conversations (chat) and documents (long docs) into one retain_batch, only one config could apply and the extraction rules / chunk size would be wrong. So mixed strategies must be split at HTTP. Also, when an operation_id (idempotency key) is present, exactly one strategy group is required, else the idempotency semantics are unclear → 400.

3. Layer two: the Engine facade & guardrails

Locate: engine/memory_engine.py → retain_batch_async (the public entry) → _retain_batch_async_internal (config prep right before the orchestrator); batching in _split_contents_into_sub_batches. Jump by function name only.

The facade centralizes a bunch of cross-cutting concerns so the retain/ package can stay focused on “extract + write”. In order it does:

  1. Tenant auth, optional OperationValidator (quota checks, rewriting contents).
  2. Deep-copy contents — because the orchestrator will later pop("content") in place to save memory, and mustn't mutate the caller's object.
  3. sanitize_text: strip bad Unicode that would crash the embedder (lone surrogates, etc.; source cites issue #1875).
  4. Validation: no duplicate document_id in one batch; append mode requires a document_id and document-text storage enabled.
  5. Split into sub-batches by token budget (when oversized); when one document is sliced into several pieces, compute chunk_index_offset (guarding against issue #1888's chunk-number collision).
  6. _retain_batch_async_internal: resolve_full_config (hierarchical config) → (optional) force chunks mode → apply_strategy → call orchestrator.retain_batch.

⚠️ The engine mutates dicts in place, so the entry must copy

This is an invariant that runs through the whole codebase: to save memory the orchestrator will pop("content") and clear large strings. If the facade didn't deep-copy first, the caller's data would be “stolen”. Anywhere you hand data to retain/, assume it will be mutated in place.

💡 Why is the Engine so “thick”?

Security, billing, config hierarchy, async enqueue — these cross-cutting concerns are concentrated in one place so the business pipeline (retain/) stays pure. The cost is the 14k-line monolith memory_engine.py — which is exactly why it can only be read by jumping to functions; never try to read it through.

4. Layer three: the orchestrator's per-document backbone

Locate: engine/retain/orchestrator.py → retain_batch.

Once inside the pipeline, it first handles “document-level” concerns, then enters the chunk loop:

flowchart TD A[fetch bank profile / narrator] --> B{multiple document_id?} B -->|yes| C[recurse retain_batch per document] B -->|no| D[Memory Defense screening] D --> E[resolve effective_doc_id] E --> F{update_mode = append?} F -->|yes| G[read old original_text, prepend it] F -->|no| H[stale-request check] G --> H H --> I{_try_delta_retain} I -->|hit| Z[return directly] I -->|miss| J[chunk_text pre-splits all chunks] J --> K[_streaming_retain_batch]
Fig 3-2: the per-document backbone of retain_batch. A few “whys” follow.

Narrator (first-person resolution)

_resolve_narrator: the extraction prompt can inject “Narrator: <name>” to help the model resolve the first person (“who is ‘I’?”). But when a bank is auto-created it often has name == bank_id, and bank_id is frequently a routing key (like agent::channel::user). Injecting that would write the routing key into the fact text and pollute later observations — so in that case it injects nothing (issue #1680).

Memory Defense (pre-write screening)

Before extracting facts, sensitive content is screened into one of ALLOW / REDACT / BLOCK. If everything is BLOCK, it raises MemoryDefenseAllBlockedError → HTTP 422. Locate: the front of retain_batch + extensions/memory_defense.py.

Append is not “only insert new facts”

In update_mode == "append", the system reads the already-stored document text and rebuilds the full document, then runs the rest of the flow (which usually hits delta and skips the unchanged prefix chunks). Reading the text: fact_storage.get_document_content. The design is counter-intuitive at first — why re-read the whole thing for an “append”? Because facts are extracted from context, and looking at only the new fragment would extract them wrong.

Stale-request (skip outdated requests)

If the document's updated_at is already newer than “this request's start time”, skip it directly, so a late, stale request can't overwrite a newer session. Note: this is only an optimization — real correctness relies on FOR UPDATE + hash checks inside the transaction (the comments say so explicitly).

5. Streaming mini-batch: the main execution path

Even a small document goes this way (usually just one mini-batch). The source comment is blunt: this is to avoid maintaining two code paths (one for small docs, one for large) that would drift in behavior.

⚠️ Extraction failure must be loud (issue #1833)

If extraction fails but returns an empty list and still marks the operation completed, the document lands with 0 facts and the UI shows “success” — the memory is silently lost, and nobody knows. So exhausted retries, protocol errors, etc. must raise, letting the caller mark failure / retry — never pretend success. An important design principle: better to fail and retry than to silently drop data.

💡 Why document tracking is moved into the first write transaction

The “delete old document record, insert new” action is deliberately moved into the first write transaction, locking with SELECT … FOR UPDATE. Why? If you “delete the document first, then call the LLM to extract facts”, there's a window in between where a concurrent request can sneak in and cause duplicates. Putting the delete and the subsequent writes in one transaction + a row lock closes that concurrency hole.

6. Recoverability: streaming & delta

Why streaming (and not “do it all at once”)

A large document (the comments mention 17k+ chunks) done as one extract → embed → write would have unacceptable memory peak and failure cost: either OOM, or one failure throws the whole document away. Streaming reduces the failure granularity to “one mini-batch” and bounds the memory peak.

Delta retain (incremental): spend less, stay correct

Locate: orchestrator._try_delta_retain, _classify_chunk_diff, _delta_metadata_only.

When the same document_id is upserted repeatedly (e.g. a chat session keeps growing), re-extracting the whole thing every time makes LLM cost and latency explode. Delta re-extracts only the changed chunks:

flowchart TD A[lock-free read existing chunks] --> B[classify by content_hash:
unchanged / changed / new / removed] B --> C[open write txn, FOR UPDATE] C --> D{content_hash still consistent?} D -->|yes| E[process only changed chunks] D -->|no| F[abandon delta -> fall back to full streaming]
Fig 3-5: delta = “optimistic read + in-transaction recheck”. First diff lock-free (cheap, fast, no long read holding a connection); right before writing, lock with FOR UPDATE and recheck the content_hash; if a concurrent request changed it in between, abandon delta and fall back to the fully-lock-protected streaming path.

📖 Pattern name: optimistic read + in-transaction recheck

First read the old data without locking and diff it (cheap, fast); then when actually writing, in a short transaction use FOR UPDATE to lock and recheck the content_hash. If someone changed it in the gap, abandon the increment and fall back to full streaming (which is lock-protected throughout). append and delta are partners: append first rebuilds the full document, then enters delta, so the unchanged prefix chunks are mostly skipped.

7. The async path: parent/child & idempotency

Locate: memory_engine.submit_async_retain, _handle_batch_retain, _split_contents_into_async_children.

oversized single item not fragmented Child --> Worker: poller claims Worker --> Retain: retain_batch_async Retain --> Seq: oversized item sliced sequentially in-process Seq --> [*]: chunk_index_offset increments
Fig 3-6: the async path. The parent is a state aggregator; children carry the task body; an oversized single item isn't split into concurrent siblings but sliced sequentially within one worker.

💡 Why operation_id idempotency?

On a client timeout-retry, the same UUID should “return the original operation, not enqueue again”. The comment stresses: the idempotency read is deliberately not in the same transaction as creation; real mutual exclusion relies on primary-key uniqueness, with a unique-violation as the backstop. So even if two requests arrive at once, only one insert succeeds.

💡 Why isn't an oversized single item split into “concurrent sibling children”? (issue #1795)

Because there is no per-document serialization across workers. If several children share one document_id and each thinks it's is_first_batch, they'd cascade-delete each other's written units; the final ANN link-insert would also hit foreign keys and exhaust the connection pool. So: an oversized item becomes one whole child, sliced sequentially inside the worker process, with chunk_index_offset continuing the chunk_index (issue #1888); document_body_override ensures the stored text is the full document, not the last slice (issue #1838).

⚠️ Why does the parent often have no task_payload?

The parent is a state aggregator (summarizing all children's progress); only children carry the real task body. The two must be created in the same transaction, else you get an “orphan parent” that is never executed while the queue metric keeps climbing.

8. Wrap-up & return

  • _run_final_semantic_ann (Phase3): after all batches commit, do one full semantic-neighbor top-up. Failure must not roll back the written facts — edges are an enhancement, not the memory body (chapter 05).
  • Returns (per-content unit_id list, TokenUsage, processed_content_tokens); the HTTP layer aggregates usage into a RetainResponse.
  • Observations are not built yet: retain only writes observation_scopes onto the facts; the real merge happens in post-hoc consolidation (chapter 09).

Summary

  • Retain in three layers: api_retain (translate & route) → retain_batch_async (guardrails & batching) → orchestrator.retain_batch (orchestration).
  • The main path is streaming mini-batch: pre-chunk everything → per batch “extract → Phase1 → Phase2 → commit → free”.
  • Correctness trio: document-level content_hash, chunk-level hash, FOR UPDATE row locks; delta is “optimistic read + in-transaction recheck”.
  • Async uses operation_id for idempotency; oversized single items are sliced in-process, not into concurrent siblings.
  • Core principle: fail loudly, never silently lose data.
