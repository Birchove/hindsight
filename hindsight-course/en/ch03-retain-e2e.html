Part 2 · Writing (Retain)

03 · Retain End-to-End

Retain is the write path. This chapter follows one typical request (text JSON, synchronous, no delta hit) from HTTP all the way to storage, threading the three code layers together, and explains the seemingly over-engineered streaming mini-batch + phased-transaction skeleton. The two finer pieces — fact extraction/chunking, and entities/edges — get their own chapters (04, 05).

Chapter takeaways

  • Retain does not “store the text then embed it” — it turns text into atomic facts + entities + three edge types, pre-building the structure Recall's four paths rely on.
  • A request crosses three layers: api_retain (translate & route) → retain_batch_async (guards & batching) → orchestrator.retain_batch (real orchestration).
  • The main execution path is the streaming mini-batch: chunk everything up front, then per mini-batch “extract → build edges → commit → release”; small documents use the same path (one batch).
  • Correctness rests on document-level content_hash + chunk-level hash + FOR UPDATE; the delta path is “optimistic read + in-transaction recheck”.
  • Sync and async paths both exist; async uses operation_id for idempotency, and an oversized single item is not split into concurrent siblings but sliced sequentially in-process.

💡 Almost all the complexity comes from three trade-offs

Recall the three trade-offs from ch01; Retain is where they concentrate most: LLM slow & costly ↔ writes fast & recoverable (→ streaming, delta, async); retrieval needs precomputed structure ↔ computing it can fail (→ Phase1/2/3); concurrent multi-tenancy ↔ per-document consistency (→ content_hash, FOR UPDATE, sequential slicing within a document). Read this chapter with them in mind.

2. Layer one: HTTP only “translates & routes”

Locate: api/http.py → api_retain (request models are RetainRequest / MemoryItem in the same file).

This layer calls no LLM and writes no business tables. It does three things:

  1. Reduce each MemoryItem into the engine's internal content_dict (timestamp → event_date, the string "unset" → None, etc.).
  2. Group by item.strategy — one request may carry several strategies, but each must enter the engine separately.
  3. async=false → call retain_batch_async (sync); async=true → call submit_async_retain (enqueue).

💡 Why group by strategy at the HTTP layer?

Because the engine's apply_strategy applies one resolved config to a whole batch. If you mixed conversations (chat) and documents (long text) into one retain_batch, only one config could apply and the extraction rules / chunk size would be wrong. So mixed strategies must be split at HTTP. Also, when an operation_id (idempotency key) is present, only one strategy group is allowed, else the idempotency semantics are ambiguous → 400.

3. Layer two: the Engine facade and its guards

Locate: engine/memory_engine.py → retain_batch_async (public entry) → _retain_batch_async_internal (config prep before the orchestrator); splitting lives in _split_contents_into_sub_batches. Jump by function name only.

The facade concentrates a pile of cross-cutting concerns so the retain/ package can stay focused on “extract + write”. In order it does:

  1. Tenant auth, optional OperationValidator (quota checks, rewriting contents).
  2. Deep-copy the contents — because the orchestrator will pop("content") in place to save memory, and must not mutate the caller's object.
  3. sanitize_text: strip the bad Unicode that would crash the embedder (lone surrogates etc.; source cites issue #1875).
  4. Validation: no duplicate document_id within a batch; append mode requires a document_id and document-text storage enabled.
  5. Split into sub-batches by token budget (when oversized); when one document is split into several pieces, compute a chunk_index_offset (prevents the chunk-number collision of issue #1888).
  6. _retain_batch_async_internal: resolve_full_config (hierarchical config) → (optional) force chunks mode → apply_strategy → call orchestrator.retain_batch.

⚠️ The engine mutates dicts in place, so the entry must copy

This invariant runs through the whole codebase: to save memory the orchestrator will pop("content") and clear large strings. If the facade didn't deep-copy first, the caller's data would be “stolen”. Anywhere you hand data to retain/, assume it will be mutated in place.

💡 Why is the Engine so “thick”?

Security, billing, config hierarchy, and async enqueueing are centralized in one place so the business pipeline (retain/) stays pure. The price is the 14k-line memory_engine.py monolith — which is exactly why you only jump by function and never try to read it through.

4. Layer three: the orchestrator's document-level skeleton

Locate: engine/retain/orchestrator.py → retain_batch.

Once inside the pipeline, it handles “document-level” concerns first, then enters the chunk loop:

flowchart TD A[fetch bank profile / narrator] --> B{multiple document_id?} B -->|yes| C[recurse retain_batch per document] B -->|no| D[Memory Defense screening] D --> E[resolve effective_doc_id] E --> F{update_mode = append?} F -->|yes| G[read old original_text, prepend it] F -->|no| H[stale-request check] G --> H H --> I{_try_delta_retain} I -->|hit| Z[return directly] I -->|miss| J[chunk_text pre-chunks everything] J --> K[_streaming_retain_batch]
Fig 3-2: the document-level skeleton of retain_batch. The “why” of each box follows.

Narrator (first-person resolution)

_resolve_narrator: the extraction prompt can be injected with “Narrator: name” to help the model resolve the first person (“I” = whom?). But on auto-created banks name == bank_id, and bank_id is often a routing key like agent::channel::user. Injecting that would write the routing key into fact text and pollute later observations — so in that case it is not injected (issue #1680).

Memory Defense (pre-write screening)

Before extracting facts, screen for sensitive content, yielding ALLOW / REDACT / BLOCK. If everything is BLOCK, raise MemoryDefenseAllBlockedError → HTTP 422. Located in the front of retain_batch + extensions/memory_defense.py.

Append (it is not “just insert new facts”)

Under update_mode == "append", the system reads the already-stored document text and prepends it to form the full document, then continues (this usually hits the delta path, skipping unchanged prefix chunks). Reading the text: fact_storage.get_document_content. The design is counter-intuitive at first — why re-read the whole thing for an “append”? Because facts are extracted from context; extracting from only the new fragment would produce wrong facts.

Stale-request (skip outdated requests)

If the document's updated_at is already newer than “this request's start time”, skip it, so a late old request doesn't overwrite a newer session. Note: this is only an optimization; real correctness rests on FOR UPDATE + hash inside the transaction (the comment states this explicitly).

⚠️ Extraction failure must be loud (issue #1833)

If extraction fails but returns an empty list and the operation is marked completed, the document lands with 0 facts and the UI shows “success” — memory silently lost, and nobody knows. So exhausted-retry and protocol-error paths must raise, letting the upper layer mark it failed / retryable, never pretend success. A core principle: rather fail-and-retry than silently drop data.

💡 Why document tracking is moved into the first write transaction

The “delete old document record, insert new” action is deliberately moved into the first write transaction, locking with SELECT … FOR UPDATE. Why? If you “delete the document first, then call the LLM to extract”, there's a gap in which a concurrent request can sneak in and cause duplication. Putting the delete and the subsequent writes in one transaction + a row lock closes that concurrent hole.

6. Recoverability: streaming and delta

Why streaming (instead of doing it all at once)

A large document (the comments mention 17k+ chunks) extracted → embedded → written in one shot has unacceptable memory peaks and failure cost: either OOM, or one failure throws the whole document away. Streaming shrinks the failure granularity to “one mini-batch” and bounds the memory peak.

Delta retain (incremental): spend less, stay correct

Locate: orchestrator._try_delta_retain, _classify_chunk_diff, _delta_metadata_only.

When the same document_id is upserted repeatedly (a chat session growing longer), re-extracting the whole thing every time explodes LLM cost and latency. Delta re-extracts only the changed chunks:

flowchart TD A[read existing chunks without a lock] --> B[classify by content_hash:
unchanged / changed / new / removed] B --> C[open write transaction, FOR UPDATE] C --> D{content_hash still matches?} D -->|yes| E[process only changed chunks] D -->|no| F[abandon delta, fall back to full streaming]
Fig 3-5: delta = “optimistic read + in-transaction recheck”. Read old data without locking (cheap, fast) to diff; right before writing, recheck the hash under FOR UPDATE; if a concurrent request changed it in the meantime, fall back to the fully-locked full streaming path.

📖 Pattern name: optimistic read + in-transaction verification

Read the old data without a lock and diff (cheap, fast); then when truly writing, lock with FOR UPDATE in a short transaction and re-verify the content_hash. If someone changed it in the gap, abandon the increment and fall back to full streaming, which is lock-protected throughout. Append and delta are partners: append first assembles the full document, then enters delta, so the unchanged prefix chunks are mostly skipped.

7. The async path: parent/child and idempotency

Locate: memory_engine.submit_async_retain, _handle_batch_retain, _split_contents_into_async_children.

Fig 3-6: the async path. The parent is a status aggregator; children carry the task body; an oversized single item is not split into concurrent siblings but sliced sequentially within one worker.

💡 Why operation_id idempotency?

When a client retries on timeout, the same UUID should “return the original operation, not enqueue again”. The comment stresses: the idempotency read is deliberately not in the same transaction as creation; real mutual exclusion rests on primary-key uniqueness, with a unique-violation as the fallback. So even if two requests arrive at once, only one insert succeeds.

💡 Why not split an oversized item into concurrent sibling children? (issue #1795)

Because there is no per-document serialization across workers. If several children shared one document_id and each thought it was is_first_batch, they would cascade-delete each other's written units; and the final ANN edge-insert would hit foreign keys and saturate the pool. So: an oversized item is one whole child, sliced sequentially in the worker process, with chunk_index_offset continuing the chunk_index (issue #1888); document_body_override ensures the stored text is the full document, not the last slice (issue #1838).

⚠️ Why does the parent often have no task_payload?

The parent is a status aggregator (it rolls up all children's progress); the children carry the real task body. The two must be created in the same transaction, or you get an “orphan parent” that is never executed while queue metrics keep climbing.

8. Wrap-up and return

  • _run_final_semantic_ann (Phase3): after all batches commit, do one full semantic-neighbor backfill. Failure must not roll back the written facts — edges are enhancement, not the memory body (ch05).
  • Returns (per-content unit_id list, TokenUsage, processed_content_tokens); the HTTP layer aggregates usage into a RetainResponse.
  • Observations are not built yet: retain only stamps observation_scopes onto the facts; the real merge happens later in consolidation (ch09).

Summary

  • Retain's three layers: api_retain (translate & route) → retain_batch_async (guards & batching) → orchestrator.retain_batch (orchestration).
  • The main path is the streaming mini-batch: pre-chunk everything → per batch “extract → Phase1 → Phase2 → commit → release”.
  • The correctness trio: document-level content_hash, chunk-level hash, FOR UPDATE row locks; delta is “optimistic read + in-transaction recheck”.
  • Async uses operation_id idempotency; oversized single items are sliced in-process sequentially, not split into concurrent siblings.
  • Core principle: fail loudly, never silently lose data.
