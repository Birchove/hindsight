第三部分 · 检索 Recall

07 · 四路检索

上一章看了流水线骨架。这一章把四路逐个拆开:语义怎么走向量、BM25 怎么做全文、图怎么从种子扩展、时间怎么"入口 + 扩散"。每一路都有值得记住的工程细节——HNSW 过取样、图扩展的"加总打分"、时间检索"按相似度而非按时间排序"的反直觉选择。

本章要点

  • 四路都读 memory_units,都按 bank_id + fact_type + tags 过滤,都返回 list[RetrievalResult]。
  • 语义:每个 fact_type 一个 UNION ALL 分支命中偏索引;HNSW 是近似的,所以过取 5× 再在 Python 里裁。
  • BM25:默认原生 tsvector + ts_rank_cd;查询无词元就整路不跑。
  • 图:不是多跳 BFS,而是"从语义种子出发、一条 SQL、经三种链信号扩展",打分跨信号加总奖励"汇聚的证据"。
  • 时间:先选"入口点"(按相似度、覆盖整个时间窗),再沿时间/因果边扩散激活(这步才像 BFS)。

1. 语义路:向量相似度

定位:SQL 由 engine/sql/postgresql.py 的 build_semantic_arm 构造;执行在 search/retrieval.py 的 retrieve_semantic_bm25_combined。

相似度用 pgvector 的余弦距离算子 <=>,表示成 1 - 距离:

engine/sql/postgresql.py · build_semantic_arm(节选)sql
(SELECT {cols},
        1 - (embedding <=> $q::vector) AS similarity,
        NULL::float AS bm25_score,
        'semantic' AS source
 FROM memory_units
 WHERE bank_id = $b
   AND fact_type = 'world'              -- 每个 fact_type 一个分支
   AND embedding IS NOT NULL
   AND (1 - (embedding <=> $q::vector)) >= {min_similarity}   -- 默认 0.3
 ORDER BY embedding <=> $q::vector
 LIMIT {fetch_limit})

💡 两个关键设计

(1) 每 fact_type 一个 UNION ALL 分支:而不是一个大查询用窗口函数 ROW_NUMBER() PARTITION BY fact_type。为什么?因为带上 fact_type = '...' 过滤,规划器才会走每 fact_type 的偏 HNSW 索引(第 02 章那批 idx_mu_emb_*);窗口函数那种写法曾逼出全表顺序扫描。
(2) HNSW 过取样:HNSW 是近似最近邻,直接 LIMIT k 可能漏掉真正的好结果。所以每个分支取 hnsw_fetch = max(limit*5, 100),过取 5 倍,再在 Python 里裁回 limit。连接初始化时还设了 ef_search=200 提高召回。

✅ 顺带:语义结果被图路复用

如果语义门槛 ≤ graph_seed_min_similarity,那么排好序的语义行会直接当作图检索的入口种子(上限 20 个),省掉图路再做一次 ANN 查询。这是第 06 章"图依赖语义"的具体体现。

2. 关键词路:BM25 / 全文

定位:build_bm25_arm(同文件)。

默认后端是原生 tsvector,用 ts_rank_cd 排序、@@ 做匹配门:

engine/sql/postgresql.py · build_bm25_arm 原生分支(节选)sql
(SELECT {cols},
        NULL::float AS similarity,
        ts_rank_cd(search_vector, to_tsquery('english', $text)) AS bm25_score,
        'bm25' AS source
 FROM memory_units
 WHERE bank_id = $b AND fact_type = 'world'
   AND search_vector @@ to_tsquery('english', $text)   -- 匹配门
 ORDER BY bm25_score DESC
 LIMIT {limit})

查询词由 prepare_bm25_text 用 |(OR)连接。要点:

  • 无词元则整路不跑:tokenize_query 去标点、按空白切;纯符号查询切不出词,就根本不生成 BM25 分支(还会改变绑定参数的布局)。
  • 后端可换:除原生 tsvector 外,还支持 pg_search(ParadeDB)、pgroonga、vchord、pg_textsearch。_pg_search.py 只是 ParadeDB 的索引 DDL 助手,不在查询路径上。
  • Oracle 兜底:若 CONTAINS 因索引未同步报错,整条查询重建成只走语义。

3. 图路:链扩展

定位:search/link_expansion_retrieval.py 的 LinkExpansionRetriever(默认图检索器)。

📖 它不是多跳 BFS

名字里有"expansion",容易想象成"层层外扩的图遍历"。实际上它是有界的、一次 SQL 往返的扩展:从语义种子出发,通过 Retain 时就建好的三种链信号找邻居。这三种信号在写入时就被限定好了规模,所以查询时不需要深遍历。

三种链信号,各有一个 CTE,最后 UNION ALL 成一条查询、一个连接:

信号来源分数
实体查询时自连接 unit_entities(共享实体)COUNT(DISTINCT entity_id),每实体带 LATERAL 上限 200
语义Retain 时预算好的 kNN 图(memory_links 里 link_type='semantic'),双向查(图不对称)MAX(weight)
因果causes/caused_by/enables/preventsweight(作为最高质量信号加权)
engine/db/ops_postgresql.py · 实体扩展 CTE(节选)sql
entity_expanded AS (
  SELECT mu.id, ...,
         COUNT(DISTINCT se.entity_id)::float AS score,   -- 共享实体数
         'entity'::text AS source
  FROM seed_entities se
  CROSS JOIN LATERAL (
      SELECT ue_target.unit_id
      FROM unit_entities ue_target
      WHERE ue_target.entity_id = se.entity_id
        AND ue_target.unit_id != ALL($1::uuid[])          -- 排除种子自身
        AND EXISTS (SELECT 1 FROM memory_units mu_target
                    WHERE mu_target.id = ue_target.unit_id
                      AND mu_target.fact_type = $2)        -- 先过滤再限流
      ORDER BY ue_target.unit_id DESC
      LIMIT 200                                            -- 每实体上限
  ) t
  JOIN memory_units mu ON mu.id = t.unit_id
  GROUP BY mu.id
  ORDER BY score DESC
  LIMIT $3
)

加总打分:奖励"汇聚的证据"

一条事实可能同时被多个信号命中。合并时跨信号相加(总分落在 [0,3]):

  • 实体 → tanh(共享数 × 0.5)(共享 1 个得 0.46,2 个得 0.76,逐渐饱和);
  • 语义 → 最大链权重;
  • 因果 → 最大链权重。

💡 为什么加总而不是取最大?

如果一条事实既和查询共享实体、又有语义边、还有因果边,那它相关的证据是"汇聚"的,应该比只命中一路的更靠前。加总让这种多重证据累加起来。最终这个加总分存进 RetrievalResult.activation——注意它必须是加总后的分,而不是单信号分,否则跨 fact_type 的排序会和图内排序打架。

⚠️ 超时降级与 observation 的特殊路径

整条图查询包在 asyncio.wait_for(timeout=10s) 里;超时就降级为只用语义+因果(丢掉最贵的实体自连接)。另外,observation 没有直接的实体链,走单独的 _expand_observations:经 source_memory_ids → world 事实 → 实体 → 其他 world 事实 → 它们的 observation 绕行。

4. 时间路:入口点 + 扩散激活

定位:search/retrieval.py 的 retrieve_temporal_combined。仅当查询分析抽到时间约束时才跑。

分两阶段:

阶段一:选入口点(按相似度,不按时间!)

每个 fact_type 一个"相似度排序 + 时间窗过滤"的分支,先捞一个池子(_TEMPORAL_POOL_SIZE = 60),再收窄到每 fact_type _TEMPORAL_ENTRY_POINTS = 10 个,且这 10 个要覆盖整个时间窗(按 8 个时间桶 round-robin 选,避免都挤在一头):

search/retrieval.py · 时间入口分支(节选)sql
(SELECT {pool_cols}, 1 - (embedding <=> $1::vector) AS similarity
 FROM memory_units
 WHERE bank_id = $2 AND fact_type = 'world' AND embedding IS NOT NULL
   AND (   -- 时间窗匹配:occurred 区间或 mentioned_at 落在 [start,end]
        (occurred_start IS NOT NULL AND occurred_end IS NOT NULL
         AND occurred_start <= $4 AND occurred_end >= $3)
     OR (mentioned_at IS NOT NULL AND mentioned_at BETWEEN $3 AND $4)
     OR (occurred_start IS NOT NULL AND occurred_start BETWEEN $3 AND $4)
     OR (occurred_end   IS NOT NULL AND occurred_end   BETWEEN $3 AND $4))
   AND (1 - (embedding <=> $1::vector)) >= $5      -- 默认 0.1
 ORDER BY embedding <=> $1::vector
 LIMIT 60)

💡 为什么"按相似度选",而不是"按时间远近选"?

早期版本按日期排序选入口,结果把结果偏向时间窗的末端;而且在日期密集/均匀的 bank 上,会退化成"近乎随机抽样 + 一次全表扫描 + 溢出磁盘的排序"——在一个 66 万行的 bank 上要 30 多秒。改成按相似度排序(走 ANN 索引)+ 用桶保证时间覆盖,又快又均衡。

阶段二:扩散激活(这步才像 BFS)

从入口点出发,沿时间/因果边做有界的多跳扩散(frontier + visited + 预算,max_iterations=5):

search/retrieval.py · 一跳扩散(节选)sql
SELECT src.from_unit_id, mu.id, ..., l.weight, l.link_type,
       1 - (mu.embedding <=> $1::vector) AS similarity
FROM unnest($2::uuid[]) AS src(from_unit_id)
CROSS JOIN LATERAL (
    SELECT ml.to_unit_id, ml.weight, ml.link_type
    FROM memory_links ml
    WHERE ml.from_unit_id = src.from_unit_id
      AND ml.link_type IN ('temporal','causes','caused_by','enables','prevents')
      AND ml.weight >= 0.1
    ORDER BY ml.weight DESC
    LIMIT $5
) l
JOIN memory_units mu ON mu.id = l.to_unit_id
WHERE mu.bank_id = $6 AND mu.fact_type = $3 AND mu.embedding IS NOT NULL
  AND (1 - (mu.embedding <=> $1::vector)) >= $4

每个邻居得到一个 temporal_proximity(时间窗中点为 1.0、边缘为 0.0)和一个传播分 = 父分 × 边权 × 因果加成 × 0.7(因果加成:causes/caused_by 为 2.0,enables/prevents 为 1.5)。取 max(接近度, 传播分);高于 0.2 的邻居重新进入 frontier。

⚠️ Oracle 上扩散被跳过

扩散用到 unnest / LATERAL,Oracle 没有等价物,所以Oracle 上跳过扩散(但入口点仍返回)。时间结果为空时会被规范成 None(表示"没有时间路"),区别于 []。

小结

  • 语义:per-fact_type 分支命中偏索引;HNSW 过取 5× 再裁;门槛 0.3;结果可复用为图种子。
  • BM25:原生 tsvector + ts_rank_cd;无词元不跑;后端可换;Oracle 兜底转纯语义。
  • 图:有界单次 SQL 扩展,三种链信号(实体/语义/因果)加总打分;超时降级;observation 绕行。
  • 时间:按相似度选入口点(桶覆盖全窗)+ 沿时间/因果边扩散激活;Oracle 跳过扩散。
