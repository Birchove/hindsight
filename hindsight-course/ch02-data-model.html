02 · 数据模型:记忆长什么样

后面所有章节都会反复写到同一批表。这一章把地基打好:有哪些表、它们怎么关联、"一条事实"在磁盘上到底长什么样、向量怎么存、多租户怎么隔离。读懂这章,后续所有 SQL 都不再陌生。

本章要点

  • 记忆的主体是 memory_units 表——一行 = 一条原子事实;它同时携带 embedding、BM25 搜索向量、时间字段和巩固记账字段。
  • 图结构由 entities + unit_entities(事实↔实体)和 memory_links(事实↔事实的三种边)构成。
  • observation 不是独立的表,而是 memory_units 里 fact_type='observation' 的行——别和 mental_models 表混淆(后者经历了多次改名)。
  • 向量用 pgvector(384 维,HNSW 余弦);HEAD 上是每 bank、每 fact_type 一个偏索引。
  • 多租户 = 每租户一个 schema + search_path,运行时用 contextvar + fq_table() 全限定表名;bank 之间靠 WHERE bank_id = … 隔离。

⚠️ 先打预防针:models.py 不是全部真相

SQLAlchemy ORM(models.py)只定义了 7 张表和一部分列;运行时引擎实际执行的是手写 asyncpg SQL(engine/db/ops_postgresql.py,约 59KB),对着一个有 ~20 张表、更多列(search vector、tags、巩固记账)的真实 schema。权威来源是 Alembic migrations(约 89 个)加上这些手写 SQL。ORM 滞后于真实 schema(例如 Bank 还显示已被改名掉的 background 字段)。读 schema 时,以 migrations 和 ops_postgresql.py 为准。

2. 关系图与基数

erDiagram banks ||--o{ documents : "bank_id" banks ||--o{ mental_models : "bank_id" documents ||--o{ chunks : "(id,bank_id) CASCADE" documents ||--o{ memory_units : "(id,bank_id) CASCADE" chunks ||--o{ memory_units : "chunk_id SET NULL" memory_units }o--o{ entities : "unit_entities" memory_units ||--o{ memory_links : "from/to" memory_units ||--o{ memory_links : "to" entities ||--o{ entity_cooccurrences : "配对" memory_units }o--o{ memory_units : "source_memory_ids(observation)"
图 2-1:核心表关系。注意 observation 到源事实是 UUID[] 数组(软引用),不是外键;bank 在 PG 上大多不以 FK 被引用,而是靠 bank_id 列逻辑隔离。
  • bank → documents / memory_units / entities:1∶N(每行都带 bank_id)。
  • document → chunks:1∶N,复合外键 (document_id, bank_id),ON DELETE CASCADE。
  • chunk → memory_units:1∶N,但 ON DELETE SET NULL——删块孤立事实而非销毁。
  • memory_unit ↔ entity:M∶N,经 unit_entities,复合主键,两边都 CASCADE。
  • memory_unit ↔ memory_unit:M∶N 有向,经 memory_links,四列主键 (from_unit_id, to_unit_id, link_type, entity_id)——同一对可以有每种类型各一条边。
  • observation → 源事实:不是外键,而是 source_memory_ids UUID[] 数组列,用数组运算查询。

3. memory_units:一条事实的本体

这是全系统最重要的表。把它的字段按职责分组:

#   fact_type IN ('world', 'experience', 'observation')
分组字段
身份 / 租户id(UUID)、bank_id(隔离键,永不为空)
溯源document_id、chunk_id(删块时 SET NULL)
内容text(事实句,NOT NULL)、context、metadata(JSONB)、tags(VARCHAR[])、search_vector(生成的 BM25 表示)

仅 observation 用proof_count(多少条证据支撑)、source_memory_ids(UUID[])、history(JSONB)、observation_scopes、text_signals

📖 为什么有四个时间字段?

因为"记忆"的时间语义本身就多维:一件事何时发生(occurred_start/end)、何时被提及(mentioned_at)、以及一个兜底的 event_date。时间检索(第 07 章)会同时在 occurred_* 和 mentioned_at 上做窗口匹配——"六月发生了什么"和"六月我们聊到过什么"是不同的问题。

⚠️ chunk_id 是确定性的,不是 UUID

chunk_id = f"{bank_id}_{document_id}_{chunk_index}"(chunk_storage.py)。插入是幂等 upsert——同一 document_id 重复提交会产生相同 chunk_id,覆盖是正确行为。这也解释了第 04 章为什么切块必须幂等:chunk_index 冲突会直接撞主键。

4. entities / unit_entities / memory_links

initial_schema.py · entities 唯一索引 + memory_links 约束(节选)python
# entities: 按 (bank, 小写规范名) 唯一 —— "Paris" 与 "paris" 同一实体
op.execute("CREATE UNIQUE INDEX idx_entities_bank_lower_name "
           "ON entities (bank_id, LOWER(canonical_name))")

# memory_links: 类型与权重约束
CheckConstraint(
  "link_type IN ('temporal','semantic','entity','causes','caused_by','enables','prevents')")
CheckConstraint("weight >= 0.0 AND weight <= 1.0")

# 唯一性:可空的 entity_id 用 nil-UUID 顶替,才能进唯一索引
op.execute("CREATE UNIQUE INDEX idx_memory_links_unique ON memory_links "
  "(from_unit_id, to_unit_id, link_type, "
  " COALESCE(entity_id, '00000000-0000-0000-0000-000000000000'::uuid))")

⚠️ memory_links 的外键是 DEFERRABLE

from_unit_id/to_unit_id 的外键被设为 DEFERRABLE INITIALLY DEFERRED,以打破"插边 vs 级联删"的死锁。代价是插边不能靠 WHERE EXISTS 防护,而要在同一条语句里对父单元加 FOR KEY SHARE 锁(第 05 章见过)。另外,约束里虽然还留着 'entity',但那只为兼容历史行——Retain 已不再写实体边。

5. observation 不是独立的表(术语排雷)

PostgreSQL 上没有 observations 表。巩固出的观察就是 memory_units 里 fact_type='observation' 的行,用那几个"仅 observation 用"的字段(proof_count、source_memory_ids、history、observation_scopes)。

⚠️ "mental model" 一词三变,读 migration 别看名字

这个词在历史上指过三个不同的东西:
(a) memory_units 里的一个 fact_type,后被 t5o6p7q8r9s0 改名为 'observation';
(b) 一张独立的 mental_models v4 表,后被 p1k2l3m4n5o6 整张删掉;
(c) HEAD 上的 mental_models 表,其实是 reflections ← pinned_reflections 改名而来,存的是 reflect 的结果(子类型 directive/pinned)。
所以 CLAUDE.md 里"mental models = 巩固出的知识"这句话,在 HEAD 上对应的是 fact_type='observation' 的行,不是 mental_models 表。这正是第 01 章强调"observation ≠ mental model"的由来。

6. pgvector:向量怎么存、怎么索引

  • 列:memory_units.embedding,类型 vector(384)。维度 384 是模块常量(DEFAULT_EMBEDDING_DIMENSION),不按 bank 可配——换模型导致维度变化时,靠重算而非混存(归档表 invalidated_memory_units 故意不带 embedding 列,免得"归档向量"和现役模型维度对不上,#2209)。
  • 索引:HNSW + 余弦(vector_cosine_ops)。向量后端可插拔(pgvector / pgvectorscale 的 diskann / vchord / scann),由 _vector_index.py 的 _INDEX_USING_CLAUSES 映射:
_vector_index.py · _INDEX_USING_CLAUSESpython
_INDEX_USING_CLAUSES = {
    "pgvector":      "USING hnsw (embedding vector_cosine_ops)",
    "pgvectorscale": "USING diskann (embedding vector_cosine_ops) WITH (num_neighbors = 50)",
    "pg_diskann":    "USING diskann (embedding vector_cosine_ops) WITH (max_neighbors = 50)",
    "vchord":        "USING vchordrq (embedding vector_cosine_ops)",
    "scann":         "USING scann (embedding cosine) WITH (mode = 'AUTO')",
}

💡 HEAD 上:全局索引已删,改为每 bank × 每 fact_type 偏索引

早期是一个全局 HNSW 索引。migration d5e6f7a8b9c0 把它删了,改成对每个 bank 建三个偏索引:idx_mu_emb_{worl|expr|obsv}_{internal_id前16位}。为什么?因为检索 SQL 总是带 WHERE bank_id = … AND fact_type = … 再 ORDER BY embedding <=> …;偏索引让规划器直接走小索引,而不是被全局索引"竞争"掉。索引名用 internal_id 而非 bank_id,是为了名字稳定且不超 PostgreSQL 63 字符标识符上限。检索时(第 07 章)每个 fact_type 一个 UNION ALL 分支,正是为了命中这些偏索引。

7. 全文检索(BM25)的存储

与向量并行,memory_units 还有一个 search_vector 列。默认后端是原生 tsvector:

initial_schema.py · 生成的全文列sql
ALTER TABLE memory_units
ADD COLUMN search_vector tsvector
GENERATED ALWAYS AS (
  to_tsvector('english', COALESCE(text, '') || ' ' || COALESCE(context, ''))
) STORED;

但 search_vector 的类型随后端而变:原生 → 生成的 tsvector;pg_textsearch/pg_search → 哑 TEXT 列 + 基列上的索引;vchord → bm25_catalog.bm25vector。所以运行时插入要按后端分支(第 07 章的 BM25 检索也会用到这个列)。

engine/schema.py · fq_tablepython
def fq_table(table_name: str) -> str:
    if _is_oracle():
        return table_name              # Oracle 用 ALTER SESSION SET CURRENT_SCHEMA
    from .memory_engine import get_current_schema
    return f"{get_current_schema()}.{table_name}"   # PG: schema.table

要点:migration 树会对每个租户 schema 各跑一遍(hindsight-admin run-db-migration --schema tenant_xyz);当前 schema 存在 contextvar 里,租户鉴权后设置;所有原始 SQL 都经 fq_table() 全限定。bank 之间则不靠外键或行级安全,而是每条查询的 WHERE bank_id = $n——在 PG 上,数据表对 banks 根本没有外键(Oracle 基线更严格,加了 ON DELETE CASCADE 的 bank 外键)。

小结

  • 中心表是 memory_units(一行一事实),兼存 embedding、search_vector、四个时间字段和巩固记账。
  • 图 = entities + unit_entities + memory_links(三种边,可空列用 nil-UUID,外键 DEFERRABLE)。
  • observation 是 fact_type='observation' 的行,不是独立表;别和 mental_models 表混。
  • 向量:pgvector 384 维 HNSW,HEAD 上是每 bank × 每 fact_type 偏索引;全文检索有并行的一列。
  • 多租户三层:schema/search_path + contextvar/fq_table + bank_id WHERE。
