第三部分 · 检索 Recall

06 · Recall 总览与查询分析

从这章起进入"读取通路"。Recall 是 Hindsight 检索质量的来源:它四路并进地找记忆,再融合、重排。这一章先建立整体流水线,并澄清一个常见的误解——那个叫"query analyzer"的东西,其实只抽一样东西:时间约束。四路的内部细节和融合重排分别在第 07、08 章。

本章要点

  • Recall = 四路并行检索(语义 / BM25 / 图 / 时间)→ 融合 → cross-encoder 重排 → token 裁剪。
  • 查询分析不是 LLM 意图分类器:它只用 dateparser(或一个本地小 T5)抽出一个 (start_date, end_date) 时间窗,用来决定要不要跑时间检索。
  • "四路并行"的真实形态是分批 + 选择性并行:语义+BM25 融在一条 SQL、一个连接里;时间是第二条查询;只有图检索按 fact_type 真正并发(asyncio.gather)。
  • 资源用 budgeted_operation(连接预算,默认 4)+ 信号量 + thinking_budget(top-k)控制;单路失败有各自的降级。

1. 为什么要四路?

单一检索方式都有盲区:

  • 语义(向量)擅长"意思相近",但对精确关键词(产品名、编号)不敏感。
  • 关键词(BM25)擅长精确词匹配,但抓不住同义改写。
  • 图(链扩展)能找到"语义/关键词都找不到、但通过实体或因果相关联"的事实。
  • 时间专门回答"六月发生了什么""上周的事"这类带时间窗的问题。

💡 互补,然后让融合来裁决

四路各自从不同角度召回一批候选(各自的分数量纲都不一样:余弦相似度、BM25 分、图激活值、时间接近度),再由融合把它们的排名(而非分数)合并——这样就不需要把四种不可比的分数硬放到同一尺度上。这是第 08 章 RRF 的动机。

3. 查询分析:只抽时间约束

定位:engine/query_analyzer.py、engine/search/temporal_extraction.py。

很多人一听"query analyzer"就以为是"用 LLM 判断意图、抽实体、改写 query"。都不是。它的输出只有一个可选字段:

engine/query_analyzer.py · QueryAnalysispython
class QueryAnalysis(BaseModel):
    """Result of analyzing a natural language query.
    Contains extracted structured information like temporal constraints."""
    temporal_constraint: TemporalConstraint | None = Field(
        default=None, description="Extracted temporal constraint, if any")
# TemporalConstraint 就是 start_date + end_date 两个 datetime。
# 没有 intent 字段,没有实体列表,没有改写后的 query。

它有两种实现,都不是那个配置的业务 LLM:

实现原理成本
DateparserQueryAnalyzer(默认)纯库 + 规则:先试周期抽取("上周/去年"),再用 dateparser.search_dates 解析,对每个候选打分取最强~10–50ms,无模型
TransformerQueryAnalyzer(可选)一个本地小模型 google/flan-t5-small(~80M),先规则、不行才用 few-shot 生成日期区间本地小模型

💡 为什么要给日期匹配"打分"?(issue #2768)

dateparser 会过度匹配:一些恰好是某语言里"星期/月份缩写"的常见短词(如 "we"/"me"/"did" → 某个星期,"do" → 周日)会被当成日期。如果这种假阳性出现在真日期之前,取第一个匹配就会悄悄产出一个错误的时间窗——比"没有"还糟。所以不靠黑名单,而是给每个匹配按它"真正携带的日期信号"打分:有数字 +100、有月份/相对词 +50、星期 +30、周期词 +20;光秃秃一个词得 0 分,直接拒绝。

查询分析在任何数据库操作之前跑;它的产出决定了"要不要跑时间检索那一路"。任何 dateparser 异常都被吞成"无约束"——解析器的 bug 绝不能拖垮整条检索。

4. "四路并行"的真实形态

模块自称"4-way parallel search",但具体编排是分批 + 选择性并行,不是四个独立并发任务:

flowchart TB A["① 时间约束抽取(CPU,无 DB)"] --> B B["② 语义 + BM25:融在一条 SQL 里
(同一连接,顺序)"] B --> C["③ 时间检索:同一连接的第二条查询
(仅当有约束)"] B --> D["④ 图检索:每个 fact_type 一个任务
asyncio.gather 真并发"] C --> D D --> E["按 fact_type 汇总"]
图 6-2:真正的并发只有图检索那一步。语义和 BM25 是同一条 SQL 的交错分支,所以"一起"执行;时间检索复用同一连接。

💡 为什么语义和 BM25 不各跑一个连接?

两个原因:(1) asyncpg 规定一个连接上不能同时跑并发查询;(2) 把语义和 BM25 做成同一条 SQL 里交错的 UNION ALL 分支,一次往返就都拿到了——这是刻意的优化(注释:"把连接占用从 2 降到 1")。时间检索复用同一连接也是同理。只有图检索(每个 fact_type 一个独立连接)用 asyncio.gather 真正并发,而且它依赖语义阶段产出的种子(见第 07 章),所以只能在语义之后跑。

资源控制(默认值,来自 config.py)

单路失败怎么办

  • 图:asyncio.wait_for 超时 → 降级为"只用语义+因果"(丢掉最贵的实体自连接)。没种子 → 该 fact_type 返回空(图这路不贡献而已)。
  • BM25(Oracle):全文索引未同步(DRG-10599 等)→ 整条查询重建成只走语义。
  • 时间:无约束 → 整路跳过;Oracle 没有 unnest → 跳过"扩散"但保留入口点。
  • 连接级:连接错误指数退避重试 3 次;但客户端断开的取消错误绝不重试,直接上抛。

⚠️ asyncio.gather 没有 return_exceptions

图检索的 asyncio.gather 没带 return_exceptions=True。所以某个图任务里一个意料之外的异常会上抛、让整个 recall 失败(由上游重试/500 兜住),而不会被静默吞掉。换句话说:在 gather 这一层,失败的路不会被"悄悄丢弃"——这通常是好事(不静默),但也意味着一路的意外崩溃会连累整次检索。

5. 关键数据结构

四路返回的统一载体是 RetrievalResult(search/types.py):它携带记忆本体(id/text/fact_type/时间/标签/proof_count 等),外加几个按来源只填其一的分数字段:

字段谁填
similarity语义路
bm25_score关键词路
activation图路(加总的多信号分)
temporal_score / temporal_proximity时间路

上层还有聚合结构:SemanticBm25Result(每 fact_type 的语义/BM25/图种子)、ParallelRetrievalResult(四个列表 + 各路计时 + 时间约束)、MultiFactTypeRetrievalResult(按 fact_type 的字典 + 汇总计时)。融合后的 MergedCandidate、重排后的 ScoredResult 见第 08 章。

✅ 取消是"协作式"的

客户端断开后,引擎在各个阶段边界检查 request_context.raise_if_cancelled()。所以一次检索仍可能"正在某个查询里"时客户端就走了——取消不是强杀,而是在下一个检查点生效。最贵的 cross-encoder 阶段前会专门查一次(第 08 章)。

小结

  • Recall = 四路(语义/BM25/图/时间)互补召回 → 融合 → 重排 → 裁剪。
  • 查询分析只抽时间约束(dateparser + 打分防假阳性,或本地小 T5),不是 LLM 意图分类。
  • 真实并行:语义+BM25 一条 SQL、时间一条 SQL、图按 fact_type gather 并发;连接预算 4。
  • 每路失败都有降级;gather 不吞异常。
