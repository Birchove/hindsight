第二部分 · 写入 Retain

03 · Retain 端到端

Retain 是"写入通路"。这一章我们跟着一次最常见的请求(文本 JSON、同步、未命中增量)从 HTTP 一路走到落库,把三层代码串起来,并讲清那个看似过度复杂的 streaming 小批 + 事务分阶段 骨架。更细的两块——事实抽取/切块、实体与建边——分别留到第 04、05 章。

本章要点

  • Retain 不是"存原文再 embed",而是把文本变成原子事实 + 实体 + 三种边,提前写好 Recall 四路检索所依赖的结构。
  • 请求经过三层:api_retain(翻译分流)→ retain_batch_async(护栏切批)→ orchestrator.retain_batch(真正编排)。
  • 主执行路径是 streaming mini-batch:先整体切块,再按小批"抽取→建边→提交→释放",小文档也走这条路(只有一个批)。
  • 正确性靠文档级 content_hash + 块级 hash + FOR UPDATE;增量(delta)是"乐观读 + 事务内复核"。
  • 同步/异步两条路径,异步用 operation_id 做幂等,超大单条不拆并发而是在进程内顺序切片。

💡 复杂度几乎全来自三组张力

回顾第 01 章的三组张力,Retain 是它们最集中的体现:LLM 慢且贵 ↔ 写入要快、可恢复(→ streaming、delta、async);检索需要预计算结构 ↔ 结构计算可能失败(→ Phase1/2/3);并发多租户 ↔ 文档级一致性(→ content_hash、FOR UPDATE、同文档顺序切片)。带着它们读本章会顺很多。

2. 第一层:HTTP 只做"翻译 + 分流"

定位:api/http.py → api_retain(请求体模型是同文件的 RetainRequest / MemoryItem)。

这一层不调 LLM、不写业务表。它只做三件事:

  1. 把每条 MemoryItem 收成引擎内部用的 content_dict(timestamp → event_date,字符串 "unset" → None 等字段映射)。
  2. 按 item.strategy 分组——同一个请求里允许带多种 strategy,但每种必须单独进引擎。
  3. async=false → 调 retain_batch_async(同步);async=true → 调 submit_async_retain(入异步队列)。

💡 为什么要在 HTTP 层按 strategy 分组?

因为引擎内部的 apply_strategy 是"整批套一套配置"。如果把 conversations(聊天)和 documents(长文档)混进一次 retain_batch,只能套用其中一套,抽取规则、chunk 大小就会错。所以混合 strategy 必须在 HTTP 拆开。另外,带 operation_id(幂等键)时还要求只能有一组 strategy,否则幂等语义不清 → 返回 400。

3. 第二层:Engine 门面与护栏

定位:engine/memory_engine.py → retain_batch_async(公开主入口)→ _retain_batch_async_internal(真正进编排器前的配置准备);切批在 _split_contents_into_sub_batches。记得只按函数名跳读。

门面层把一堆"横切关注点"集中处理,让 retain/ 包能专注于"抽 + 写"。它按顺序做:

  1. 租户鉴权,可选的 OperationValidator(额度检查、改写 contents)。
  2. 深拷贝 contents——因为后面编排器会就地 pop("content") 省内存,不能污染调用方传入的对象。
  3. sanitize_text:清掉会打崩 embedder 的坏 Unicode(孤立代理对等,源码指向 issue #1875)。
  4. 校验:同一批里不能有重复 document_id;append 模式必须带 document_id 且开启文档正文存储。
  5. 按 token 预算切 sub-batch(过大时);同一文档被切成多片时计算 chunk_index_offset(防 issue #1888 的块号冲突)。
  6. _retain_batch_async_internal:resolve_full_config(层级配置解析)→(可选)强制 chunks 模式 → apply_strategy → 调 orchestrator.retain_batch。

⚠️ 引擎会就地改 dict,所以入口必须拷贝

这是一条贯穿全代码的不变量:编排器为了省内存会 pop("content")、清空大字符串。如果门面层不先深拷贝,调用方传进来的数据会被"偷走"。凡是要把数据交给 retain/ 的地方,都要假设对方会就地修改。

💡 为什么 Engine 这么"厚"?

安全、计费、配置层级、异步入队这些横切关注点集中在一处,业务流水线(retain/)才能保持纯粹。代价就是 memory_engine.py 这个 1.4 万行的巨石——所以它只能按函数跳读,不要试图通读。

4. 第三层:orchestrator 的文档级骨架

定位:engine/retain/orchestrator.py → retain_batch。

进入流水线后,先处理"文档级"问题,再进入 chunk 循环:

flowchart TD A[取 bank profile / narrator] --> B{多个 document_id?} B -->|是| C[按文档递归 retain_batch] B -->|否| D[Memory Defense 筛查] D --> E[解析 effective_doc_id] E --> F{update_mode=append?} F -->|是| G[读旧 original_text 拼到前面] F -->|否| H[stale-request 检查] G --> H H --> I{_try_delta_retain} I -->|命中| Z[直接返回] I -->|未命中| J[chunk_text 预切全部 chunks] J --> K[_streaming_retain_batch]
图 3-2:retain_batch 的文档级骨架。下面逐个解释几个"为什么"。

Narrator(第一人称消解)

_resolve_narrator:抽取 prompt 里可注入"Narrator: 名字",帮模型消解第一人称("我"到底是谁)。但自动建 bank 时常有 name == bank_id,而 bank_id 往往是路由键(形如 agent::channel::user)。若把它注入,路由键会被写进事实文本、进而污染后续 observation——所以遇到这种情况直接不注入(issue #1680)。

Memory Defense(写入前防御)

在抽事实之前先筛敏感内容,得到 ALLOW / REDACT / BLOCK 三种处置。如果全员 BLOCK,抛 MemoryDefenseAllBlockedError → HTTP 422。定位:retain_batch 前段 + extensions/memory_defense.py。

Append(追加不是"只插新事实")

update_mode == "append" 时,系统会取出已存的文档正文,拼成完整文档,再走后续流程(通常会配合 delta 跳过未变的前缀 chunk)。读正文:fact_storage.get_document_content。这个设计初看反直觉——"追加"为何要重读全文?因为事实是从上下文里抽的,只看新增片段会抽错。

Stale-request(跳过过期请求)

如果该文档的 updated_at 已经新于"本次请求的开始时间",直接跳过,避免一个迟到的旧请求覆盖了新会话的内容。注意:这只是优化,真正的正确性靠事务里的 FOR UPDATE + hash 校验(注释里写明这一点)。

⚠️ 抽取失败必须"响亮"(issue #1833)

如果抽事实失败却返回空列表、还把操作标成 completed,那么这个文档会以 0 条事实落库,界面显示"成功"——记忆被静默丢失,而且没人知道。因此重试耗尽、协议异常等路径必须 raise,让上层标失败、可重试,绝不能假装成功。这是一条重要的设计原则:宁可失败重试,不可静默丢数据。

💡 文档跟踪为何挪进第一个写事务

"删旧文档记录、插新文档记录"这个动作被故意挪到第一个写事务内,并用 SELECT … FOR UPDATE 锁住。为什么?如果"先删文档、再去调 LLM 抽事实",这中间有空窗,并发请求可能插进来导致重复。把删除和后续写入放进同一事务 + 行锁,就堵上了这个并发空洞。

6. 可恢复性:streaming 与 delta

为什么是 streaming(而不是一次做完)

大文档(注释提到过 17k+ chunks)若一次性 extract → embed → 写库,内存峰值和失败代价都不可接受:要么 OOM,要么失败整篇作废。streaming 把失败粒度降到"一个 mini-batch",内存峰值有界。

One-shot(一次做完)Streaming
失败粒度整篇一个 mini-batch
内存峰值随全文事实集涨有界
代码路径简单需要 recovery / offset / 边界处理

崩溃恢复怎么做

sequenceDiagram participant W as Worker/进程 participant O as streaming participant DB as DB W->>O: 重试同一 document O->>DB: 读 documents.content_hash alt hash 与本次一致且已有 chunk O->>O: RECOVERY:跳过已提交 chunk O->>DB: 只处理剩余 chunk else hash 不同或无记录 O->>DB: 正常全量 / 首批事务内文档跟踪 end
图 3-4:崩溃后重试同一文档时,靠"文档级 content_hash + 块级 hash"双保险,跳过已提交的块,只补剩余部分。

Delta retain(增量):少花钱,但仍要正确

定位:orchestrator._try_delta_retain、_classify_chunk_diff、_delta_metadata_only。

同一个 document_id 反复 upsert(如聊天会话越来越长)时,如果每次整篇重抽,LLM 费用和延迟会爆炸。delta 只对变化的块重抽:

flowchart TD A[无锁读已有 chunks] --> B[按 content_hash 分类:
unchanged / changed / new / removed] B --> C[开启写事务, FOR UPDATE] C --> D{content_hash 仍一致?} D -->|是| E[只处理变更 chunk] D -->|否| F[放弃 delta → 回退全量 streaming]
图 3-5:delta = "乐观读 + 事务内校验"。先无锁读(避免长读占连接)做 diff,真正写之前再用 FOR UPDATE 复核 hash;若并发请求已改过,就回退全量。

📖 模式名:乐观读 + 事务内校验

先在不加锁的情况下读旧数据、做 diff(便宜、快),等真正要写的时候,再在一个短事务里用 FOR UPDATE 锁住并复核 content_hash。如果这中间被别人改过,就放弃增量、回退到全程有锁保护的全量 streaming。append 与 delta 是搭档:append 先拼出完整文档,再进入 delta,于是未变的前缀 chunk 大多被跳过。

💡 为什么要 operation_id 幂等?

客户端超时重试时,同一个 UUID 应该"返回原操作、不再入队"。注释特别强调:幂等读故意不和创建放在同一事务;真正的互斥靠主键唯一,冲突时用 unique-violation 兜底。这样即使两个请求同时到达,也只有一个能插入成功。

💡 为什么超大单条不拆成"并发兄弟 child"?(issue #1795)

因为多个 worker 之间没有 per-document 串行。如果多个 child 共享同一个 document_id、又都以为自己是 is_first_batch,会互相 cascade-delete 对方已写的 units;最终 ANN 插边时还会撞外键、打满连接池。所以:过大单条整块作为一个 child,在 worker 进程内顺序切 sub-batch,并用 chunk_index_offset 续上 chunk_index(issue #1888);document_body_override 保证存的是全文而非最后一片(issue #1838)。

⚠️ parent 为什么常没有 task_payload?

parent 是状态聚合器(汇总所有 child 的进度),child 才有真正的任务体。二者必须在同一事务里创建,否则会出现"孤儿 parent":它永远不被执行,队列指标却一直涨。

8. 收尾与返回

  • _run_final_semantic_ann(Phase3):所有批次提交后,做一次全量语义邻居补全。失败不应回滚已写入的事实——边是增强,不是记忆本体(第 05 章细讲)。
  • 返回 (每条 content 的 unit_id 列表, TokenUsage, processed_content_tokens);HTTP 层汇总 usage,组成 RetainResponse。
  • Observation 此时还没建:retain 只是把 observation_scopes 写到 fact 上,真正的合并发生在事后 consolidation(第 09 章)。

小结

  • Retain 三层:api_retain(翻译分流)→ retain_batch_async(护栏切批)→ orchestrator.retain_batch(编排)。
  • 主路径是 streaming mini-batch:预切全部 chunk → 逐批"抽取→Phase1→Phase2→提交→释放"。
  • 正确性三件套:文档级 content_hash、块级 hash、FOR UPDATE 行锁;delta 是"乐观读 + 事务内复核"。
  • 异步用 operation_id 幂等;超大单条进程内顺序切,不拆并发兄弟。
  • 核心原则:失败要响亮,不可静默丢数据。

下一章钻进 streaming 循环里最关键的一步——事实是怎么从文本里抽出来、chunk 又是怎么切的。
