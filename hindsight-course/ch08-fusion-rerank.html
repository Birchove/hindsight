第三部分 · 检索 Recall

08 · 融合与重排

四路各交回一个排名列表。这一章讲"合并 → 精排 → 裁剪"三步:用倒数排名融合(RRF)把四个不可比的排名合成一个;用cross-encoder对幸存集精排;再按 token 预算裁成最终答案。这里有两个经典考点:为什么用 RRF、为什么"先融合再重排"。

本章要点

  • RRF 只看排名、不看分数:score(d) = Σ 1/(k+rank),k=60。无需把四种分数量纲对齐,也没有权重可调。
  • cross-encoder 贵,所以先 RRF 预筛到 300 再重排——这是整条流水线的成本闸门。
  • 重排分是主信号,再乘上时效/时间/证据三个加成(都以 0.5 为中性的 ×1.0),得到最终排序。
  • 裁剪分两次:先按 thinking_budget×2 截条数,再按 max_tokens(tiktoken)在溢出那条之前停,不切碎事实。

1. 代码在哪

纯算法在 search/fusion.py、search/reranking.py、search/recall_boost.py;但编排(谁先谁后、预筛、裁剪)在 memory_engine._search_with_retries。流水线一览:

步做什么
2四路返回排名列表;可选每路截断(cap_per_source)
3融合:RRF(默认)或轮询 interleave
4按(加权)RRF 分预筛到 reranker_max_candidates → cross-encoder 重排

6按 max_tokens 做 token 裁剪

2. RRF:倒数排名融合

定位:search/fusion.py → reciprocal_rank_fusion(result_lists, k=60)。

公式:score(d) = Σ_lists 1/(k + rank(d)),k=60(Cormack/Clarke/Buettcher 的经典常数),排名从 1 开始。

engine/search/fusion.py · reciprocal_rank_fusion(节选)python
rrf_scores[doc_id] += 1.0 / (k + rank)
source_ranks[doc_id][f"{source_name}_rank"] = rank

# 合并结果只保留"第一次出现"那路的 RetrievalResult,
# 所以把每路的原始分数单独记到 ArmScores 里,供下游报告/过滤。
if source_name == "semantic" and retrieval.similarity is not None:
    arm_scores[doc_id].semantic = retrieval.similarity
elif source_name == "bm25" and retrieval.bm25_score is not None:
    arm_scores[doc_id].keyword = retrieval.bm25_score

# 最终按 RRF 分降序;rrf_rank 在这个顺序里从 1 编。
for rrf_rank, (doc_id, rrf_score) in enumerate(
    sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True), start=1):
    merged_results.append(MergedCandidate(
        retrieval=all_retrievals[doc_id], rrf_score=rrf_score,
        rrf_rank=rrf_rank, source_ranks=..., arm_scores=...))

💡 为什么用 RRF,而不是加权求和?

四路的原始分数量纲完全不可比:余弦相似度在 [0,1]、BM25 分无上界、图激活值在 [0,3]、时间接近度又是另一套。若加权求和,得先费心把它们归一到同尺度,还要调权重。RRF 只用排名——"你在你这路里排第几"——于是:没有权重可调,也不用对齐量纲,天然抗某种分数的异常放大。这就是所谓"无参数融合"(parameter-free fusion)。

  • 去重键是文档 id;同一条事实在多路出现,RRF 分累加,但合并结果只保留第一次出现那路的载荷(原始分数靠 ArmScores 另存)。
  • cap_per_source:融合前可先把每路截到 top-cap,防止某一路过度膨胀挤掉别人(默认 0=关)。

📖 还有个 interleave 模式,专门治 RRF 的一个毛病

RRF 用"各路倒数排名之和"打分,于是一条在某路排第 1、但在别路缺席/很低的结果,会被平均拉低。这在巩固去重时咬过人:一条与已有 observation 几乎相同的"孪生"结果,语义路排第 1,却被 RRF/重排埋到预算之外,导致模型没看见它、又建了个重复的。interleave_fusion 用轮询保证每路的 top 都拿到一个位置(并跳过后续的合并打分重排)。巩固专门用 interleave 就是这个原因(第 09 章)。

3. Cross-encoder 重排

定位:search/reranking.py 的 CrossEncoderReranker;模型抽象 cross_encoder.py 的 CrossEncoderModel。

📖 先搞懂 bi-encoder vs cross-encoder

bi-encoder(就是语义路用的)把 query 和 doc 分别编码成向量再算相似度——便宜,doc 向量可预算,所以能从百万条里快速召回。但它没让 query 和 doc "见面",精度有限。cross-encoder 把 [query, document] 拼在一起过同一个 transformer,直接输出一个相关性分——准得多,但没法预算 doc 向量,必须对每个候选现算,O(n) 次前向,很贵。这个"成本不对称"决定了整条流水线的形状:便宜的 bi-encoder 先大范围召回,昂贵的 cross-encoder 只精排小集合。

构造 [query, doc] 对时,doc 文本是 context + ": " + text,还会前置一个格式化日期增加时间感知:f"[Date: {date_readable} ({date_iso})] {doc_text}"。所有对一次性送进 cross_encoder.predict(pairs)。

归一化是有条件的

engine/search/reranking.py · rerank(节选)python
scores = await self.cross_encoder.predict(pairs)

# 外部 API 重排器(Cohere/Jina 等)返回已校准到 [0,1] 的分数 —— 原样保留,
# 保住"绝对置信度"(一个 0.007 的候选就该低,别被排名归一抬成 1.0)。
# 本地模型返回 logits(任意实数)—— 用 sigmoid 映射到 (0,1)。
if scores and min(scores) >= 0.0 and max(scores) <= 1.0:
    normalized_scores = list(scores)          # 已校准,直通
else:
    normalized_scores = [1 / (1 + np.exp(-s)) for s in scores]   # sigmoid

4. 流水线顺序:先融合,再重排,在预筛后的集合上

最终排序:CE 为主,三个乘法加成

apply_combined_scoring 把 cross-encoder 分当主信号,再乘上三个加成。每个加成以 0.5 为中性(缺信号就是 ×1.0):

engine/search/reranking.py · apply_combined_scoring(节选)python
recency_boost     = 1.0 + recency_alpha     * (sr.recency - 0.5)    # α=0.2
temporal_boost    = 1.0 + temporal_alpha    * (sr.temporal - 0.5)   # α=0.2
proof_count_boost = 1.0 + proof_count_alpha * (proof_norm - 0.5)    # α=0.1
sr.combined_score = (sr.cross_encoder_score_normalized
                     * recency_boost * temporal_boost * proof_count_boost)
sr.weight = sr.combined_score

💡 为什么用乘法而不是加法?

乘法保证这些次要信号的影响力始终与"基础相关性"成正比——一个 CE 分很低的候选,再怎么"新"也不会被抬上去;而且它对 cross-encoder 的分数标定方式不敏感(不同模型打分尺度不同)。默认 α 下,加成最多带来约 +21%/−19% 的摆动:够微调,不至于喧宾夺主。

📖 recall_boost:在两处、两种尺度上加权某一路

部署可以让某一路优先(如 HINDSIGHT_API_RECALL_STRATEGY_BOOSTS=graph:high)。它在两个结构不同的地方生效:① 重排封顶之前,用"加权 RRF"(rank-aware)让被加权路的候选不被 300 名裁掉;② 重排之后,给最终 weight 加一个平的加成,把它们往前挪。

5. Token 预算裁剪

两次有序的裁剪:

  1. 按条数:top_scored = scored_results[: thinking_budget * 2]。thinking_budget 由 budget 枚举解析(默认 100/300/1000,或按 max_tokens 自适应)。
  2. 按 token:_filter_by_token_budget 用 tiktoken cl100k_base,只数 text 字段,按排名顺序累加,一旦下一条会超就 break——丢掉剩下的,而不切碎一条事实:
engine/memory_engine.py · _filter_by_token_budget(节选)python
for result in results:
    text_tokens = len(encoding.encode(result.get("text", "")))
    if total_tokens + text_tokens <= max_tokens:     # 默认 4096
        filtered_results.append(result)
        total_tokens += text_tokens
    else:
        break          # 在溢出的那条之前停下

⚠️ chunk 是另一套预算,且会被截断

若 include_chunks,chunk 用独立的 max_chunk_tokens(默认 8192)预算、在事实裁剪之前取;而且和事实不同,最后一个 chunk 会被截断塞进去(而非丢弃)。后果:max_tokens=0 会返回 0 条事实,但仍可能返回 chunk。

7. 易踩坑

坑说明
k=60 重复且必须一致RRF 和 boosted_rrf_score 各自硬编码 k=60,漂移会悄悄破坏加权逻辑
直通重排(rrf provider)所有 CE 分相同;代码用显式 flag 从 RRF 排名"种"出 CE 分,否则会退化成纯时效排序
融合只留第一路的载荷改动各路的先后顺序会改变载荷(不改变排序)
token 裁剪只数 text不数 context、不数 CE 看到的日期串;在溢出前停,绝不切事实
无分数缓存重排每次查询都全量重算
RRF 平局按稳定排序的"首次出现顺序"打破,没有二级分数

小结

  • RRF:只用排名的无参数融合,Σ1/(60+rank),去重按 id。
  • cross-encoder:把 query+doc 拼一起精排,贵;所以先 RRF 预筛到 300 再重排;归一化对"已校准 vs logits"区别对待。
  • 合并打分:CE 为主 × 时效 × 时间 × 证据(乘法,0.5 中性)。
  • 裁剪:先 thinking_budget×2 截条数,再按 token 在溢出前停;chunk 另一套预算。
