第二部分 · 写入 Retain

04 · 事实抽取与切块

上一章我们走完了 Retain 的骨架。这一章钻进 streaming 循环里最关键的一步:文本如何被切成 chunk、又如何被 LLM 抽成一条条原子事实。这里藏着两个看似普通、实则反复出过问题的设计——切块的幂等性,和抽取 prompt 与 bank 解耦。

本章要点

  • 切块 chunk_text 按内容类型分流:纯文本句子感知、JSON 对话轮次边界、JSONL 行边界。
  • 切块必须幂等(对结果再切一次不变),否则 streaming 的"先预切、抽取时再切一次"会让子块撞 chunk_id(issue #2301)。
  • 一条"事实"是多维的:what/when/where/who/why + fact_type + entities + causal_relations,最终拼成一句 fact_text。
  • 抽取 prompt 的 system 部分刻意与 bank 无关(mission 放进 user message),只为跨 bank 共享 LLM 缓存。
  • chunks 模式是"不调 LLM"的兜底方案:整块当一条事实。

1. 两个子问题:怎么切、怎么抽

Retain 的"抽 + 嵌"发生在 engine/retain/fact_extraction.py(约 2800 行,是本包最大的文件之一,同样建议按函数跳读)。它解决两个子问题:

  • 切块(chunking):把可能很大的输入文本,切成适合喂给 LLM 的小块。入口 chunk_text。
  • 抽事实(extraction):把每个小块交给 LLM,抽出一条条结构化事实。入口 extract_facts_from_contents(并行处理多个 content)。

2. 切块:chunk_text

定位:engine/retain/fact_extraction.py → chunk_text;分支辅助函数 _chunk_conversation、_chunk_jsonl、_split_oversized_unit。

它先判断输入是什么类型,再选不同的切法:

engine/retain/fact_extraction.py · chunk_text(节选)python
def chunk_text(text: str, max_chars: int, structured_chunk_size: int | None = None) -> list[str]:
    # 文本足够小,直接整块返回
    if len(text) <= max_chars:
        return [text]

    structured_limit = structured_chunk_size if structured_chunk_size is not None else max_chars

    # 尝试当成 JSON 对话数组解析([{user...}, {assistant...}, ...])
    try:
        parsed = json.loads(text)
    except (json.JSONDecodeError, ValueError):
        parsed = None

    if isinstance(parsed, list) and all(isinstance(turn, dict) for turn in parsed):
        # 是对话 —— 按"轮次"边界切,不切断一条发言
        return _chunk_conversation(parsed, max_chars, structured_limit)

    if isinstance(parsed, dict):
        # 单个 JSON 对象(可能是已被上游预切的一条 JSONL)—— 尽量保持完整
        if len(text) <= structured_limit:
            return [text]
        return _split_oversized_unit(text, max_chars)

    # 尝试按 JSONL(每行一个 JSON 对象,如会话日志)切
    jsonl_chunks = _chunk_jsonl(text, max_chars, structured_limit)
    if jsonl_chunks is not None:
        return jsonl_chunks

    # 兜底:句子感知的纯文本切分
    return _split_oversized_unit(text, max_chars)

行为要点:

  • 纯文本:句子感知切分(尽量在句号等边界切,不从句子中间砍断)。
  • JSON 对话数组:在轮次边界切,不会把一条发言切成两半。
  • JSONL:在行边界切,一行一个对象不被切断。
  • 单条发言/单行若超过 max_chars,最多保持到 structured_chunk_size,再大就按文本切。

⚠️ 幂等性:这里最重要的不变量(issue #2301)

chunk_text 的 docstring 明确写道:"结果是幂等的:对返回的任何一个 chunk 再次切块,得到的还是它本身。"为什么必须如此?因为 streaming 流水线会先整篇预切一次,抽取阶段对每一片再切一次。如果第二次会把某片再切开,那么这些子块会继承同一个 chunk_index,而 chunk_id = {bank}_{doc}_{chunk_index} 是确定性主键——于是冲突、数据错乱。上面 isinstance(parsed, dict) 那一分支,就是专门为了堵住"一个已被上游保持完整的对象,落到纯文本切分里又被切碎"这个破坏幂等的漏洞。

✅ 一个通用的工程教训

"同一个函数会被流水线在不同阶段重复调用"时,务必让它幂等。否则第二次调用的副作用(这里是再切一刀)会悄悄破坏第一次调用建立的不变量。这类 bug 极难复现,往往只在特定长度的输入上偶发。

切完后,编排器会清空 RetainContent.content 这个大字符串,只留 all_pre_chunks 工作集——纯粹为了内存(大文档可达数 MB × N 份)。

3. 一条"事实"长什么样

定位:fact_extraction.py → ExtractedFact(默认模式的 Pydantic schema)。

LLM 被要求对每条事实输出多个维度,而不是一句话:

engine/retain/fact_extraction.py · ExtractedFact(节选)python
class ExtractedFact(BaseModel):
    what: str = Field(description="Core fact - concise but complete (1-2 sentences)")
    when: str = Field(description="When it happened. 'N/A' if unknown.")
    where: str = Field(description="Location if relevant. 'N/A' if none.")
    who: str = Field(description="People involved with relationships. 'N/A' if general.")
    why: str = Field(description="Context/significance if important. 'N/A' if obvious.")

    fact_kind: str = Field(default="conversation", description="'event' or 'conversation'")
    occurred_start: str | None = Field(default=None, description="ISO timestamp for events")
    occurred_end: str | None = Field(default=None, description="ISO timestamp for event end")
    fact_type: Literal["world", "assistant"] = Field(
        description="'world' = objective/external facts, including user preferences, rules...; "
                    "'assistant' = actions/experiences the assistant/agent actually performed.")
    entities: list[str] = Field(default_factory=list,
        description='People, places, concepts - plain strings, e.g. ["Alice", "Kubernetes"]')
    causal_relations: list[FactCausalRelation] | None = Field(
        default=None, description="Links to previous facts (target_index < this fact's index)")

    def build_fact_text(self) -> str:
        parts = [self.what]
        if self.who and self.who.upper() != "N/A":
            parts.append(f"Involving: {self.who}")
        if self.why and self.why.upper() != "N/A":
            parts.append(self.why)
        return " | ".join(parts) if len(parts) > 1 else parts[0]

📖 fact_type 的"方言":world/assistant → world/experience

注意 LLM 抽取时输出的 fact_type 是 "world" 或 "assistant";而第 01 章讲数据库里存的是 world / experience。这是同一个概念的两种叫法:prompt 里用"assistant"更贴合模型对"第一人称是我(Agent)"的理解,落库时被映射成更通用的 experience。读代码时看到这两个词别以为是两回事。

  • entities 是纯字符串列表(如 ["Alice", "Kubernetes"]),甚至包括"友谊""职业成长"这类抽象概念。这些字符串会在下一章被归一成规范实体——抽取层只管"提到过什么",不管"它和已有实体是不是同一个"。
  • causal_relations 只能指向之前的事实(target_index < this fact's index,每条最多 2 个)。这是因果边的来源,第 05 章会看到它如何变成 caused_by 边。用"批内序号"而非 ID 来引用,是因为此时事实还没落库、没有真实 ID。
  • build_fact_text() 把多维信息拼成一条字符串(what | Involving: who | why),这才是真正存进 memory_units.text、被 embed、被检索的内容。

4. Prompt 设计:为什么 system 部分与 bank 无关

定位:fact_extraction.py → _build_extraction_prompt_and_schema(组装 system prompt + 选 schema);_build_user_message(组装每次请求的 user message)。

抽取模式(extraction modes)

配置项 retain_extraction_mode 决定用哪套 prompt 与 schema:

模式行为何时用
concise(默认)抽成简洁的多维事实常规
verbose更啰嗦的事实(用 ExtractedFactVerbose schema)需要更丰富细节
verbatim尽量逐字保留原文,不建因果边不想让模型改写
custom注入 retain_custom_instructions 自定义指令领域定制
chunks不调 LLM,整块当一条事实(见第 5 节)provider=none / 速度成本优先

关键设计:system prompt 刻意"与 bank 无关"

这是本章最值得记住的设计决策。直觉上,bank 的 retain_mission("这个记忆库关注什么")似乎该写进 system prompt。但源码故意不这么做:

engine/retain/fact_extraction.py · _build_extraction_prompt_and_schema(注释)python
# The per-bank retain mission is NOT baked into this system prompt: it would
# make the prompt bank-specific and force a separate Gemini context cache per
# mission (one per bank). Instead the prompt is bank-agnostic so a single
# CachedContent serves every bank, and the mission rides in the per-request
# user message via _retain_mission_preamble().

💡 为什么?为了跨 bank 共享缓存、省钱

Gemini(以及 Anthropic、OpenAI)支持prompt 前缀缓存:相同的前缀可以只付一次全价,后续命中缓存便宜很多。如果把 mission 写进 system prompt,那么每个 bank 的 system prompt 都不一样,就得为每个 bank 单独建一份缓存——成千上万个 bank 就是成千上万份缓存,缓存命中率暴跌。把"对所有 bank 都一样"的部分(抽取规则、输入格式、输出格式)放进可缓存的 system,把"每个 bank 不同"的 mission 放进每次请求的 user message,就能让一份缓存服务所有 bank。这是一个"为成本而调整 prompt 结构"的典型例子。

第一人称归属:Narrator 与 Context 的优先级

抽取时还要解决"我"是谁的问题。_build_user_message 会注入一段 Narrator 说明,并且明确 Context 优先:

engine/retain/fact_extraction.py · _build_user_message(节选)python
if agent_name:
    narrator_section = (
        f"\nNarrator: {agent_name} (the AI agent whose memory this is). By default, "
        f'first-person statements like "I did X" are {agent_name}\'s own actions → classify as '
        f'"assistant".'
    )
    if context:
        narrator_section += (
            " BUT the Context above takes precedence: if it identifies a different "
            "first-person speaker (e.g. a user or customer in a transcript), attribute those "
            'statements to that speaker and classify them as "world", not "assistant".'
        )

含义:默认情况下"我做了 X"是 Agent 自己的行为 → 归为 assistant(即 experience);但如果 Context 表明说话的是用户/客户,那么"我"指用户 → 归为 world。这决定了这条记忆是"我的经历"还是"关于世界(用户)的事实"。

✅ 顺带一提:输出语言与检索语言是两回事

prompt 末尾还会追加一条"强制用配置语言输出事实"的指令(llm_output_language)。源码注释专门强调:这和 BM25 的索引语言(text_search_extension_native_language)是相互独立的两个配置——"LLM 输出什么语言"和"全文检索按什么语言分词"是不同关注点,别混。

5. chunks 模式:不调 LLM 的兜底方案

定位:fact_extraction.py → _extract_facts_chunks。

当不需要(或不能)调 LLM 时,系统走 chunks 模式:每个 chunk 直接成为一条 world 事实,原文即 fact_text,不抽实体。

engine/retain/fact_extraction.py · _extract_facts_chunks(节选)python
# chunks mode: no LLM call, no entity extraction.
# Each chunk becomes one memory unit with the raw text as fact_text.
for chunk in chunks:
    extracted_facts.append(ExtractedFactType(
        fact_text=chunk,
        fact_type="world",
        entities=[],          # 本模式不抽实体
        content_index=content_index,
        chunk_index=global_chunk_idx,
        ...
    ))

📖 什么时候会被强制走 chunks?

把 HINDSIGHT_API_LLM_PROVIDER 设为 none 时,配置校验会强制 retain_extraction_mode="chunks" 并关闭 observations——逻辑是:没有模型,就别假装能抽事实,老老实实做"只能向量检索"的朴素记忆。这也让"无 LLM"成为一个可运行、可演示的降级形态。

6. 失败处理:必须响亮,但也要能容错

  • 该失败就失败:重试耗尽、协议异常等必须 raise(issue #1833),绝不能返回空列表还标成功——那会静默丢记忆(第 03 章已强调)。
  • 输出过长会自动切分重试:如果模型说"输出太长"(OutputTooLongError),_extract_facts_with_auto_split 会把这个 chunk 一分为二再分别抽,而不是直接放弃。
  • 瞬时错误可重试:偶发的 JSON 解析失败、连接错误等走重试;但像"embedding 维度不匹配"这种确定性错误不重试(重试只是白白烧 worker 槽位)。

⚠️ 两个同名函数,别混

embedding_processing.py 和 embedding_utils.py 里各有一个 generate_embeddings_batch——前者是包装,后者是实现。import 时看准路径。

小结

  • chunk_text 按类型分流(文本/对话/JSONL),核心不变量是幂等(issue #2301)。
  • 一条事实是多维的(what/when/where/who/why + fact_type + entities + causal_relations),最终拼成单条 fact_text。
  • fact_type 抽取时叫 world/assistant,落库叫 world/experience。
  • 抽取 system prompt 与 bank 解耦,mission 放进 user message,为的是跨 bank 共享 LLM 缓存。
  • chunks 模式是无 LLM 的兜底方案;失败处理遵循"该响亮就响亮、该容错就容错"。
