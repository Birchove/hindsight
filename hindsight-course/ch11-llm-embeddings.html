第五部分 · 横切支撑

11 · LLM 抽象层与 Embeddings

前面所有操作都踩在同一套地基上:调 LLM(抽事实、巩固、反思)和生成 embedding(语义检索)。这一章讲这套横切抽象——如何把十几种 provider 收敛成一个接口、结构化输出怎么保证、embedding 的维度怎么管、以及一个容易被 CLAUDE.md 误导的层级配置真相。

本章要点

  • 三层:LLMProvider(门面)包一个由工厂选出的 LLMInterface 实现;引擎只和门面打交道(门面加并发许可、重试策略、追踪、多 LLM 路由)。embedding 是另一套更简单的层级,全服务器一个实例。
  • 接口没有流式——Hindsight 是批处理记忆系统,不是聊天 UI,所有调用都 await 到完成。
  • provider 选择是一个 if/elif 工厂;一大批(openai/groq/ollama/lmstudio/minimax…)都落到同一个 OpenAICompatibleLLM。
  • 结构化输出三级:strict(语法强制) → soft(prompt + json_object)→ 无语法(部分本地后端)。
  • embedding 维度由模型决定,schema 跟着模型走,换模型就重算维度(#2209)。
  • provider/model/key 不是 per-bank 可配的——它们是服务器级 + 按操作级;CLAUDE.md 说的"LLM 设置是层级的"在 bank 层并不成立。

2. LLM 接口:契约

定位:engine/llm_interface.py → LLMInterface(ABC)。四个抽象方法:verify_connection、call、call_with_tools、cleanup。

               initial_backoff=1.0, max_backoff=60.0, skip_validation=False,
               strict_schema=False, return_usage=False, cached_prefix=None) -> Any:
    # response_format: 结构化输出的 Pydantic 模型
    # scope: 追踪用的 scope 标识
    # strict_schema: 用 json_schema strict 语法强制(而非软的 json_object)
    # return_usage: True 则返回 (result, TokenUsage)
    # cached_prefix: 可缓存 system 前缀的不透明句柄(Gemini 等)
  • 没有流式:全仓库 grep stream 在 LLM 层是空的。所有调用都等到完成——这符合"记忆系统"而非"聊天 UI"的定位。
  • 能力钩子默认 no-op:supports_batch_api()、supports_prompt_caching() + get_or_create_cached_prefix() 等,不支持的 provider 就"透明地不缓存"。职责划分写得很清楚:"引擎决定什么可缓存,provider 只决定怎么缓存"(显式 Gemini CachedContent / OpenAI 自动 / Anthropic 内联标记)。
  • 工具调用返回 LLMToolCallResult,用一个类型化的 LLMToolChoice(AUTO/NONE/REQUIRED/NAMED)——"只在 provider 边界序列化",provider 的原生 tool-choice 方言不会泄漏进引擎代码。

3. 门面 LLMProvider:横切关注点

定位:engine/llm_wrapper.py → LLMProvider。

💡 构造函数故意"不读全局配置"

LLMProvider 的构造器接收约 20 个参数,刻意不读全局 HindsightConfig。为什么?这样"一个 provider 的有效配置就是它参数的纯函数"——这正是让多 LLM 链里每个成员能被独立配置的前提。把默认值的解析留给调用方。

LLMProvider.call 做完横切工作再委派:

  1. 重试策略解析:本次调用参数 → provider 配的默认 → 方法兜底(10/1.0/60.0)。
  2. strict_schema 解析一次:用 x if x is not None else get_config().llm_strict_schema。注释专门提醒:不能用 or——那会让"本次显式传 False"和"没传"无法区分。
  3. 并发许可:进入该 scope 的所有信号量(每操作 + 全局),先打一个 .queued 阶段。注释引了事故 #3002:有人曾对着根本没到达 Bedrock 的任务排查了一小时 llm.bedrock.*——原来是卡在排队。
  4. 委派给 _provider_impl.call(...);异常时把 provider 已上报的 usage 附到错误追踪上(provider 不管成不成功都收了钱)。

token 计费:两条路径

  • 返回路径:return_usage=True 返回 (result, TokenUsage);TokenUsage 有 input/output/total/cached/thoughts_tokens 和 __add__ 便于聚合。
  • 旁路:provider 在本地解析之前就把 usage 塞进 contextvar(stash_response_usage)。为什么?issue #2387——provider 调用可能成功了、也计费了,但随后的 JSON 解析/校验失败;这时要把真实 token 数附到错误追踪上(反正钱已经花了)。

重试循环在每个 provider 内部,指数退避;分类很讲究:401/403 快速失败不重试(认证错误重试无益);OutputTooLongError 不重试;MultiLLMProvider 再加一层——每个成员耗尽自己的重试后,路由器前进(failover 或加权轮询),但超长输出不 failover("换个 provider 也装不下")。

4. Provider 模型:一个 if/elif 工厂

定位:llm_wrapper.py → create_llm_provider(约 270–539 行)。没有装饰器注册表,就是对小写 provider 串的 if/elif。

OpenAICompatibleLLM(约 1700 行)是主力:它用一个 call_params dict + 各家小修补(Groq 的 seed/service_tier;MiniMax 温度钳到 [0.01,1];推理模型加 reasoning_effort 和 16k token 下限)吸收一大批 OpenAI 兼容后端。按操作选 provider 发生在 MemoryEngine.__init__,有三条独立的回退链:retain/reflect/consolidation_llm_provider or config.* or memory_llm_provider。

⚠️ LLMConfig 不是配置对象

LLMConfig = LLMProvider(就是个别名)。读 memory_engine._build_llm 时若以为 LLMConfig 是个纯配置,会一头雾水——它其实就是那个 provider 门面。

6. Embeddings:另一套更简单的层级

定位:engine/embeddings.py。

Embeddings ABC 只有四样:provider_name、dimension(int 属性)、initialize()、encode(texts)。实现有 local(sentence-transformers)、ONNX、TEI、OpenAI、Cohere、Gemini 等。引擎持有全服务器一个实例。

💡 维度由模型拥有,schema 跟着走

维度在初始化时探测(local 直接读模型的 get_sentence_embedding_dimension();TEI 则 embed 一个字面量 "test" 量长度),启动时把现役维度传进 migration,让 pgvector 列匹配。换模型会给 memory_units 重新定维,被设计成"结构上不可能踩到维度不匹配"(#2209)。归档表干脆不带 embedding 列,免得"归档向量"和现役模型对不上。

local vs TEI 两个细节:local 默认不用 MPS(变长负载下 MPS 漏内存);CPU 上的 encode 故意不做 gc/malloc_trim(它在 retain 紧循环里跑,每次 gc 太贵)。TEI 是 httpx 客户端,batch_size=32,只对连接错误/超时/5xx 指数退避重试。没有 embedding 级缓存——有的只是批处理和 GPU 内存回收。

7. 层级配置:一个重要的澄清

定位:config_resolver.py → ConfigResolver(get_bank_config 对外、resolve_full_config 内部保留凭证)。

解析顺序:① 全局(env)→ ② 租户覆盖 → ③ bank 覆盖。每次调用都现解析(不缓存),保证多 API server 一致。但关键在这里:

⚠️ "LLM 设置是层级的"在 bank 层是个误解

租户和 bank 的覆盖都会被过滤到 _CONFIGURABLE_FIELDS 白名单。而 LLM provider/model/key 字段不在这个集合里(它们在 _CREDENTIAL_FIELDS);白名单里只有行为字段(retain_chunk_size、retain_extraction_mode、mission、disposition、recall 预算等)。所以尽管 CLAUDE.md 简写成"LLM 设置是层级的",实际上 provider/model 的选择是服务器级、且只按操作(retain/reflect/consolidation 那三条静态回退链),从不按 bank。解析器甚至会从全局配置重新钉死多 LLM 链对象,"绝不可被租户/bank 覆盖"。

8. none 与 mock:两个特殊 provider

行为用途
NoneLLM安全网:任何调用都抛 LLMNotAvailableError。真正的降级在配置校验:llm_provider="none" → 强制 retain_extraction_mode="chunks"、关 observations、reflect 返回 400"无 LLM 也能跑"的降级形态
MockLLM确定性:记录每次调用,按 scope 返回罐头答案(retain 返回罐头事实,让 retain→recall→reflect 端到端可跑;去重裁决固定返回 keep),还能注入异常/假 usage离线测试

9. 设计决策与易踩坑

点说明
门面 + 纯函数构造器provider 有效配置 = 参数的纯函数,多 LLM 链成员才能各自独立
引擎定"什么"、provider 定"怎么"缓存策略统一在一个可选钩子后
失败分类学认证错误永不重试;超长输出永不重试、也永不 failover
计费诚实usage 在校验前就 stash;推理 token 从输出计数里扣除,避免重复计费
重复的 OutputTooLongError在 llm_interface.py 和 llm_wrapper.py 各有一个(同名不同身);从错的模块 import 去 except 会悄悄漏接
embedding 维度不匹配不可重试确定性错误,重试只是烧 worker 槽;需新请求或修好的后端
小模型在 strict 结构化输出上易循环门面专门把 attempt={n}/{N} 发布到 worker 阶段便于观察

小结

  • LLM 三层:接口 LLMInterface → 门面 LLMProvider(横切)→ 具体 provider(工厂 if/elif 选);无流式;结构化输出三级阶梯。
  • provider 一大批收敛到 OpenAICompatibleLLM;按操作选 provider(三条回退链);LLMConfig 就是 LLMProvider。
  • embedding 维度模型拥有、schema 跟随、换模型重算;无缓存。
  • provider/model/key 非 per-bank 可配(白名单只有行为字段)——别被 CLAUDE.md 误导。none/mock 各有用途。
