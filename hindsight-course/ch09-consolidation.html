第四部分 · 推理与巩固

09 · 巩固:从事实到观察

Hindsight 宣称自己"会学习,不只是记得"。这份"学习"就发生在巩固(consolidation):一个在 Retain 之后异步运行的后台 job,把零散的 world/experience 事实合成、更新成 observation。这一章讲它怎么运作、为什么不能在 Retain 里顺手做、以及为什么它对"标签"近乎偏执。

本章要点

  • 巩固是自底向上的"学习":facts → observation(memory_units 里 fact_type='observation' 的行)。它不是 mental_models 表(后者是用户定义、按需刷新的)。
  • 与 Retain 解耦:Retain 流式按块提交,进行的途中没有"全文事实全集";巩固又贵;解耦后还可崩溃续跑。
  • 工作队列就是一个 SQL 谓词:consolidated_at IS NULL AND fact_type IN ('experience','world')。
  • 核心策略:优先 UPDATE 而非 CREATE(一个 observation 挂多条证据 > 一堆各挂一条的孪生);标签是安全边界,不同标签的事实绝不共享一次 LLM 调用。
  • source 变了就删 observation + 重置 consolidated_at,让事实在下一轮重新巩固。

1. 巩固做什么,为什么和 Retain 分开

Retain 是记录流水线:抽事实、落库,并在每条事实上盖一个 observation_scopes 指令,但不合成任何东西。巩固是单独的学习流水线:读一批未巩固的事实,产出/更新 observation 行(带 proof_count 支撑数、source_memory_ids 证据集、history 变更历史)。

# NOTE: Observations are distinct from mental models (pinned reflections).

💡 为什么不在 Retain 里顺手巩固?

(1) 没有全集:Retain 流式按块提交,进行到一半时根本没有"这篇文档的全部事实",而观察需要跨块、跨文档聚合。(2) 成本:巩固是 LLM 重活(召回 + 合成 + 可选去重裁决),塞进 Retain 会让写入延迟和综合强耦合;独立出来可以在 worker 池里用自己的并发预算、还能用"与 bank 无关的可缓存 prompt 前缀"省钱。(3) 可重跑:进度按事实标记(consolidated_at),失败隔离(consolidation_failed_at),崩了/跑一半都能接着来。

2. observation_scopes:按什么粒度巩固

定位:consolidator.py → _resolve_obs_tags_list。

Retain 时每条内容可带一个 observation_scopes,决定"把这些事实按什么标签范围聚成观察":

取值含义
combined(默认/None)用该事实的完整标签集作为一个范围,做一次巩固
per_tag每个标签一次:标签 [a,b] 分别进范围 {a} 和 {b}
all_combinations标签的每个非空子集各一次:{a}、{b}、{a,b}
shared只对空范围做一次:产出的 observation 不带标签,用 tags_match="any" 匹配——所有事实聚成一个全局观察(用于跨"易变来源标签"去重)
显式 list[list[str]]每个内层标签列表一次,完全自定义
engine/consolidation/consolidator.py · _resolve_obs_tags_list(节选)python
parsed = _parse_observation_scopes(memory)
tags = list(memory.get("tags") or [])
if parsed == "per_tag":
    return [[t] for t in tags] if tags else None
if parsed == "all_combinations":
    return [list(c) for r in range(1, len(tags)+1) for c in combinations(tags, r)] if tags else None
if parsed == "shared":
    return [[]]                      # 一个空范围
if parsed == "combined" or parsed is None:
    return None                      # 默认:用事实自己的标签
return parsed                        # 显式 list[list[str]]

还有个 _resolve_write_scopes 把范围转成 frozenset,让并行调度器能按范围加锁:两个标签组若写范围有交集,就在共享范围上串行(防止抢同一行 observation);不相交的组并发跑。加锁顺序是一个全序,专门为了无死锁。

3. 巩固 job 的流程

定位:consolidator.py → run_consolidation_job / _run_consolidation_job / _process_memory_batch。

flowchart TB A["工作队列:SQL 谓词

先 delete,再 update,再 create"] E4 --> F["标记 consolidated_at=NOW()

engine/consolidation/consolidator.py · 取批与分组(节选)python
memories = await conn.fetch(f"""
    SELECT id, text, fact_type, ..., observation_scopes
    FROM memory_units
    WHERE bank_id = $1
      AND consolidated_at IS NULL
      AND consolidation_failed_at IS NULL
      AND fact_type IN ('experience', 'world')
    ORDER BY created_at ASC
    LIMIT ${limit_idx}""", *fetch_params)
if not memories:
    break

# 按精确标签集分组 —— 安全要求:不同标签的事实绝不能共享一次 LLM 调用。
tag_groups: dict[tuple[str, ...], list[dict]] = {}
for m in memories:
    tag_key = tuple(sorted(m.get("tags") or []))
    tag_groups.setdefault(tag_key, []).append(dict(m))

每个 LLM 批内部:① 每条事实并行召回相关 observation(就是复用 recall,但限定 fact_type=["observation"]、tags_match="all_strict"、reranking="interleave");② 跨批并集去重;③ 一次 LLM 调用处理 N 条事实 + 这些 observation;④ 顺序执行写动作(写要串行保一致)。执行顺序是先 delete(腾出 observation 名额)再 update 再 create。失败处理用自适应二分:一批失败就劈成两半重试,一直劈到单条;只有单条失败才盖 consolidation_failed_at。

4. Prompt:一个"防模型犯蠢"的样板

定位:consolidation/prompts.py。

prompt 分成"与 bank 无关、可缓存的 system 前缀"和"每批的 user 消息"——和第 04 章抽取 prompt 是同一个省钱思路:

engine/consolidation/prompts.py · build_consolidation_system_prompt(注释)python
# Holds only what is constant across banks: processing rules, input format,
# decision guide, and output format. The bank's MISSION is deliberately NOT
# here — baking it in would make the prefix bank-specific and force a separate
# Gemini context cache per mission. ... so this prefix is identical for every
# bank and a single CachedContent serves them all.

处理规则里几条尤其值得记(都是模型容易犯错的地方):

规则原文要旨
优先 UPDATE 而非 CREATE若新事实描述的是已有 observation 覆盖的同一规范事件/论断,更新它、把新事实挂为证据,不要建近重复的兄弟。"一个挂多条证据的规范 observation,永远好过一堆各挂一条的兄弟。"
一个 facet 一个 observation一个计数、一个实体、一个关系——绝不混并。
状态变化要更新"卖了 X""X 死了""搬到 Y" → 更新匹配的 observation 反映当前状态。
保留历史记录重大事件的 observation 是重要历史,绝不删除;删除要极其保守。
禁止计算"你没有全貌——绝不计算、推导、调整数值。用户说'我有 2 条狗'又说'我有条叫 Rex 的狗',别把数改成 3——你不知道 Rex 是不是那 2 条之一。"

输出是 {"creates":[...], "updates":[...], "deletes":[...]},每个动作都要带 reason("CREATE 要说明考虑过哪些已有 observation、为何都不匹配——这会被审计以抓重复创建")。而且每个 observation_id 至多一个 UPDATE(多个会互相覆盖)。

💡 模型不可信,所以层层设防

LLM 之后还有好几道确定性防线:_dedupe_updates 把同一 observation_id 的多个 update 合并;精确文本守卫丢掉"和上下文里已有 observation 一字不差"的 CREATE(因为"模型时不时就会这么干");可选的语义去重(阈值 <1.0 时)对每个 CREATE/UPDATE 探测 top-5 邻居,再用一次聚焦的 LLM 调用裁决"合并还是保留"。

📖 为什么巩固专用 interleave 重排?

巩固召回 observation 时用 reranking="interleave"(第 08 章讲过)。原因被实测写在注释里:cross-encoder 会把那条"几乎一样的孪生 observation"从语义第 1 打到重排第 37,RRF 也会把它挤出 512-token 预算——结果模型看不见它,又建了个重复的。interleave 保证每路 top 都有位置,孪生总能被看见,于是模型去 UPDATE 而非 CREATE。

5. 更新 vs 重建,以及失效

UPDATE 就地改写observation 的文本与 embedding、扩展证据、合并字段——绝不从头重建。注意两点:标签是"并"不是"替"(每个贡献者都能继续看见它);时间字段聚合(最早 start、最晚 end、最晚 mentioned)。每次 update 先把旧状态快照进 observation_history 表,限行数——因为曾用单 JSONB 列存历史,一条被反复强化的 observation 把它撑过 PostgreSQL 的 256MB jsonb 上限而卡死。

⚠️ 失效 = 删 observation + 重置 consolidated_at

当底层事实被删/被替换(文档重灌、删记忆、改标签、清空观察),delete_stale_observations_for_memories 会:① 删掉引用了这些事实的 observation(哪怕只少了一个来源,它的文本就过时了);② 把幸存的来源事实 consolidated_at 重置为 NULL,让它们下一轮重新巩固。这就是系统的"再巩固"机制:删 + 重置 = 把事实放回工作队列。反向的竞态(巩固到一半源事实被删)由 _filter_live_source_memories 在每次写之前 FOR SHARE 复检源 id 来堵上。

6. 触发与调度

  • Retain 后自动:每条事实落库后调 _submit_post_insert_maintenance,受 bank 配置 enable_observations + enable_auto_consolidation 门控。失败只记日志、绝不上抛——巩固不能搞砸一次 retain。
  • bank 级去重:提交时若已有该 bank 的"未限定范围 pending"操作,就复用原 operation_id,不重复排队(去重只看 pending,不看 processing——处理中的任务用的是它启动时的水位线,之后新增的事实仍需新一轮)。
  • worker 领取:独立 worker 进程每 500ms 轮询 async_operations,且给巩固预留槽位(默认 {"consolidation": 2}),保证巩固有算力又不饿死 retain。
  • 手动 / 维护:POST /banks/{id}/consolidate、清空某记忆的 observations、维护对账扫 backlog。
  • 自我重排:一轮撞到预算上限就重新入队——这个失败必须上抛,否则"bank 有 backlog 却没排上的活——悄悄卡死"。
  • 下游:一轮最终完成后,给标签匹配、且设了 refresh_after_consolidation 的用户 mental model 提交刷新任务。

7. 设计决策与易踩坑

点说明
标签是安全边界,不是提示不同标签的事实绝不共享 LLM 调用;召回用 all_strict;写前再按事实复检召回集——防跨租户/跨用户泄漏
可见性由算法决定,模型说了不算标签是算法继承/合并的;prompt 明确"不要输出 tags"
只巩固 world/experienceobservation 之间不互相巩固;单条失败被标记后不再自动跑(有手动 recover)
total_count 只是时点估计运行中新写入的会被捞起,processed 可能超过它
语义去重仅 PG用了 unnest/array_agg/UPDATE...FROM;Oracle 跳过,改用 observation_sources 连接表
shared 范围无标签、全局可见用错就是跨标签泄漏;文档把它定位为"跨来源标签去重"的专用模式

小结

  • 巩固 = 自底向上的学习:facts → observation(一种特殊事实);与 retain 解耦(无全集、贵、可重跑)。
  • 工作队列是 SQL 谓词;按精确标签集分组(安全);每批"并行召回 → 一次 LLM → 顺序写";先删后建。
  • 策略核心:优先 UPDATE;禁止计算;层层防模型犯蠢;标签是安全边界。
  • 失效 = 删 observation + 重置 consolidated_at = 再巩固。
